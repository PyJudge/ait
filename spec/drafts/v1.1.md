# ait v1.1 — 계약을 코드에서 떼어 낸다

2026-10-14 사용자와의 논의를 정리한 초안. 브랜치 `v1.1`(master `89338dc`에서 분기). 이 문서가 v1.1의 결정 목록이다. 명세 본문(`ait-phase1-spec.md`)은 결정이 끝난 뒤 이것에서 다시 쓴다.

## 0. 왜

v14의 복잡함은 한 원인에서 나온다: **계약(`.ait/`)과 명세 파일이 코드와 같은 tree에 있다.** 그래서 모든 git 조작(일반 커밋, merge, rebase, cherry-pick, reset)이 계약을 건드릴 수 있고, ait는 그것을 막거나 수습해야 했다. guard pre-commit, 통합 hook과 되돌리기, merge driver, 판 합치기와 `prev` DAG, 사고 판, 묶음 무결성, 설치 확인(H12), 이력을 실어 나르는 `contract pull`이 모두 이 수습이다.

v1.1은 원인 자리에서 끊는다. **계약은 코드와 이력을 공유하지 않는 ait 브랜치에만 있다.** 코드 브랜치의 git 조작은 원리적으로 계약을 건드릴 수 없으므로, 위 장치는 고칠 것이 아니라 필요가 없어진다.

## 2. 모델

### 2.1 ait 브랜치

- `refs/heads/ait/<name>`. 코드 브랜치와 공통 조상이 없는 orphan 이력이다(gh-pages와 같은 모양). 사람은 `git switch ait/<name>`으로 들어가 보고 고칠 수 있다.
- 안에 있는 것은 두 종류뿐이다(U4).
  ```
  <ID>.yaml              계약
  fulfill/<ID>-<RID>.md  이행 한 번 = 파일 하나 (U6)
  ```
- `ait init`은 `ait/<D>`를 만든다. D는 git의 `repo_default_branch_name()`(`refs.c:707`)이 주는 이름이다: `init.defaultBranch`, 없으면 2.53에서 `master`(U11).
- ait 브랜치끼리 주고받고 합치는 일은 git이다: `git fetch origin ait/master`, `git merge`, `git push`, `git log ait/master -- K.yaml`.

### 2.2 체크아웃·체크인 (U3, U9, U10)

- **체크아웃** `ait use ait/<name>`(이름은 Q6): 이 worktree가 상대하는 ait 브랜치를 정한다. `git config --worktree ait.branch`에 둔다. 작업 폴더는 바뀌지 않는다.
- ait 브랜치는 `refs/heads/ait/*`만 센다(원격 추적 브랜치 `refs/remotes/*/ait/*`는 세지 않는다). 하나뿐이면 체크아웃 없이 그것을 쓴다. 여럿인데 체크아웃이 없으면 스스로 고르지 않고 멈춘다. 0개일 때는 Q9. `git switch ait/x`로 한 번 들어가 보면 git의 DWIM이 로컬 브랜치를 만들어 수가 늘어난다(9.8). 그 뒤의 멈춤은 사용자가 만든 브랜치 때문이므로 그대로 둔다.
- **쓰기 전 거절(F1)**: 체크아웃한 ait 브랜치가 어느 worktree에서든 git으로 체크아웃되어 있으면, 쓰기 명령은 처음에 `fatal: 'ait/<name>' is already used by worktree at '<path>'`로 멈춘다. `update-ref`는 git이 브랜치 갱신 때 하는 이 검사를 건너뛰고, 그 worktree의 다음 `git commit`이 체크인을 되돌리기 때문이다(9.9). git의 `die_if_checked_out`(`branch.c:847`)과 같은 판정, 같은 문구다. 이 worktree의 HEAD가 `ait/*`이면 fulfill의 코드 커밋이 ait 브랜치에 들어가므로(U4) 같은 판정에 걸린다.
- **체크인**: ait 쓰기 명령(demand·amend·cancel·fulfill 등) 하나가 체크인 하나다. 작업 폴더와 코드 브랜치를 건드리지 않는다.
  1. 체크아웃한 ait 브랜치의 tip T를 읽는다.
  2. 임시 index(`GIT_INDEX_FILE`)에 T를 올리고 바꿀 파일만 바꾼다. `write-tree`, `commit-tree -p T`.
  3. `update-ref refs/heads/ait/<name> NEW T`. T가 그새 움직였으면 git이 거절한다(CAS).
  4. 거절되면 새 tip을 T'로 읽는다. 이 요청이 바꾸는 파일이 모두 T와 T' 사이에 바뀌지 않았으면 T'에서 2부터 다시 한다. 하나라도 바뀌었으면 멈춘다. 예외는 없다. (처음에는 "`rev`가 그대로면 다시"라는 예외를 두었으나, `rev`를 두는 `--force` amend 둘이 동시에 오면 뒤의 것이 앞의 것을 소리 없이 덮었다: 9.10.) fulfill도 이 규칙 하나를 쓴다(2.8의 3). 그래서 같은 계약을 동시에 이행하면 첨부 목록 때문에 뒤의 것이 멈춘다 — Q8.
- git의 선례: `git notes`(`refs/notes/commits`), `git stash`(`refs/stash`)가 작업 폴더를 건드리지 않고 임시 index로 다른 ref에 커밋한다.

### 2.3 계약 YAML

```yaml
rev: r7f3a                 # 조건을 마지막으로 바꾼 요청의 ID (2.5)
kind: demand
creator: agent-a
consumer: src/ui/
provider: src/api/
state: future
body: |
  GET /users는 페이지당 50건 이하를 돌려준다
command: make test-api     # 코드 쪽 파일을 부르는 방법일 뿐이다 (U4)
fulfilled:                 # 첨부 목록: 더하기만 한다 (U6)
  - fulfill/K1-r9b21.md
```

- 레코드와 명세 정의가 하나다. 명세가 몰래 바뀔 길(코드 tree의 커밋)이 없으므로 `file` 고정과 묶음 무결성이 필요 없다.
- `state`에는 사람이 정한 것만 둔다(future, cancelled 등). "이행됨"은 저장하지 않고 계산한다(2.6).

### 2.4 이행 파일 (U5, U6)

```markdown
---
contract: K1
rev: r7f3a                 # 이행할 때 본 계약의 rev (결과 틀에 ait가 적어 준다)
by: agent-b
command: make test-api
outcome: pass              # pass | forced
code:                      # 확인할 때 provider 범위마다 그 객체 (파일은 blob, 디렉터리는 tree)
  src/api/: 3f2a…
---
12 passed. 페이지 크기 경계(49/50/51)를 확인함.
```

- 한 번 쓰면 고치지 않는다. ait는 이를 검사하지 않는다(F5: 고쳤는지 알려면 ait 브랜치의 이력을 걸어야 하는데, squash·rebase로 이력이 사라지면 판정이 갈린다. ait는 데이터로 판정하고 git 조작을 쫓지 않는다).
- 코드를 커밋 OID가 아니라 범위의 객체로 가리킨다. 그래서 rebase·squash·cherry-pick 뒤에도 유효하다. 디렉터리 범위는 tree OID 하나로 가리키므로, 그 아래에 파일이 새로 생겨도 바뀐 것으로 잡힌다(`git rev-parse HEAD:src/api`).

### 2.5 `rev`는 조건을 바꾼 요청의 ID다

`rev`는 계약을 만들거나 조건·상태를 바꾸는 요청이 그 요청 ID로 바꾼다. 이행(첨부 한 줄 더하기)과 `--force` amend(2.7)는 바꾸지 않는다.

같은 계약을 두 ait 브랜치에서 고치면 git merge가 반드시 충돌해야 한다. 숫자를 올리는 `rev`는 양쪽이 같은 값이 되면 같은 변경으로 합쳐져 충돌이 사라진다. 아래 9.3에서 재현했다: 한쪽은 provider를 `a.c`→`a.c,b.c`로, 다른 쪽은 `a.c`로 이행해 첨부를 더했는데 `rev: 8`이 같아 **충돌 없이** "b.c까지 이행됨"이 됐다. 고유한 요청 ID면 같은 경우가 충돌한다.

### 2.6 이행 판정 (계산, 저장 안 함)

브랜치 하나의 tree X에서 계약 K는:
- 첨부 목록의 이행 파일 중 `rev`가 K의 `rev`와 같은 것이 **유효한 이행**이다. 다른 `rev`의 이행은 옛 조건의 것이라 세지 않는다(U7). 이 비교 하나가 조건 변경도, ait 브랜치끼리의 merge(9.6)도 막는다.
- 유효한 이행 중, **계약의 지금 provider 범위마다** `code`에 같은 범위가 있고 그 객체가 X의 것과 같은 것이 있으면 **이행됨**. 이행 파일에 없는 provider 범위가 하나라도 있으면 그 이행은 이 판정에서 맞지 않는다(F4: `rev`를 두고 provider를 넓힌 `--force` amend 뒤에 확인하지 않은 범위가 이행된 것으로 보이지 않게).
- 유효한 이행은 있는데 그런 것이 없으면 **이행 뒤 바뀜**(v14의 미확인).
- 유효한 이행이 없으면 **이행 안 됨**.
- X는 읽는 명령에서는 index의 tree다(v14 7.8.1과 같다). fulfill이 적는 객체는 코드 커밋의 tree에서 읽는다.

같은 코드라도 체크아웃한 ait 브랜치에 따라 결과가 다르다. 이것이 요구사항을 시험한다는 뜻이다(U9).

### 2.7 amend와 `--force` (U7)

- `ait amend K …`: 조건을 바꾸고 `rev`를 이 요청 ID로 바꾼다. 옛 이행은 첨부 목록과 `fulfill/`에 그대로 남지만 `rev`가 달라 세지 않는다(2.6). 과거 기록은 건드리지 않는다(U6).
- `ait amend K … --force -m <why>`: 조건을 바꾸되 `rev`를 그대로 둔다. "같은 조건이다(사소하다)"는 판단이고, 그래서 옛 이행이 계속 센다. 판단은 그 체크인 커밋의 메시지와 작성자로 남는다.
  - 대가: 두 ait 브랜치에서 각자 `--force` amend를 하면 `rev`가 안 바뀌므로 git이 충돌 없이 합칠 수 있다. 둘 다 사소하다고 책임진 변경이므로 받아들인다.
- `ait fulfill K --force -m <why>`: 확인을 돌리지 않고 지금 blob으로 `outcome: forced`인 이행 파일을 더한다. v14의 `check forced`와 같은 뜻이다.

### 2.8 fulfill 순서 (U8)

0. **먼저 판정한다.** 체크아웃한 ait 브랜치의 tip T를 읽고 본다: K가 이행할 수 있는 상태인가, 결과 파일의 `rev`(에이전트가 받은 결과 틀에 ait가 적은 것)가 T의 K `rev`와 같은가, 결과 형식이 맞는가. 틀리면 멈춘다. 아무것도 바뀌지 않는다.
1. 코드 브랜치에 코드를 커밋한다.
2. 그 커밋의 blob으로 이행 파일을 쓰고, 첨부 한 줄을 더해 T 위에 체크인한다(2.2).
3. CAS에 지면 2.2의 4를 따른다: 이 요청이 바꾸는 파일(이행 파일과 K.yaml)이 그새 안 바뀌었으면 새 tip 위에서 다시 하고, 바뀌었으면 멈춘다. 남는 것은 기록 없는 코드 커밋, 즉 "이행 안 됨"뿐이다.

git의 선례: 로컬 커밋 뒤 `git push`가 거절되면 커밋은 남기고 이유와 다음 일을 알린다(`builtin/push.c` `reject_reasons`).

### 2.9 hook

강제가 없어지므로 hook은 선택이다. 없어도 맞게 동작한다.
- 구독 알림: ait 브랜치 ref가 바뀔 때 `git diff --name-only OLD NEW`로 바뀐 계약을 안다. 로컬 `reference-transaction`, 서버 `post-receive`.
- 코드 쪽 경고(원하면): post-commit에서 "이행된 K의 provider 경로를 바꿨다".

## 3. 명령과 그것이 부르는 git (U12)

| 명령 | git |
|---|---|
| `ait init` | `extensions.worktreeConfig=true` 켜기, orphan 커밋, `update-ref` |
| `ait use` (Q6) | `git config --worktree ait.branch` |
| 쓰기 명령(체크인) | `GIT_INDEX_FILE`, `update-index`, `write-tree`, `commit-tree`, `update-ref NEW OLD` |
| `ait status`, `ait peek` | `git status`(status) + ait 브랜치 `ls-tree`·`cat-file` + 코드 쪽 index tree |
| 이력 | `git log ait/<name> -- K.yaml` |
| 구독 알림 | `diff-tree OLD NEW` |
| 주고받기·합치기 | git 그대로 (ait 명령 없음) |

**ait 고유로 남는 것**: 계약 YAML과 이행 파일 앞머리의 형식 검사, 상태 전이 규칙, fulfill 순서(2.8), 이행 판정(2.6), 출력과 hint.

## 6. 열린 질문 (사용자가 정할 것)

- **Q1 행 범위.** v14의 범위는 `PATH:S-E`까지 받고 diff로 위치를 따라간다(3.3–3.10). 이행 판정을 blob으로 하면 같은 파일 안의 다른 곳이 바뀌어도 "이행 뒤 바뀜"이 된다. (a) 범위를 경로와 디렉터리로 줄인다: 사상 코드가 빠지고 판정이 blob 비교 하나다. 대신 큰 파일에서 경고가 넓어진다. (b) 행 범위를 남긴다: 판정은 그 범위 행의 내용 비교가 되고 사상이 남는다(+250행).
- **Q2 session.** 이행 파일의 `by:`와 구독은 에이전트 이름이 필요하다. v14 session을 그대로 둘지, worktree 설정 하나(`ait.agent`)로 줄일지.
- **Q3 계약 종류.** demand·offer·undertake·drop·cancel을 모두 v1.1로 가져가는가. 가져가면 undertake는 offer YAML의 `undertakes:` 목록이 된다.
- **Q4 읽는 명령.** v14에는 코드의 계약을 보는 길이 셋이다: `ait peek PATH`(7.9.3), `ait todo PATH`(7.8.1), `ait todo`의 `index` 블록. 같은 겹침 판정을 두 명령이 따로 한다. 제안: 전체 현황은 `ait status`(git status 출력 뒤에 계약 부분: 내 약속, 이행 뒤 바뀐 것, 지금 변경이 건드리는 계약 — U2의 "전체 todo"), 특정 코드나 계약은 `ait peek PATH|ID`(git에 맞는 짝이 없다. `git show PATH`는 인자 뜻이 달라 쓸 수 없다: C15 — U2의 "해당 코드 todo"). 겹침 판정은 한 함수이고 둘이 같이 읽는다. `todo`는 없앤다.
- **Q5 U7의 장치.** C10대로 첨부 목록은 비우지 않고 `rev` 비교로 옛 이행을 거르는 것으로 바꿔도 되는가(9.6). 참고: 사람이 ait 브랜치에서 조건을 손으로 고치고 `rev`를 두면 `-m` 없는 `--force`와 같아진다. v14는 고정의 해시(PINS)로 이것을 데이터에서 잡았다. 같은 효과를 원하면 `rev` 대신 조건 내용의 해시를 쓰는 길이 있으나, 그러면 `--force` amend가 옛 이행을 살릴 장치가 따로 필요하다.
- **Q6 체크아웃 명령의 이름.** `git checkout`은 HEAD와 작업 폴더를 바꾸고, ait의 체크아웃은 설정만 바꾼다. 쓰임이 달라 `checkout`은 쓸 수 없다(C15). 후보: `ait use ait/<name>`. 체크아웃·체크인은 개념의 이름으로 문서에 쓴다.
- **Q8 첨부 목록을 둘 것인가.** U6는 계약 YAML이 이행 파일을 가리키게 했다. 검수(9.10, 9.11)에서 그 목록이 세 가지 비용을 낸다는 것이 재현됐다. (1) 두 ait 브랜치(또는 clone)에서 같은 계약을 각자 이행하면 git merge가 목록 끝에서 반드시 충돌한다. 목록 없이 이행 파일만 더하면 충돌 없이 둘 다 남는다. (2) 같은 계약을 동시에 이행하면 체크인 규칙(2.2의 4)에서 뒤의 것이 멈춘다. 목록이 없으면 이행은 새 파일만 더하므로 언제나 다시 얹힌다. (3) 목록과 `fulfill/<ID>-*.md` 파일이 같은 사실을 두 곳에 둔다. 제안: 목록을 없애고 "`fulfill/<ID>-*.md` 중 `rev`가 맞는 것"을 그 계약의 이행으로 본다. 가리킴은 파일 이름(`<ID>`)이 한다.
- **Q9 ait 브랜치가 0개일 때.** clone 직후에는 `origin/ait/master`만 있고 로컬 ait 브랜치가 없다(9.8). (a) 멈추고 `hint: ait use origin/ait/master`처럼 원격 것을 가리킨다. (b) 원격 추적 브랜치가 하나뿐이면 그것으로 로컬 브랜치를 만든다(git switch의 DWIM과 같은 모양). (c) `ait init`을 다시 하라고 한다.
- **Q7 `ait init`** (닫힘: C15). `git init`처럼 준비하고 다시 해도 결과가 같다. 같은 쓰임이므로 이름을 유지한다.

## 9. git 전제 재현 (git 2.53.0)

### 9.1 작업 폴더를 건드리지 않고 다른 브랜치에 커밋 (C2)
```
echo "dirty" >> a.c
export GIT_INDEX_FILE=$S/idx
B=$(printf 'kind: demand\n…' | git hash-object -w --stdin)
git update-index --add --cacheinfo 100644,$B,K1.yaml
T=$(git write-tree); C=$(git commit-tree $T -m "demand K1")
git update-ref refs/heads/ait/main $C ""     → create ok
git status --short                            →  M a.c   (그대로)
```

### 9.2 CAS (C2)
```
git update-ref refs/heads/ait/main $C3 $C
→ fatal: … cannot lock ref 'refs/heads/ait/main': is at b38e90f… but expected 9af12c1…  (exit 128)
```

### 9.3 `rev` 숫자는 충돌을 숨긴다 (C4)
base `rev: 7, provider: a.c`. ait/master: `rev: 8, provider: a.c,b.c`. ait/try: `rev: 8, provider: a.c, fulfilled: - f/K1-r1.md`.
```
git merge-tree --write-tree --name-only ait/master ait/try   → exit 0
결과: rev: 8 / provider: a.c,b.c / fulfilled: - f/K1-r1.md
```
`rev: rA` / `rev: rB`로 같은 경우:
```
→ 충돌 (내용): K1.yaml에 병합 충돌   exit 1
```

### 9.4 `extensions.worktreeConfig` (C11)
```
git config --worktree ait.branch ait/main   → exit 0
git config --local --get ait.branch         → ait/main   (저장소 설정에 씀)
git config extensions.worktreeConfig true
git config --worktree ait.branch ait/x      → .git/config.worktree 에 씀
```

### 9.5 이름과 이력
```
git branch ait          → fatal: cannot lock ref 'refs/heads/ait': 'refs/heads/ait/main' exists
git merge-base main ait/main   → exit 1 (공통 조상 없음)
```
`ait`라는 코드 브랜치가 있으면 ait 브랜치를 만들 수 없다. `ait init`은 그때 git의 오류를 그대로 전한다.

### 9.6 첨부 목록 비우기는 merge에서 뚫린다 (C10)
base `rev: r0, provider: a.c, fulfilled:`(빈 목록). ait/master: amend로 `rev: rA, provider: a.c,b.c`, 목록 비움(바뀐 행 없음). ait/try: 옛 조건으로 이행, `rev: r0` 그대로, `- fulfill/K1-r1.md` 더함.
```
git merge-tree --write-tree ait/master ait/try   → exit 0
rev: rA / provider: a.c,b.c / fulfilled: - fulfill/K1-r1.md
```
옛 조건의 이행이 새 조건 아래 첨부로 남는다. 이행 파일의 `rev: r0` ≠ `rA`로만 걸러진다. (base 목록이 비어 있지 않으면 같은 경우가 충돌한다: exit 1.)

### 9.7 디렉터리 범위의 tree OID (C7)
```
git rev-parse HEAD:src/api   → f2793fb…
echo b > src/api/new.c; git add .; git commit -qm 2
git rev-parse HEAD:src/api   → 5343a5e…   (새 파일로 바뀜)
git ls-tree $(git write-tree) src/api   → 040000 tree 5343a5e…   (index의 tree에서도 같은 값)
```

### 9.8 clone 뒤의 ait 브랜치 수 (C17, Q9)
```
git clone -q r cl; cd cl; git for-each-ref refs/heads/ait   → (없음; origin/ait/*만 있음)
git switch -q ait/f1 && git switch -q -
git for-each-ref refs/heads/ait   → refs/heads/ait/f1   (DWIM이 로컬 브랜치를 만듦)
```

### 9.9 체크아웃된 ait 브랜치에 update-ref하면 다음 커밋이 되돌린다 (C16)
```
git worktree add -q $S/w ait/master; echo n > $S/w/note.txt; git -C $S/w add note.txt
ckin.sh ait/master $O K1.yaml 'rev: rB\nprovider: a.c,b.c\n'   → checkin ok
git -C $S/w status --short   → M  K1.yaml / A  note.txt   (체크인을 거꾸로 stage한 상태)
git -C $S/w commit -qm human; git show ait/master:K1.yaml   → rev: r0 / provider: a.c
```
`ckin.sh`는 2.2의 1–3단계(`read-tree OLD`, `hash-object -w`, `update-index --cacheinfo`, `write-tree`, `commit-tree -p OLD`, `update-ref NEW OLD`)를 그대로 옮긴 스크립트다.

### 9.10 `rev` 예외는 동시 `--force` amend를 덮는다 (C3)
```
T=$(git rev-parse ait/master)
A=$(ckin.sh ait/master $T K1.yaml 'rev: r0\nbody: Y\n')
ckin.sh ait/master $T K1.yaml 'rev: r0\nbody: Z\n'   → fatal: … is at 581a0bd… but expected a428b00…
(T와 T'의 rev가 같다 → 옛 규칙으로 다시 얹음)
ckin.sh ait/master $A K1.yaml 'rev: r0\nbody: Z\n'; git show ait/master:K1.yaml → body: Z   (Y가 경고 없이 사라짐)
```

### 9.11 두 브랜치의 이행이 첨부 목록에서 충돌한다 (Q8)
```
base: fulfilled: [- fulfill/K1-r1.md]; ait/f1에 r2, ait/f2에 r3 한 행씩
git merge-tree --write-tree --name-only ait/f1 ait/f2   → 충돌 (내용): K1.yaml에 병합 충돌
```
