# v2에서 v1.1로 옮기기 — 계획

2026-10-18. 사용자: "2를 1.1로 마이그레이션하는 방법도 정리해줘". 이 문서는 계획이다. 대상은 criminal-decision-draft이고, 다른 v2 저장소도 같은 절차를 따른다. 옮기기는 7장의 결정이 끝난 뒤 한다.

## 1. 무엇이 다른가

| | v2 | v1.1 |
|---|---|---|
| 계약이 사는 곳 | 코드 브랜치의 `.ait/<ID>` (레코드 행) | 독립 브랜치 `ait/<name>`의 `<ID>.yaml` |
| 조건 | `file <정의 파일> MODE BLOB def`. 정의 파일은 코드 쪽에 있다 | 계약 안의 `specs`(정의 파일의 내용을 복사한다) |
| 검사 재료 | 정의의 `inputs`, 레코드의 `file … input` 행(blob 고정) | spec의 `fixtures`(U60). blob은 이행 파일의 `code`에 적힌다 |
| 범위 | `consumer`·`provider PATH BLOB`. 파일 범위도 blob을 고정한다 | `consumer`·`provider`는 경로만. 행 범위만 기준 blob을 가진다 |
| 저장된 상태 | `future`·`current`·`cancelled` | `future`·`cancelled`·`withdrawn`. current는 저장하지 않고 이행 기록과 코드로 계산한다(규칙 4) |
| 확인 | 레코드의 `check reported <pins>`. 결과는 코드 커밋 메시지에 있다 | `fulfill/<ID>-<RID>.md`(이행 파일). `code`에 확인한 코드의 항목을 적는다 |
| 떠맡기 | `.ait/undertake/D-O` 파일(`state undertaken`·`released`) | offer의 `undertakes`·`undertakes-partially` 목록 |
| 이력 | 레코드의 `prev` | `ait/<name>`의 git 이력 |
| 만든 이 | `creator AGENT SID` | `creator: AGENT` |
| hook | 커밋·merge·push hook 여러 개(로컬 `.git/hooks`) | 알림용 `reference-transaction` 하나 |

## 2. 실측: criminal-decision-draft (2026-10-18, master `a0dc121a`)

- **기준 브랜치는 master다.** 다른 브랜치(`codex/*`, `t*`, `five-layer` 등)는 모두 master의 조상이다(`git rev-list master..<branch>`가 0).
- **계약 277개**: demand 202, offer 75.
  - live 74개(`state current`): demand 36, offer 38. `future`는 없다.
  - cancelled 203개.
- **떠맡기 81개**:
  - 둘 다 live인 `undertaken`이 36개다. 부분 떠맡기는 없다.
  - 나머지는 `released`(14)이거나 한쪽이 cancelled인 것(31)이다.
- **live 74개의 조건**:
  - 정의 파일은 74개 모두 저장소에 blob이 있다. 68개는 JSON, 6개는 YAML이다(JSON도 YAML이므로 v1.1이 읽는다).
  - JSON 68개의 키는 `body`·`inputs`이고, exec 43개는 `engine`·`command`를 더한다. `environment`는 없다.
  - `inputs`는 1,134개이고 모두 파일 경로다(디렉터리·행 범위가 없다).
- **live 74개의 범위**:
  - provider는 모두 파일 범위다(`/`·디렉터리·`new:`가 없다). 그래서 모두 v1.1에서 이행 기록을 가질 수 있다.
  - consumer 6개가 공백이 든 경로다(`research_notes/1심 형사판결서 작성과 계산 설계/…`, `research_notes/형사판결서 함수와 기대값 검토/…`). v1.1은 U67부터 공백이 든 경로를 받으므로 그대로 옮긴다.
- **확인 행**: live 74개 모두 `check reported`다(`check forced`가 없다).

## 3. 규칙(한 문장)

**옮기기는 가져오기 커밋 하나다. v2 레코드가 적은 사실(조건, 범위, 떠맡기, 확인한 코드의 blob)을 v1.1의 형식으로 그대로 적고, 다시 확인하지 않으며, ait가 그것을 읽어 내는 판정으로 검증한다.**

- 새 사실을 만들지 않는다. v2에서 확인한 판(blob)이 지금 코드와 같으면 current이고, 다르면 `current ?unverified`다. v1.1의 규칙 4가 그대로 판정한다.
- ait 명령으로 다시 만들지 않는다. 그렇게 하면 ID와 만든 이가 바뀌고, 74개를 모두 다시 확인해야 한다. 이행 기록은 `ait fulfill`만 쓴다(규격 4.8 FULFILMENT). 그래서 가져오기는 git으로 ait 브랜치에 쓰는 커밋이다. 규격이 git으로 바뀐 ait 브랜치를 읽고 판정하는 것과 같다(`ait status`가 형식 오류와 구조 불변식 위반을 보여 준다).

## 4. 대응표 (계약 하나)

| v1.1 | v2에서 |
|---|---|
| 파일 | `<ID>.yaml`. group은 없다(v2에 group이 없다) |
| `condition-id`, `change-id` | 가져오기의 RID 하나(`R` + 12자리). 모든 계약이 같은 값이다 |
| `kind` | `role` |
| `creator` | `creator AGENT SID`의 AGENT |
| `consumer` | `consumer PATH BLOB` 행들의 PATH를 `,`로 잇는다. 행 범위면 `PATH:S-E BLOB`(기준 blob)이다. demand만 |
| `provider` | `provider PATH BLOB` 행들의 PATH |
| `state` | `current` → `future`(이행 기록이 current를 만든다), `cancelled` → `cancelled` |
| `specs` | `def` 행의 blob을 읽은 정의 하나. `body`·`engine`·`command`·`success`(없으면 `[0]`)는 그대로, `inputs` → `fixtures` |
| `undertakes` | offer O에 대해, `.ait/undertake/D-O`가 `state undertaken`이고 D·O가 둘 다 live인 D들 |
| `undertakes-partially` | 빈 목록(v2에 부분 떠맡기가 없다) |
| `fulfilled` | live이고 확인 행이 맞으면 이행 파일 하나 |

**이행 파일** `fulfill/<ID>-<RID>.md` (live 계약마다):

| 필드 | 값 |
|---|---|
| `contract`, `condition-id` | 그 계약의 ID, 가져오기의 RID |
| `by`, `session` | 레코드의 `creator`의 AGENT·SID |
| `commit` | `.ait/<ID>`에 그 `check reported` 행을 쓴 코드 커밋. v2는 코드와 레코드를 한 커밋으로 쓴다 |
| `outcome` | `pass`(`check reported`) |
| `code` | provider 범위마다, 그리고 fixture마다 레코드에 고정된 blob과 그 커밋의 mode: `"PATH": "MODE blob BLOB"` |
| 본문 | 그 커밋의 메시지(v2는 확인 결과를 거기 남겼다)와 `imported from ait v2 at <master 커밋>` |

- **확인 행이 맞는지 본다.** v2의 `check reported <pins>`는 그 판의 provider 행과 `file` 행을 이은 바이트열의 해시다(v2 시나리오 `pins(REV, ID)`). 가져오기는 이것을 다시 계산한다. 같지 않으면 그 계약에는 이행 파일을 쓰지 않는다. 그러면 future로 남아, 다시 확인해 `ait fulfill`해야 한다.
- 레코드의 `file … input` 행이 정의의 `inputs`보다 많은 계약이 40개다. offer는 떠맡은 demand의 재료까지 고정했기 때문으로 보인다(v2 개념 "offer는 떠맡은 요구의 것까지"). v1.1에서는 offer의 확인 범위가 자기 spec의 fixtures뿐이다. 그래서 `code`에는 자기 fixtures의 항목만 쓴다. 떠맡은 demand는 자기 이행 파일이 있다.

## 5. 절차

1. **멈춘다.** 그 저장소에서 일하는 에이전트를 모두 멈추고 worktree의 변경을 커밋한다. 옮기는 동안 v2 레코드가 바뀌면 안 된다.
2. **가져오기 스크립트**(7장의 질문 4)를 master에서 돌린다.
   - `.ait/`를 읽어 4장대로 YAML과 이행 파일을 만든다.
   - `git hash-object -w` → 임시 index → `write-tree` → `commit-tree`로 부모 없는 커밋 하나를 만들고, `refs/heads/ait/master`로 둔다.
   - 그 커밋 메시지에는 가져온 master 커밋과 버린 것의 목록(cancelled를 버리면 그 ID들, 확인 행이 맞지 않은 ID들)을 쓴다.
3. **v1.1을 설치하고 `ait init`을 돌린다**(같은 이름의 로컬 ait 브랜치를 그대로 쓰고, 알림 hook을 둔다. git plumbing으로 만든 `ait/master`를 init이 받고 status가 읽는 것을 2026-10-18에 시험 저장소에서 확인했다). 로컬 `.git/hooks`의 v2 hook(`pre-commit`, `commit-msg`, `post-commit`, `post-merge`, `pre-merge-commit`, `pre-push`)은 지운다. 그대로 두면 모든 커밋에서 v2 ait를 부른다.
4. **검증**(6장).
5. **코드 브랜치를 정리하는 커밋 하나.**
   - `.ait/`의 v2 레코드를 지운다(`.ait/`는 v1.1에서 초안 자리이고 `info/exclude`에 들어간다, U47).
   - 정의 파일(`specs/…yaml`)은 지우지 않는다. 계약이 내용을 복사해 가졌지만, 사람이 고쳐 다시 `amend`에 줄 원본이다.
   - `setup.sh`로 스킬과 `AGENTS.md`·`CLAUDE.md`의 ait 안내를 v1.1로 바꾼다.
6. **push**: `git push -u origin ait/master`, 그리고 master.
7. **다른 clone과 worktree**: v1.1을 설치하고 v2 hook을 지운 뒤 `ait init`을 돌린다. 옛 브랜치를 master에 merge하면 `.ait/`의 v2 레코드가 되살아날 수 있다. 옛 브랜치는 merge하지 않거나, merge 뒤 `.ait/`를 지운다.
8. **클라우드**: `v1.1-cloud-plan.md`의 묶음을 `tools/ait/`에 넣는다.

## 6. 검증

1. `ait status /`에 `warning: bad format`이 없고, 구조 불변식 위반(4.10)이 없다.
2. live 계약 수가 74이고, 떠맡기가 36쌍이다.
3. 판정을 v2와 견준다.
   - v2 바이너리(`../ait-v2`)의 `ait todo`가 current라고 한 계약은, 코드가 그 뒤 바뀌지 않았으면 v1.1에서도 current다.
   - 다르면 `current ?unverified`이고, `provider`나 `fixtures` 행의 `?changed`가 그 파일을 가리킨다.
   - 두 목록을 표로 만들어 하나씩 설명할 수 있어야 한다.
4. 계약 하나를 골라 `ait future amend K -m <why>`로 다시 열고 `ait fulfill`까지 해 본다. 가져온 계약이 v1.1 명령으로 계속 다뤄지는지 보는 것이다.
5. `ait contract push`가 `ait/master`를 원격에 올린다.
