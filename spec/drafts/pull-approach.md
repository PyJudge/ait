# `ait contract pull`: 어떻게 여기까지 왔나 (검수자용)

검수 대상은 [pull-criteria.md](pull-criteria.md)(기준, 개정 9)다. 이 문서는 그 기준이 어떤 문제에서 나왔고, 경우를 어떤 차원으로 나눴는지를 적는다. 근거가 된 사용자의 결정은 [pull-decisions.md](pull-decisions.md)의 1~30이다. 같은 파일의 "Claude가 허락 없이 정한 것 (기록)" 1~113은 Claude가 결정과 v14에서 끌어낸 것이다. 직전 검수는 [pull-review-r24.md](pull-review-r24.md), [pull-review-r27.md](pull-review-r27.md), [pull-review-r30.md](pull-review-r30.md), [pull-review-r33.md](pull-review-r33.md), [pull-review-r36.md](pull-review-r36.md), [pull-review-r39.md](pull-review-r39.md), [pull-review-r42.md](pull-review-r42.md)에 있다.

**사용자 원칙 (2026-10-10):** git과 싸우지 않는다. 고치는 길이 있고 경고로 드러나고 원칙이 분명하면 된다. ait는 계약 데이터의 규칙만 정하고, git이 하는 일(코드 합치기, abort, merge 설정과 driver, 사용자가 직접 하는 git 조작)에는 장치를 더하거나 보장을 하지 않는다.

## 1. 지나온 길

1. **v14** (`../ait-phase1-spec.md` 7.12): `pull RID`는 요청 커밋과 그 조상을 git merge로 받는다. 아직 이행되지 않은 코드가 섞이면 계약 커밋만 골라 받는다. 이미 받았는지는 요청 ID로 본다.
2. **개정 2** (r24 검수): 받는 단위를 계약으로 바꾸고, 판과 `prev`로 판정했다. 그런데 받는 방법이 판의 내용만 복사하는 것이었다. 남의 커밋이 내 이력에 들어오지 않으므로, 확인 기록이 사라지고 구현이 기대는 파일이 빠졌다.
3. **개정 3** (r27 검수): 이력째 받는다(git merge). 들어오는 계약은 모두 지정하고, 코드는 언제나 함께 받는다. git 조작은 보지 않고 판만 본다.
4. **개정 4** (r30 검수): 계약 파일과 고정 명세 파일은 pull이 정하고, git merge 결과는 코드에만 쓴다. 끝난 쪽이 이기고, 여러 끝을 한 번에 받고, 갈라짐은 3-way로 보고, 확인은 계약 파일의 확인 행에 적는다. 검수에서 다음이 드러났다.
   - pull이 적는 새 판이 덜 정해졌다(`prev`, 확인 행, 다른 clone에 전해지는지).
   - 여러 끝을 받다 중간에 코드가 충돌하면 중간 커밋이 남고 abort해도 시작 상태로 돌아가지 않았다.
   - 3-way가 셋 이상에서 꼬리를 물거나 공통 조상의 blob이 없을 때 한쪽을 알리지 않고 버렸다.
   - git merge 충돌을 손으로 풀어 cancel을 되살린 판이 사고로 잡히지 않았다.
5. **개정 5** (r33 검수): 결정 20~25와 그 검수에서 끌어낸 고칠 것(기록 47~66)을 반영했다.
   - 결과 판은 최신 판을 모두 포함한다. 새 판의 `prev`는 최신 판 모두다.
   - 여러 끝은 중간 커밋 없이 받는다. 코드 충돌은 마지막 끝에서만 허용한다(git의 octopus와 같다).
   - `prev`에 끝난 판이 있으면 결과도 끝난 판이어야 한다.
   - 같은 PINS면 `reported`가 이긴다.
   - `pull D`는 D가 끝인 떠맡기 기록도 본다.
   - 3-way가 꼬리를 물면 고른다. 3-way를 먼저, 끝난 쪽 규칙을 그다음에 한다.
   - 고르기에는 `-m <why>`가 붙는다.
   - 재현 스크립트의 PINS를 v14 5.4대로 고쳤다.
   - 검수에서 다음이 드러났다. 사고 판 위에 쌓은 판이 사고로 잡히지 않았다. 들이는 쪽에서 ait 밖에서 고친 명세 파일을 코드로 받았다. 함께만 받을 수 있는 두 끝이 둘 다 충돌하면 막다른 길이었다. pull의 고르기가 남의 이행을 버려도 되돌린 쪽이 생기지 않았다.
6. **개정 6** (r36 검수): 결정 26·27과 기록 67~87을 반영했다.
   - 사고 판 위에 쌓은 판도 사고다.
   - 들이는 쪽이 계약이 고정한 명세 파일을 ait 밖에서 바꿨으면 사고로 보고 받지 않는다. 상대 쪽에서 코드였던 파일만 코드 변경으로 받는다.
   - 코드 충돌은 파일마다 한 번까지 한 merge 상태에 함께 둔다(결정 26).
   - pull의 고르기로 남의 이행을 버리면 고른 쪽이 되돌린 쪽이다(결정 27).
   - 새 판 위에 얹는 판의 `prev`는 그 새 판과 그 `prev` 모두다.
   - 코드 충돌로 멈춘 pull의 로컬 상태를 없앴다. 마치는 커밋의 hook은 데이터만 본다. abort와 merge 설정에 대한 보장을 뺐다.
7. **개정 7** (r39 검수): r36 검수에서 끌어낸 기록 88~98을 반영했다. 사용자 결정은 새로 없다.
   - 끝난 판을 포함하는 판은 그 끝난 판이어야 한다(기록 88).
   - 고정 명세 파일은 두 쪽의 변경을 똑같이 본다. 옛 판·버린 판의 명세는 받지 않고, 그 쪽 고정과 다른 내용은 사고로 경고하고, 나머지는 합쳐 다시 고정한다. 지우는 변경은 받지 않고 경고한다(기록 89, 90).
   - 마치는 커밋의 hook도 출발 판에서 사고 판을 뺀다. 마치는 hint는 v14의 마치는 커밋이다(기록 91, 95).
   - 결정 26의 차례는 파일마다 한 번만 충돌하는 차례를 찾는다(기록 92). 나눠 받는 hint는 끝마다 하나다(기록 97).
   - 결정 27의 판정은 커밋과 그 부모로 한다. 되돌린 커밋이면 경고와 H10을 쓴다(기록 93, 94).
   - HEAD의 명세 파일 사고는 0단계에서 멈춘다(기록 96).
8. **개정 8** (r42 검수): 결정 28·29와 r39 검수에서 끌어낸 기록 99~106을 반영했다.
   - 사고 판을 거쳐서라도 끝난 판을 포함하는 판은 사고다(결정 28, 기록 88을 올림).
   - 고정 명세 파일은 판이 아니라 고정으로 견준다. 들이는 쪽은 들이는 커밋이고, 끝난 판은 고정하지 않고, 지우는 변경은 먼저 빼고, 경로마다 3-way 한다(기록 100). 받는 변경끼리 충돌하면 둘 다 계약의 고정이어도 코드 충돌이다(결정 29).
   - 되돌린 커밋은 v14 1.5d의 식을 바꾼 하나의 식이다(기록 99).
   - 결정 26의 "또 바꾸면"은 합친 결과와의 merge base로 보고, 나눠 받는 명령은 차례대로 정한다(기록 101).
   - 마치는 커밋의 hook은 들어오는 쪽의 사고 판만 빼고, 7.1.3-4는 레코드마다 본다. 마치는 hint와 되돌림 경고는 v14 문구와 조건 그대로다(기록 102~104).
9. **개정 9** (이번, r42 정리): 결정 30과 기록 107~113을 반영했다. 다음은 C 구현이다(사용자 제안).
   - 명세 파일은 ait가 받지 않을 변경만 정하고, 그 변경을 그 쪽에서 뺀 뒤 git이 코드와 함께 합친다(기록 107). 같은 장치를 r27부터 여섯 번 덧댄 원인(pull이 git 대신 합침)을 없앴다.
   - 마치는 커밋의 다시 고정은 그 판 위에 얹는다(기록 108). 나눠 받기는 결정 20의 상태로 돌아갔다(기록 109).
   - TIE는 내 판을 포함하는 판의 커밋을 먼저 고른다(결정 30).

## 3. 무엇을 실제로 돌렸나

- [pull-criteria-runs/](pull-criteria-runs/)의 스크립트가 각 행의 이력을 실제 git 저장소(2.53.0)로 만든다.
  - 출력하는 것은 git의 사실과 기준의 낱말에 따른 데이터다. git의 사실은 merge와 merge-tree 결과, 충돌 경로, 들이는 커밋과 그 새 커밋 수다. 데이터는 포함, 최신 판, 3-way, 꼬리 물기, 끝난 쪽, 남는 판, 사고 판, 형식이 틀린 판, 확인 행이다.
  - `scen9.py`가 개정 9에서, `scen8.py`가 개정 8에서, `scen7.py`가 개정 7에서, `scen6.py`가 개정 6에서, `scen5.py`가 개정 5에서 더한 경우를, `scen4.py`가 개정 4의 경우를, `scen.py`가 개정 3부터 이어 온 경우를 만든다.
  - `flows.py`는 hint를 그대로 따른 결과가 v14의 5.9 b~e를 지나는지, 새 미확인이 없는지를 본다.
  - `cycle3.py`는 D-O 떠맡기 경우를 한 번에 받는다.
  - `verify-r30.py`와 `verify-r30-gitcycle.sh`는 r30 검수의 주장을 Claude가 다시 돌린 것이다(`verify-r30.py`는 지금 규칙으로).
  - 로그는 기준 머리말에 적은 차례로 만든다. 차례가 바뀌면 커밋 OID만 바뀐다.
- ait의 판정 자체(멈출지, 무엇을 hint로 줄지)는 기준의 규칙으로 손으로 정했다. 스크립트는 판정하지 않는다.

## 4. 검수에서 특히 보아 줄 것

**r42는 개정 8에서 바뀐 것만 본다.** 바뀐 것은 1절의 "형식이 틀린 판"(값 검사), "사고 판"(결정 28), "되돌린 커밋"(하나의 식), "합친 결과"("또 바꾸면"의 기준), "받는 결과"(고정 명세 파일 전체, 코드인 파일의 범위), 2절 1(XT1과 결정 26)·4(멈춤 문장, 나눠 받는 hint, 목표 상태)·6(충돌 상태, 출력, 마치는 hint, hook의 출발 판, 되돌림 경고), "그래서"의 MF2 예외, 3절의 새 행(RP5, RP6, U1z, IND4, DL2, SP5~SP8, SF2, SP4c, RN2, HK3, MH9, MH10)과 고친 행(RP4, SF1, RV3b, MH8, ORD1), 4절과 5절의 고친 곳, 결정 28·29와 기록 99~106, 재현 스크립트(`lib.py`의 형식 검사와 `reopen_commit`, `scen8.py`, `verify-r30.py`)다. 그 밖은 r39까지 본 그대로다.

먼저 범위: ait가 git의 동작(abort, merge 설정과 driver, rename, 사용자가 직접 하는 git merge·rebase 등)을 다루도록 장치·상태·보장을 더하라는 지적은 하지 않는다. 그런 경우는 "ait의 데이터 규칙이 깨지는가"로만 본다. 깨지면 그것을 지적하고, 고치는 길은 데이터 규칙과 경고로 낸다.

1. 기준의 규칙이 결정 1~29와 어긋나는 곳. 기록 99~106 중 결정이나 v14에서 하나로 끌어낼 수 없고, 고르는 답에 따라 사용자가 겪는 결과가 달라지는 것(사실은 Claude의 선택인 것)이 있는지. 문구나 계산 순서처럼 결과가 같은 것은 빼고 본다.
2. 같은 입력에서 두 구현이 서로 다른 결과를 낼 수 있는 곳(정의가 모자란 곳). 특히 1절의 "결과 판", "남는 판"(꼬리 물기), "앞으로 나감"(없는 blob), "받는 결과"(코드 변경과 버린 명세 변경의 구별), 결정 22의 확인 행.
3. hint를 그대로 따랐는데 같은 거절이 되풀이되거나, 막다른 길이나 교착으로 가는 경우.
4. 판을 잃거나, 사용자가 모르게 변경이 버려지거나, 같은 경고가 되풀이되는 경우. "결과 판은 최신 판을 모두 포함한다"가 깨지는 이력.
5. 결정 20·26(여러 끝, 중간 커밋 없음, 파일마다 충돌 한 번)을 git plumbing으로 실제로 만들 수 있는지. 마치는 커밋의 hook이 데이터만 보고도 pull의 결정을 그대로 두는지.
6. 표에 빠진 경우 중 규칙이 답을 정하지 못하는 것. 5절(규격에서 바뀌는 것)에 빠진 조항.

반례와 대안은 반드시 실제 git 저장소에서 돌린 명령과 출력으로 보여 준다.
