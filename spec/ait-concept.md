# ait — 컨셉

## 한 줄 정의

ait는 여러 코딩 에이전트가 코드에 거는 **계약을 git 안에서 다루게 하는 git 확장**이다. 계약은 에이전트가 코드 범위에 대해 거는 요구나 보장(그리고 그 철회 예약)이고, 무엇을 충족해야 하는지는 그 계약의 **명세 파일**(조건과 확인 방법을 적은 명세 정의와 그것이 선언한 검사 재료)에 적는다. 아직 이행되지 않은 계약을 **약속**이라 한다.
- 에이전트는 계약을 요구하고, 보장하고, 떠맡고, 고치고, 이행한다.
- 수많은 에이전트가 한 코드베이스를 동시에 고치는 것을 전제로 한다. 코드에는 주인이 없다. 요구는 코드에 걸고, 그 일에 **착수하는 에이전트가 그때 떠맡는다.**
- 계약이 바뀌거나 current 계약의 provider 코드가 확인 없이 바뀌면 **그 코드를 공유하는 에이전트 중 그 계약을 약속하거나 요구한 에이전트(떠맡은 쪽, 되돌린 쪽 포함)와 그 범위를 구독한 에이전트에게 알린다. 다른 코드베이스에도 알린다.**

## 기준: git의 단순성

ait가 강제하는 것은 짧은 목록 하나가 전부다. 나머지는 모두 된다.

강제하는 것:
- 계약 레코드의 형식·구조와 상태 전이
- 명세 파일(명세 정의와 그것이 `inputs`로 선언한 스크립트·데이터·환경 정의)은 계약을 거쳐서만 바뀔 것
- 계약을 바꾸는 커밋과 코드를 바꾸는 커밋이 섞이지 않을 것
- 이행 조건: **확인 결과**. 확인할 모든 명세 정의(offer는 떠맡은 요구의 것까지)에 대해 이행하는 에이전트가 근거를 단 결과를 내고, 모두 pass일 것. 하찮으면 `--force`로 "사소하다고 판단하고 책임진다"는 확인을 남긴다. 확인은 계약 파일에 `check reported`나 `check forced`로 기록된다
- current 계약은 확인 결과와 함께 성립할 것: ait 명령이 쓰는 커밋(등록·다시 고정·이행·`ait commit`)이 그 계약을 current로 만들거나 그 코드에 **걸릴** 때. 확인할 코드를 찾을 수 없으면 커밋하지 않는다. 일반 커밋은 요구하지 않고, 통합에서 확인 없이 고정이 바뀐 current는 약속으로 되돌린다. `contract pull`은 받기 전에 멈춘다
- `ait contract push`는 계약을 올릴 것: 계약 커밋이 없는 push는 멈춘다(`--force`로도). 올리는 커밋이 만든 미확인이 남은 push는 멈추고, `--force`면 그 미확인을 사소하다고 확인하는 기록을 남기고 올린다(그 코드가 남아 있을 때만)
- `ait contract pull`은 지정한 계약을 이력째 받을 것: 판이 갈라졌는데 고르지 않으면, 지정하지 않은 계약까지 바뀌면, 받는 결과의 구조가 틀리면, 받으면 확인한 것이 확인 없이 바뀌면 멈춘다. 마지막 것만 `--force`로 책임지고 넘긴다
- 계약 파일과 명세 파일은 ait의 규칙으로만 바뀔 것: 규칙 밖에서 바뀐 판(**사고**)이 있는 브랜치는 고칠 때까지 막히고, 남의 pull은 그 판을 받지 않는다

나머지는 모두 된다:
- 모든 git 조작
- hook 끄기
- 아무 에이전트나 아무 계약이나 고치고 이행하기
- current 계약의 코드를 바꾸고, 옮기고, 지우기. 확인 없이 바꾸면 그 계약은 **미확인**이 되고, 그것이 받는 쪽에 알림으로 간다. 여러 커밋에 걸쳐 바꾸려면 먼저 그 계약을 약속(future)으로 되돌린다(`ait future amend`). 되돌린 동안의 변경은 미확인이 아니고, 다시 이행할 때 확인한다. 규칙은 하나다: current는 확인된 것이다
- 기대는 쪽(consumer) 코드 바꾸기. 계약이 요구하는 것은 provider의 조건뿐이므로 아무 일도 일어나지 않는다
- 확인 결과의 내용. ait는 CI가 아니다. 과제마다 pass가 근거와 함께 보고됐는지만 보고, 그 결과를 커밋 메시지에 남긴다

에이전트에 대해서는 하나를 가정한다: **에이전트는 유한한 시간에, 한정된 문맥에서, 명세를 충족하는 구현을 할 수 있다. 다만 이행하기 전까지는 실수할 수 있다.** 그래서 ait는 이행을 믿고 기록하며, 이행 전의 실수는 막지 않고 경고로 드러낸다. 한정된 문맥에서 한 구현이므로 이행한 뒤에도 코드는 다시 고치고(여러 커밋에 걸친 수정·리팩터링은 확정된 계약을 약속으로 되돌려 한다), 모든 출력은 다음 명령을 준다.

경고와 알림은 최소충분하게 한다. 기준은 둘이다: **위험인가**(따로 한 변경들이 한 계약에서 만나거나, 이행 전의 실수가 확인된 것을 바꿨다), 그리고 **받는 쪽이 정말 그 위험에 놓이는가**.
- 둘 다 맞을 때만 알린다. 예를 들어 같은 요구를 둘이 떠맡거나, 떠맡은 요구의 조건이 바뀌거나, 확인된 코드가 확인 없이 바뀐 것은 받는 쪽(그 계약을 약속하거나 요구한 쪽, 떠맡은 쪽, 구독자)에 알린다.
- 다시 확인만 한 것(`--force` 포함)은 뜻이 바뀌지 않았으므로 아무에게도 알리지 않는다. current offer의 미확인은 그 offer를 만든 쪽에 알리지 않는다(약속도 요구도 아니므로, 구독하면 받는다). 누가 무엇을 했는지는 기록(`peek`)에 남는다.
- 오류·경고·알림은 받는 에이전트가 자기 문맥에서 할 다음 명령을 `hint:`로 준다. 따로 읽어야 할 해석표가 필요하면 출력이 모자란 것이다.

규격(`ait-phase1-spec.md`)은 이 기준을 두 개의 **전제**(코드에는 주인이 없다, 에이전트는 유한한 시간에 한정된 문맥에서 명세를 충족하는 구현을 할 수 있되 이행 전까지는 실수할 수 있다)와 아홉 개의 **규칙**으로 적고, 나머지는 모두 거기서 나오는 결론으로 쓴다. 규칙에 없는 예외는 두지 않는다. 저장하는 것은 누가 무엇을 했다는 사실뿐이고, 미확인·받는 쪽·다음 명령 같은 판정은 그 사실에서 그때 계산한다.

막는 대신 **누가, 무엇을, 어떻게** 했는지를 커밋 기록줄, 이력, 알림으로 드러낸다. 출력과 오류 표기는 git의 선례를 그대로 따른다(`fatal:`·`error:`·`warning:`·`hint:`, 종료 코드 128·1·129). 무엇이 막히고 무엇이 되는지가 분명해야, 예측하지 못한 실제 상황에서도 쓸 수 있다.

## 왜 에이전트 코딩에 필요한가

| 에이전트 코딩의 문제 | ait의 답 |
| --- | --- |
| **휘발된다.** 컨텍스트가 넘치거나 재시작하면 무엇을 약속했는지 잊는다 | 계약이 저장소에 남는다. `ait todo` 한 번이면 내 약속이 다시 보인다. 내가 떠맡은 요구, 그 조건(body)과 확인할 명령, 남은 일이 함께 나온다 |
| **"됐다"고 주장한다.** 구현 없이 완료를 선언하거나 테스트를 고쳐 통과시킨다 | 이행은 확인 결과로만 된다. **고정된 판**의 명세 정의마다 무엇을 돌려 무엇을 봤는지 결과를 내야 이행 커밋이 만들어진다. 그 결과는 커밋에 남아 상대가 본다. 명세 파일을 바꾸면 그것은 계약 변경이 되고, 상대에게 알림이 간다 |
| **잡아 두고 손대지 않는다.** 누가 맡은 것처럼 보여 아무도 못 한다 | 착수할 때만 떠맡고, 그만두면 자기 offer를 거둔다(cancel). 이미 누가 맡았어도 그것 없이 나아갈 수 없으면 함께 떠맡는다. 여럿이 떠맡아도 깨지지 않고, 먼저 이행한 쪽이 요구를 충족시킨다. 남은 쪽은 알림의 hint대로 정리한다 |
| **떠맡고 잊는다.** 남의 요구를 맡겠다고 해 놓고 자기 것만 끝낸다 | 떠맡기는 비대칭이다. 요구는 그 자체로 먼저 이행될 수 있다. 반대로 offer는 떠맡은 요구의 명세 파일까지 확인해야 이행되고, 아직 future인 요구는 같은 커밋에서 함께 이행된다. `ait todo`가 그 요구의 조건과 확인할 범위를 보여 준다. 떠맡긴 요구는 고아가 되지 않는다 |
| **기다린다.** 남의 구현이 끝나야 내 일을 시작한다 | 약속(future)과 그 명세 파일을 기준으로 바로 개발한다 |
| **사람이 메시지를 나른다** | 계약 변경이 곧 알림이다. 상대 에이전트가 띄운 `ait listen`이 변경 전문과 할 일(`hint:`)을 내보낸다(입력 큐에 바로 넣는 것은 3단계) |
| **누구에게 알려야 할지 모른다** | 바뀐 계약을 약속하거나 요구한 에이전트(떠맡은 쪽, 되돌린 쪽 포함)와, 그것을 구독한 에이전트에게만 간다. 약속이 끝나면 그 약속 때문에 오던 알림도 멈춘다. 다시 확인만 한 것은 아무에게도 가지 않는다. 알림에는 받는 쪽이 할 일이 `hint:`로 붙는다 |
| **전제가 조용히 깨진다.** 남이 기대는 코드를 무심코 바꾸거나 옮긴다 | current는 언제나 확인된 것이다. 변경이 current 계약의 provider에 닿으면 그 계약은 그 변경에 **걸린다**. 고치기 전에는 `peek now`가 걸릴 계약을 보여 준다. `ait commit`은 걸린 계약을 같은 커밋에서 확인하고, 확인할 코드가 없으면 커밋하지 않는다. 여러 커밋에 걸친 리팩터링은 먼저 그 계약을 약속으로 되돌린다. 그 밖에 무심코 바꾼 것은 미확인이 되고, 새 미확인이 될 때 받는 쪽에 알림이 간다 |
| **동시 수정이 덮인다** | 계약은 판마다 앞선 판(`prev`)을 적는다. 받을 때 두 쪽이 공통 조상 뒤에 둘 다 바꿨으면 `contract pull`이 고르게 하고, 고른 판은 고르지 않은 판도 `prev`에 담는다. 고르지 않은 쪽에 알림이 간다. 코드는 git이 합치고 충돌은 git처럼 드러난다 |
| **누가 무엇을 했는지 모른다** | `ait peek ID`가 이력을 보인다. 누가 만들고, 떠맡고, 고치고, 다시 확인하고, 이행했는지가 나온다. 확인한 근거는 그 커밋 메시지에 있다. hook을 우회한 변경은 이력에 `event - ?` 행으로 남는다 |
| **합의 절차가 없다** | 따로 합의하지 않는다. 요구(demand)를 건 쪽은 그 약속을 기준으로 계속 개발하고, 그 일에 착수하는 에이전트가 그때 최신 판을 들여 떠맡는다(undertake). 이행되면 요구를 건 쪽이 그 이행과 구현을 받아 이어서 개발한다. 조건이 틀렸으면 고친다(amend). 모두 기록과 알림으로 오간다 |
| **다른 저장소의 에이전트와는 조율할 길이 없다** | 서버 없이 git remote만으로 된다. push한 계약은 상대의 listener가 fetch하는 순간 알림이 된다 |

명세 파일의 중심은 **명세 정의**(YAML)다. 조건과 확인 방법을 함께 적는다.

```yaml
body: 재고가 0인 상품의 예약 요청은 거절한다.   # 조건. ait todo가 구현 목표로 보여 준다
engine: exec                                   # 생략하면 prompt
command: [sh, tests/no_oversell.sh]
environment: node                              # prepare(의존성 설치)·env·cwd·timeout을 정한 환경 정의
inputs: [tests/no_oversell.sh]
```

- **exec**: 확인할 명령과 환경이다. exit 코드가 `success`(기본 0)에 있으면 충족이다.
- **prompt**(engine 생략): 코드를 읽고 판단할 조건이다.
- 1단계의 ait는 어느 쪽도 실행하지 않는다. 이행하려는 에이전트에게 과제(조건, 돌릴 명령과 환경, 확인할 tree)를 주석으로 주고, 그 에이전트가 확인해 결과와 근거를 낸다(`-r`). ait가 exec를 직접 돌리는 것은 2단계다.
- 정의가 `inputs`로 선언한 스크립트·데이터와 환경 정의까지 계약이 함께 고정한다. 그래서 테스트를 몰래 바꿀 수 없다(`inputs`에 없는 파일은 고정되지 않고 경고가 나온다).
- 어느 코드에 구현할지 아직 모르면 **추상 약속**으로 건다: provider를 `/`(코드베이스 전체)나 `src/` 같은 디렉터리로 둔다. 요구도 offer도 된다(`ait future demand src/order.c / specs/x.yaml`: "어딘가가 이걸 충족해야 한다"). future에만 쓸 수 있고, 이행할 때 실제로 구현한 코드로 좁힌다(`ait fulfill O=src/runner.c,src/cli.c`). current는 언제나 구체 코드를 가리킨다.

## git과 hook이 대부분을 푼다

| 문제 | 해결 |
| --- | --- |
| 계약을 어떻게 공유하나 | 커밋·push·fetch. 계약도 코드처럼 clone된다 |
| 계약을 주고받기 | `ait contract push`는 내 브랜치를 통째로 올린다. 올릴 것이 없으면 noop, 계약 커밋이 하나도 없으면 멈추고(`git push`로), 올리는 커밋이 만든 미확인이 남아 있으면 멈춘다(`--force`면 사소하다고 확인하는 기록을 남기고 올린다). `ait contract pull D…`는 지정한 계약의 받을 판이 처음 들어간 커밋과 그 조상을 받는다. 그 이력이 바꾸는 계약은 모두 지정해야 하고, 코드는 함께 온다. 그래서 계약 커밋을 코드 커밋보다 먼저 하면 남이 내 약속을 받을 때 아직 이행되지 않은 코드가 가지 않는다. git은 보낼 때 고를 수 없으므로, 고르는 일은 받는 쪽만 한다 |
| 같은 계약을 동시에 고치면 | `contract pull`이 판 체인(`prev`)으로 나중 판을 고르고, 한쪽만 바꿨으면 그쪽을 받는다(3-way). 진짜 동시 수정만 고르게 한다. 한쪽이 끝냈으면 끝난 쪽을 받는다. 계약 파일은 git merge에 맡기지 않는다 |
| 코드가 충돌하면 | `contract pull`은 git merge처럼 멈춘다. 계약 파일과 명세 파일은 pull이 이미 정해 두고, 충돌한 코드만 풀어 마치는 커밋을 한다. 그 커밋과 그 밖의 git 조작(cherry-pick·rebase·revert)의 해결 커밋은 hook이 데이터로 정리한다: 계약을 다시 고정하고, 합치며 고정이 바뀐 current 계약은 확인되지 않았으므로 약속으로 되돌리고, 합친 코드가 확인된 것과 다르면 미확인으로 드러난다 |
| git만 써도 알림이 가나 | 간다. 각 에이전트의 `ait listen`이 ref를 1초마다 보다가, 계약의 새 판과 current 계약을 새 미확인으로 만든 커밋이 commit·merge·cherry-pick·fetch로 들어오면 알린다. 같은 판은 몇 커밋에 생기든 한 번만 간다. listener가 없는 동안의 사건은 다음에 띄울 때 나온다(지워진 브랜치에만 있던 것은 빼고) |
| ait가 없는 환경이면 | hook은 그냥 통과하고, merge driver는 git 기본 병합으로 돌아간다. IDE·CI의 git이 멈추지 않는다 |

## 사용법

```sh
ait init                                                             # 시작할 때마다. 이 clone을 준비하고, 처음이면 .ait/init 표시를 커밋한다
ait session open --agent me                                          # 나를 등록 (기본 session이 없으면 이 worktree의 기본이 된다)
ait listen >> "$(git rev-parse --git-common-dir)/ait-inbox.<SID>" &       # 알림을 받는다 (다른 clone의 변경까지 받으려면 --fetch 60)
ait peek now src/stock.c                                             # 고치면 걸릴 계약 읽기 (약속까지 보려면 now 없이)
ait sub src/order.c                                                  # 바뀌면 알림을 받을 범위 구독 (ait unsub으로 지운다)

# 계약 만들기: 입구는 둘, 관문은 하나
ait future demand src/order.c src/stock.c specs/x.yaml -m "이유"           # ① 도우미: 한 명령 = 계약 커밋 하나
ait contract new demand                                                       # ② 직접 작성: 틀을 받아 채우고
ait contract add .ait/D… specs/x.yaml && ait contract commit -m "이유"   #    관문으로

ait future offer src/stock.c specs/y.yaml as o undertake D… o -m "착수"     # 착수할 때 요구를 떠맡는다 (그만두면 ait future cancel O…)
ait todo                                       # 내 약속 + 떠맡은 요구의 조건(body)·확인할 명령 (범위의 미확인은 ait todo <범위>)
ait fulfill O… -m "구현"                       # -r 없이: 확인할 과제와 결과 틀을 받는다. 커밋하지 않는다
ait fulfill O… -r <check-result> -m "구현"     # 확인해 채운 결과로 이행 = 구현 + 계약 상태 + 결과를 커밋 하나로
ait commit -m "정리"                           # 코드만 커밋. 걸린 계약이 있으면 과제를 주고, -r(하찮으면 --force)로 같은 커밋에서 확인
ait future amend O… -m "옮길 예정"            # 여러 커밋에 걸친 리팩터링은 먼저 약속으로 되돌린다 → 끝나면 ait fulfill O…=src/b.c -r …
ait contract push                              # 다른 clone으로 공유 (같은 clone의 에이전트는 listener가 곧 받는다)
ait contract pull D…                           # 바뀐 계약이나 내 요구의 이행 받기 (알림의 hint에 이 명령이 있다)
ait peek D…                                    # 누가 무엇을 어떻게 했나
ait amend K… -r …                              # 미확인을 다시 확인한다(코드를 옮겼으면 새 범위를 준다)
```

## 검토 고리 예

1. 저자가 설계를 `future demand`로 올린다. 설계를 prompt 정의의 조건으로, 시험 스크립트를 exec 정의로 적는다(둘 다 그 계약의 명세 파일).
2. 다른 코드베이스의 검토 에이전트들이 알림을 받고 들인다. 고친 뒤 `contract commit`하고 `ait contract push`한다.
3. 저자는 수정마다 알림을 받아 들인다.
4. 두 검토자가 같은 계약을 동시에 고쳤다면 저자의 `contract pull`이 고르게 한다. 고른 판은 고르지 않은 판도 담고, 고르지 않은 검토자에게 알림이 간다.
5. 검토자는 알림의 hint대로 결과 판을 받는다.

사람이 손으로 하던 "보내고, 모으고, 합치는" 일이 git 위에서 돈다.

## 1단계에서 하지 않는 것

- 우회를 막지 않는다(`--no-verify`, ait 없는 merge, revert, rebase 등). 기록줄 없는 변경은 이력에 `event - ?` 행으로 드러나고, rebase된 커밋은 원래 기록줄을 그대로 가진다. 계약을 규칙 밖에서 바꾼 판은 사고로 드러나 그 브랜치가 고칠 때까지 막히고, 옛 판으로 돌아간 브랜치는 옛 상태에 있을 뿐 남에게 전해지지 않는다. push hook은 결과 상태의 형식·구조와 명세 파일 일치만 본다.
- 명세 정의를 실행하지 않는다. 확인 결과가 참인지 보장하지 않고, 누가 무엇을 근거로 했는지를 남긴다.
- 범위는 내용만 고정한다(mode만 바뀐 것은 미확인이 아니다). 함수 단위 범위, rename 추적은 하지 않는다. 여러 offer 명세 파일의 합이 요구를 함의하는지도 따지지 않는다. 요구 자신의 명세 파일을 확인할 뿐이다.
- 서버나 daemon이 없다. 알림은 각 에이전트가 띄운 `ait listen`으로만 받는다. 다른 clone의 알림은 fetch할 때 도착한다. 에이전트의 입력 큐에 바로 넣는 hook 전달은 3단계다.
