# v1.1 검사 재료 — 계획

2026-10-17. 사용자: "input이라는 이름이 너무 헷갈려. 다른 이름으로 해서 넣자. 계획부터". 이 문서는 계획이고, 명세 본문과 코드는 결정이 끝난 뒤 바꾼다. 키 이름은 `fixtures`다(U60).

## 1. 왜: 규칙 4가 v1.1 안에서 참이 아니다

- U4는 "검사 재료(테스트, 데이터)도 코드이므로 코드 브랜치에 둔다"고 한다.
- 규칙 4는 "계약은 지금 `condition-id`로 한 이행 기록이 있고 그 기록의 코드가 지금 코드와 같을 때만 current다"라고 한다.
- 그런데 이행 파일의 `code`(2.5)는 provider 범위만 적는다. 그래서 검사 재료는 규칙 4 밖에 있다.
  - 이행한 뒤 테스트를 약하게 고쳐도 계약은 `?unverified`도 아닌 current로 남는다.
  - 조건 본문은 그대로이므로 `condition-id`도, 결과의 유효성(C40)도 그것을 못 본다.
  - 환경 정의(`specs/environments/<이름>.yaml`, C39)도 같다. 확인 틀을 낼 때 HEAD에서 읽기만 한다.
- v14·v2에서는 이것을 명세 정의의 `inputs`와 계약 레코드의 `file … input` 행(계약을 걸 때의 blob)이 맡았다. v1.1은 U4·U27로 그것을 뺐고, 그 자리를 비워 두었다.

## 2. 규칙(한 문장)

**계약은 자기 검사 재료를 경로로 선언하고, 이행은 provider와 함께 재료의 blob을 기록하며, 규칙 4는 이행 기록의 코드 전부에 그대로 적용된다.**

새 판정은 만들지 않는다. provider에 쓰던 판정(이행 파일 `code`의 항목과 tree X의 항목 비교, `current ?unverified`, `?changed`)을 재료에도 쓴다.

## 3. 바뀌는 자리(명세)

1. **2.3.2 spec 원소**: 키 `fixtures`를 더한다.
   - 값은 경로의 flow list다. 키 순서는 `body engine command success environment <재료>`이고, prompt 원소에도 올 수 있다(v14 2.5.6의 `inputs`와 같은 자리).
   - `specs`는 확인 조건(2.3.3)이므로, 목록을 바꾸면 `condition-id`가 바뀐다. 따로 정할 것이 없다.
2. **계약의 재료**: 모든 spec 원소의 `fixtures`와, 각 원소의 `environment`가 가리키는 환경 정의 파일을 합친 것이다. 환경 정의는 따로 적지 않아도 재료다. 그래서 C39의 구멍이 함께 닫힌다.
3. **3장 값의 꼴**: (U62로 바뀜) 각 원소는 provider처럼 파일 범위나 행 범위이고, 요청이 provider와 같은 tree에서 고정한다. `DIR/`·`/`·`new:`는 받지 않는다.
4. **2.5 이행 파일의 `code`**: provider 범위의 항목에 더해, 재료 경로마다 이행 커밋의 tree 항목(`mode 타입 OID`)을 적는다.
   - provider의 파일 범위와 경로가 같으면 항목은 하나다. 같은 사실이기 때문이다.
   - 이행할 때 그 커밋에 재료가 없으면 어떻게 할지는 7장의 질문 2다.
5. **5.3·5.4 판정**: 5.4의 "K의 provider 범위가 모두 같은 이행"을 "**그 이행 파일의 `code` 항목이 모두 X와 같은 이행**"으로 바꾼다.
   - provider와 재료를 따로 묻지 않고 한 문장이 답한다.
   - 5.5(걸린 계약, `touch`)도 같은 항목 집합으로 본다.
6. **6.3 `status`의 블록**: provider 행처럼 재료 행을 쓰고, 다르면 `?changed`, 없으면 `?missing`·`?deleted`를 쓴다(3.4의 표시 그대로).
7. **7.2 확인 요청 파일**: 과제마다 그 spec 원소의 재료 경로를 싣는다. 확인하는 쪽이 무엇을 근거로 볼지 알게 하려는 것이다.
8. **9장 알림**: 바꾸지 않는다. 재료는 코드 쪽이고, 코드 쪽 변화는 알리지 않는다(C37과 같다).
9. **이력**: 이행 파일의 `commit`(C51)이 열쇠다.
   - `git log <commit>..HEAD -- <재료>`와 `git diff <commit> HEAD -- <재료>`로 무엇이 언제 바뀌었는지 볼 수 있다. `status`가 hint로 그 명령을 줄지는 7장의 질문 3이다.
   - 판정에는 쓰지 않는다. 커밋이 rebase·squash로 사라져도 판정은 `code`의 OID로 선다(U26과 같은 이유).

## 4. 바뀌지 않는 것

- U4: ait 브랜치에는 경로와 OID 문자열만 들어간다. 코드는 들어가지 않는다.
- U27: 작업 폴더와 index에 묶지 않는다. 기록하는 것은 지금처럼 이행이 커밋한 뒤의 HEAD다(6.7).
- 쓰기를 막지 않는다. 재료가 바뀌면 `current ?unverified`로 드러낼 뿐이다(규칙 4의 "막지 않고 드러낸다").

## 5. 코드(예상)

- `contract.c`:
  - spec 원소를 읽고 쓰는 곳에 키 하나를 더한다.
  - 계약의 재료 목록(합집합과 환경 정의)을 함수 하나가 만든다.
  - 판정은 provider 범위를 도는 곳을 `code` 항목을 도는 것으로 바꾼다. 늘지 않고 합쳐지는 쪽이다.
- `request.c`(6.7 이행): `code`를 쓰는 곳이 provider와 재료를 한 목록으로 쓴다.
- `notify.c`(`status` 블록): 재료 행.
- 예상 증감은 +40~60행이다. 줄 상한(3,900)과의 차이는 이미 크므로(7,407행), 같은 판정을 합치는 쪽으로 쓴다.
- 시험(`t/`, 고치기 전 실패·고친 뒤 통과):
  1. 이행 뒤 재료를 바꾸면 `current ?unverified`이고 `?changed`가 보인다.
  2. 환경 정의를 바꿔도 같다.
  3. 재료 목록을 바꾸면 `condition-id`가 바뀐다.
  4. 행 범위·`DIR/`의 재료는 E_SCOPE다.
  5. 이행 커밋을 rebase로 없앤 뒤에도 판정이 같다.
  6. 다른 clone이 그 blob 객체 없이도 같은 판정을 낸다.
  7. provider와 같은 경로의 재료는 항목 하나다.

## 6. pull 문제가 돌아오지 않게 지킬 조건

1. 판정은 OID가 같은가만 본다. 재료의 내용을 읽는 판정을 만들지 않는다. 받는 쪽에 그 객체가 없어도 되게 하려는 것이다.
2. (U62로 바뀜) 행 범위의 fixture는 provider의 행 범위와 같은 대가를 받아들인다: 기준 blob의 내용이 필요하고, 없으면 `?nobase`다. 파일 범위는 OID 비교만 한다.
3. `git log` 이력은 보여 주는 데만 쓴다.

## 7. 정할 것

1. (닫힘: U60) 키 이름은 `fixtures`다. 목록이므로 복수형이고, 원소 하나는 fixture라 부른다.
2. (닫힘: C77, (a)) **이행 커밋에 재료가 없을 때**:
   - (a) 이행을 거절한다(E_SCOPE). 추천. provider가 이행할 때 구체 범위여야 하는 것(3.3)과 같다. 없는 파일은 사실로 적을 수 없다.
   - (b) 없음으로 적고 `?missing`으로 보인다.
3. (닫힘: 주지 않는다) **`status`가 이력 명령을 hint로 줄지**: `git log <commit>..HEAD -- <재료>`는 git 명령이라, hint는 ait 명령만 준다는 규칙과 부딪친다. 그래서 주지 않는 쪽을 추천한다. 사람이 쓸 수 있게 `commit`은 블록에 보인다.
4. (닫힘: 이행 파일의 `commit`이면 충분하다. 사용자 "이거면 충분해") **반대쪽 연결**: 이행 파일은 코드 커밋을 가리킨다(`commit`). 코드 커밋이 ait 쪽 이행 체크인을 가리키게 할지(예: 코드 커밋 메시지에 기록줄)는 사용자의 "풀필에는 상대커밋 id가 저장되어야할듯"이 이것을 말하는지 확인한다.
5. (닫힘: 사용자 "fixtures 구현해") **기능 동결의 예외**: 이것은 기능을 더하는 일이다. 규칙 4가 참이 되게 하는 수리로 볼지 결정한다.

## 8. criminal-decision-draft 옮기기와의 관계

- v2의 `inputs`(정의마다의 경로 목록)는 그대로 `fixtures`가 된다.
- v2의 환경 정의 `input` 행은 2번 규칙으로 저절로 재료가 된다.
- v2 레코드의 `file … input` blob(계약을 걸 때의 지문)을 옮긴 계약의 첫 이행 기록으로 볼지는 옮기기 계획에서 정한다.
