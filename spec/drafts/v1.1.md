# ait v1.1 — 계약을 코드에서 떼어 낸다

2026-10-14 사용자와의 논의를 정리한 초안. 브랜치 `v1.1`(master `89338dc`에서 분기). 이 문서가 v1.1의 결정 목록이다. 명세 본문(`ait-phase1-spec.md`)은 결정이 끝난 뒤 이것에서 다시 쓴다.

## 0. 왜

v14의 복잡함은 한 원인에서 나온다: **계약(`.ait/`)과 명세 파일이 코드와 같은 tree에 있다.** 그래서 모든 git 조작(일반 커밋, merge, rebase, cherry-pick, reset)이 계약을 건드릴 수 있고, ait는 그것을 막거나 수습해야 했다. guard pre-commit, 통합 hook과 되돌리기, merge driver, 판 합치기와 `prev` DAG, 사고 판, 묶음 무결성, 설치 확인(H12), 이력을 실어 나르는 `contract pull`이 모두 이 수습이다.

v1.1은 원인 자리에서 끊는다. **계약은 코드와 이력을 공유하지 않는 ait 브랜치에만 있다.** 코드 브랜치의 git 조작은 원리적으로 계약을 건드릴 수 없으므로, 위 장치는 고칠 것이 아니라 필요가 없어진다.

## 2. 모델

### 2.1 ait 브랜치

- `refs/heads/ait/<name>`. 코드 브랜치와 공통 조상이 없는 orphan 이력이다(gh-pages와 같은 모양). `git checkout ait/<name>`으로 들어가 볼 수 있다. 계약을 바꾸는 것은 ait 명령뿐이다(U16). ait 브랜치끼리 merge하다 난 충돌을 푸는 것은 git의 일이다(U17).
- 안에 있는 것은 두 종류뿐이다(U4).
  ```
  <ID>.yaml              계약
  fulfill/<ID>-<RID>.md  이행 한 번 = 파일 하나 (U6)
  ```
- `ait init`은 원격 추적 `refs/remotes/<remote>/ait/<name>` 중 로컬에 없는 이름마다, 그 이름이 원격 하나에만 있거나 `checkout.defaultRemote`(`git config --get`)가 그 원격을 가리키면 `git branch ait/<name> <remote>/ait/<name>`으로 로컬 브랜치를 만든다(upstream도 git의 DWIM처럼 설정된다. C19. 다시 해도 결과가 같다). 여러 원격에 있고 고를 수 없으면 그 이름은 만들지 않고 `warning: 'ait/<name>' matched multiple (N) remote tracking branches`(`builtin/checkout.c:1321`의 문구. git은 거기서 `die`하지만 init은 다른 이름을 계속 만든다)를 쓴다(C19도 이 문장을 따른다). ait 브랜치 이름의 집합(로컬과 원격 추적)이 비어 있을 때만, 설정된 원격마다 `git ls-remote <remote> 'refs/heads/ait/*'`로 확인한다(U29). 닿지 못한 원격(`ls-remote`가 0이 아닌 코드)은 `warning: cannot reach '<remote>'; skipped`를 쓰고 건너뛴다(U36). 닿은 원격 중 어느 원격에 ait 브랜치가 있으면 만들지 않고 `fatal: '<remote>' has ait branches that are not fetched`와 `hint: fetch 'refs/heads/ait/*' from '<remote>', then 'ait init'`으로 멈춘다(`--single-branch` clone처럼 받아 오지 않은 경우. 새로 만들면 이력이 갈라진다, 9.24). 원격이 없거나 닿은 어느 원격에도 없으면 `ait/<D>`를 orphan으로 만든다. D는 `git var GIT_DEFAULT_BRANCH`로 git에게서 받는다(`builtin/var.c:53`이 `repo_default_branch_name()`, `refs.c:707`을 부른다: `init.defaultBranch`, 없으면 2.53에서 `master`. U11). 첫 커밋의 요약 행은 git처럼 ` (root-commit)`을 붙인다.
- ait 브랜치끼리 주고받고 합치는 일은 git이다: 받기 `git fetch origin ait/<name>:ait/<name>`(fast-forward면 체크아웃 없이 된다), 갈라졌으면 그 브랜치를 체크아웃해 `git merge`, 올리기 `git push origin ait/<name>`(기본 `push.default=simple`은 지금 브랜치만 올리므로 이름을 준다), 이력 `git log ait/<name> -- K.yaml`.

### 2.2 체크아웃·체크인 (U3, U9, U10, U14)

- **ait 브랜치 이름의 집합**: 로컬 `refs/heads/ait/*`와 원격 추적 `refs/remotes/<remote>/ait/*`의 이름(`ait/<name>`)을 합친 것이다. 이것을 세는 함수는 하나다(C29).
  - 로컬 ait 브랜치가 하나도 없는데 원격 추적 것이 있으면(clone 직후) `ait init`이 만들 수 있는 이름이 있을 때 `fatal: no local ait branch`와 `hint: ait init`으로 멈춘다(U19). 만들 수 있는 이름이 없으면(모두 여러 원격에 겹친다) hint를 내지 않는다(틀릴 수 있는 hint는 주지 않는다).
  - 원격에만 있는 이름도 "여럿"을 셀 때는 넣는다. 그래서 clone 뒤에 `git switch`로 하나만 로컬로 만들어져도 그것을 소리 없이 쓰지 않는다(9.8). 체크아웃할 수 있는 것은 로컬 이름뿐이고, 원격에만 있는 이름의 hint는 `ait init`이다.
  - 이름이 하나뿐이면 체크아웃 없이 그것을 쓴다(U9). 여럿인데 체크아웃이 없으면 `fatal: more than one ait branch; none is checked out`와 이름마다 `hint: ait checkout ait/<name>`으로 멈춘다(C8).
- **체크아웃** `ait checkout ait/<name>`: 이 worktree가 상대하는 ait 브랜치(ait의 HEAD)를 `$(git rev-parse --git-path ait-branch)` 파일에 한 행으로 둔다(U30. 경로는 `git rev-parse --path-format=absolute --git-path ait-branch`로 읽는다: 하위 디렉터리에서 그냥 `--git-path`는 상대 경로를 준다. 작업 폴더가 없는 bare 저장소에서는 ait를 쓰지 않는다). git이 worktree마다의 HEAD를 두는 자리와 같은 규칙이라 main은 `.git/ait-branch`, linked는 `.git/worktrees/<id>/ait-branch`이고, `git worktree remove`가 함께 지운다(9.25). 저장소 설정을 바꾸지 않는다. 작업 폴더는 바뀌지 않으므로 끝에 `hint: the work tree stays on '<branch>'; to enter the contract branch: 'ait switch ait/<name>'`을 쓴다(C18, U35. HEAD가 detached면 `'<branch>'` 자리에 `a detached HEAD`). 추적 중인 파일에 커밋하지 않은 변경이 있으면 git이 전환을 거절하므로(9.30) 그때는 앞 절만 쓴다(틀릴 수 있는 hint는 주지 않는다).
- **ait 브랜치에 들어가기** `ait switch ait/<name>`(U35, U37): ait가 정의하는 명령이다(git 통과에 기대지 않는다). `git switch`와 같은 쓰임(HEAD와 작업 폴더를 그 브랜치로)에 계약 쪽 확인만 더한다(C15).
  1. 꼴: 인자가 정확히 `ait/<name>` 하나일 때만 ait가 맡는다. 그 밖(`-`, 코드 브랜치, 옵션)은 `git switch`의 일이므로 그대로 `git switch`에 넘긴다(`ait checkout`의 C30과 같은 규칙).
  2. 먼저 확인한다: 그 이름이 로컬 ait 브랜치가 아니면 넘기지 않는다. 원격에만 있으면 git의 DWIM이 브랜치를 만들기 때문이다: `fatal: no local branch 'ait/<name>'`, `hint: ait init`. 이름의 집합에 아예 없으면 `fatal: no contract branch 'ait/<name>'`. 추적 중인 파일에 커밋하지 않은 변경이 있으면(`git diff --quiet HEAD`) `fatal: uncommitted changes in the work tree; commit them before entering 'ait/<name>'`.
  3. 그다음 `git switch ait/<name>`을 부르고 git의 출력과 종료 코드를 그대로 전한다(그 브랜치를 다른 worktree가 쓰고 있으면 git이 거절한다). 성공하면 `hint: contracts change only through ait commands; to go back: 'ait switch -'`를 쓴다.
  - 들어가 있는 동안 그 ait 브랜치로의 쓰기는 2.2의 거절 4로, fulfill은 거절 5로 막힌다. 들어가는 것은 보거나 merge 충돌을 풀기 위해서다(U16).
- **지금 상대하는 ait 브랜치를 늘 보여 준다(U25)**: 한 worktree의 session들은 체크아웃 하나를 같이 쓰므로, 다른 session이 바꿨을 수 있다. 그래서 `ait status [PATH...]`는 먼저 `On contract branch ait/<name>` 한 행을 쓰고(하나뿐이라 자동으로 고른 것이면 `(the only one)`을 붙인다) 내보낸 뒤, `git status -- PATH...`를 stdout을 물려준 채 돌려 git의 출력을 손대지 않고(색, 지역화 그대로) 그 뒤에 계약 부분을 쓴다. 인자는 PATH만 받는다(옵션을 받으면 porcelain 출력에 ait 행이 섞인다). git이 0이 아닌 코드로 끝나면 그 코드를 돌려준다. 계약을 거르는 PATH는 문자 그대로의 경로다(v14 3.1). 그리고 모든 체크인은 끝에 git commit처럼 `[ait/<name> <짧은 OID>] <요약>` 한 행을 쓴다(`git commit`의 `[master 1a2b3c4] msg`와 같은 모양). fulfill이 엉뚱한 브랜치의 계약을 이행하는 일은 0단계가 막는다: 그 브랜치에 K가 없으면 `fatal: no such contract 'K'`, `rev`가 다르면 거절이다. `rev`가 같으면 확인 조건이 같은 계약(또는 `--force`로 같다고 책임진 계약)이므로 그 브랜치에 기록돼도 틀리지 않다.
- **먼저 거절할 상태**(망가진 상태는 명령 처음에 한 함수로, CLAUDE.md 절차 3). 계약을 읽거나 쓰는 ait 명령(demand·offer·undertake·release·amend·cancel·drop·fulfill·status·sub·listen)이 처음에 이 목록을 위에서부터 보고 처음 걸린 것으로 멈춘다. 명령별 판정은 이것을 지난 뒤에만 한다. 그 상태를 고치는 명령(`ait init`, `ait checkout`, `ait switch`)과 `session`·`unsub`은 이 목록을 지나지 않는다(git에서 고치는 도구만 그 상태에서 도는 것과 같다).
  0. ait 브랜치가 하나도 없음(로컬도 원격 추적도): `fatal: no ait branch`, `hint: ait init`.
  1. 로컬 ait 브랜치가 없고 원격 추적 것만 있음: `fatal: no local ait branch`, 만들 수 있으면 `hint: ait init`(위).
  2. 상대할 ait 브랜치를 정할 수 없음: 여럿인데 체크아웃이 없거나(위), `ait-branch` 파일이 로컬 ait 브랜치가 아닌 이름을 가리킴(`fatal: contract branch 'ait/<name>' does not exist`, 이름마다 `hint: ait checkout ait/<name>`).
  3. 상대하는 ait 브랜치의 계약 YAML·이행 파일이 형식에 맞지 않음(merge 충돌 표시가 커밋된 것 포함): `fatal: bad format: '<path>' at 'ait/<name>'`. 읽기(`ait status`)는 멈추지 않고 같은 줄을 `warning:`으로 쓰고 그 파일을 건너뛴다(git status가 망가진 상태를 보여 주듯이, v14 5.10).
  4. 쓰기 명령: 상대하는 ait 브랜치를 어느 worktree가 쓰고 있으면(HEAD로 체크아웃했거나, 그 브랜치를 rebase·bisect하는 중이거나, rebase의 update-refs 대상이면) 체크인 3의 (a)에서 git이 `fatal: refusing to fetch into branch 'refs/heads/ait/<name>' checked out at '<path>'`로 거절하고, ait는 그것을 그대로 전한다. fulfill은 코드를 커밋하기 전에 알아야 하므로(U8) 0단계에서 같은 (a)를 먼저 돌린다. `update-ref`는 git이 브랜치를 바꿀 때 하는 이 검사를 건너뛰고, 그 worktree의 다음 `git commit`이나 `git rebase --abort`가 체크인을 소리 없이 되돌리기 때문이다(9.9, 9.15). 판정과 문구는 git의 것이다(U24). 그래서 ait 브랜치끼리 `git merge`하는 동안에는 그 브랜치로의 쓰기가 막힌다. 막는 것이 맞다: merge가 끝나지 않은 브랜치에 체크인을 섞지 않는다.
  5. fulfill: 이 worktree의 HEAD가 `ait/*`이면 `fatal: HEAD is on contract branch 'ait/<name>'`(코드 커밋이 ait 브랜치에 들어간다, U4). index에 unmerged 경로가 있으면 git의 `error_resolve_conflict`(`advice.c:201`)와 같은 판정으로 `error: fulfilling is not possible because you have unmerged files`(문구는 CLAUDE.md 출력 규칙대로 소문자로 시작하고 마침표 없이). 읽기(`ait status`)는 unmerged 경로를 HEAD 판으로 읽고 이 둘을 보지 않는다.
- **체크인**: ait 쓰기 명령 하나가 체크인 하나다. 작업 폴더와 코드 브랜치를 건드리지 않는다.
  1. 상대하는 ait 브랜치의 tip T를 읽는다.
  2. 임시 index(`GIT_INDEX_FILE`)에 T를 올리고 이 요청이 바꾸는 파일만 바꾼다. `write-tree`, `commit-tree -p T`.
  3. 두 판정을 나눠 git에게서 받는다. (a) 그 브랜치를 어느 worktree가 쓰고 있는가: `git fetch -q --dry-run --no-write-fetch-head --no-recurse-submodules . NEW:refs/heads/ait/<name>`. 쓰고 있으면 git이 `fatal: refusing to fetch into branch … checked out at …`(exit 128)로 거절하고 ait는 그것을 그대로 전하고 멈춘다(`builtin/fetch.c:1382` `check_not_current_branch` → `branch_checked_out()`. HEAD뿐 아니라 rebase 중인 worktree도 잡는다, 9.22). (b) 갱신은 정확한 CAS인 `update-ref refs/heads/ait/<name> NEW T`. fetch만으로 갱신하면 누가 브랜치를 T의 조상으로 되감은 경우 fast-forward로 받아들여 되감긴 커밋을 되살린다(9.22). ait가 `branch_checked_out()`을 옮기려면 worktree·wt-status·sequencer를 통째로 들여와야 해서 (a)를 git에게 묻는다(CLAUDE.md: 판정은 git에게서 받을 수 있으면 받는다). 남는 틈: (a)와 (b) 사이에 누가 그 브랜치를 체크아웃하는 경합.
  4. 거절되면 새 tip T'를 읽는다(git의 메시지는 지역화되므로 문구가 아니라 tip으로 판정한다). T'가 T와 같으면(lock 파일 등 다른 이유로 실패했다) git의 오류를 그대로 전하고 멈춘다(9.16). T'가 다르고, 이 요청이 **읽고 판정에 쓴 파일과 바꾸는 파일**이 모두 T와 T' 사이에 바뀌지 않았으면 T'에서 2부터 다시 한다. 하나라도 바뀌었으면 멈춘다. 예외는 없다(C3, 9.10). 읽은 파일까지 보는 것은, 예컨대 undertake가 D.yaml(D가 future인가)을 읽고 O.yaml만 바꾸는데 그새 D가 cancel되면 낡은 판정으로 다시 얹게 되기 때문이다(9.17). 같은 계약을 동시에 이행하면 첨부 목록 때문에 뒤의 것이 멈춘다. 그것이 맞다(U17).
- git의 선례: `git notes`(`refs/notes/commits`)와 `git stash`(`refs/stash`)가 작업 폴더를 건드리지 않고 임시 index로 다른 ref에 커밋한다.

### 2.3 계약 YAML

```yaml
rev: r7f3a                     # 확인 조건을 마지막으로 바꾼 요청의 ID: 이행의 유효성 (2.5)
edited: r7f3a                  # 계약 행을 마지막으로 고친 요청의 ID: merge 충돌 (2.5)
kind: demand                   # demand | offer | drop
creator: agent-a
consumer: src/ui/
provider: src/api/page.c:10-40 9a1c…   # 행 범위는 그 행 번호의 기준 blob과 함께 (v14 3.3)
state: future                  # future | cancelled | withdrawn  (drop: future | cancelled)
body: |
  GET /users는 페이지당 50건 이하를 돌려준다
command: make test-api         # 코드 쪽 파일을 부르는 방법일 뿐이다 (U4)
undertakes:                    # offer만: 통째로 떠맡은 demand (2.8a)
undertakes-partially:          # offer만: 부분으로 떠맡은 demand (U40)
target: K3                     # drop만: 철회할 계약 (v14 1.4. drop에는 provider·consumer·body·command가 없다)
fulfilled:                     # 첨부 목록: 더하기만 한다 (U6, U17)
  - user/fulfill/K1-r9b21.md
```

- 레코드와 명세 정의가 하나다. 명세는 ait 명령으로만 바뀌므로(U16) v14의 `file` 고정과 묶음 무결성이 필요 없다.
- **범위**: 파일 `PATH`, 디렉터리 `DIR/`, 전체 `/`, 행 범위 `PATH:S-E BLOB`(U22). 행 범위만 기준 blob을 가진다. 행 번호는 그 blob의 것이고, 다른 판에서는 그 blob에서 사상해 읽는다(v14 3.3·3.7). 기준 blob 없이 지금 파일에 행 번호를 그대로 대면 위에 행이 끼어든 뒤 엉뚱한 행을 보게 된다(9.14).
- **state**는 요청이 정한 것만 저장한다(cancel, 그리고 drop의 이행이 target을 `withdrawn`으로): D·O는 `future`·`cancelled`·`withdrawn`, X는 `future`·`cancelled`. v14의 `current`(확인된 것)는 저장하지 않고 브랜치의 tree마다 계산한다(2.6). 그래서 같은 계약이 `ait/master`에서는 current, `ait/try`에서는 future로 보일 수 있다(U9).

### 2.3a 그룹 폴더와 작업 폴더의 `.ait/` (U43, U44, U45)

- ait 브랜치는 그룹 폴더를 가질 수 있다: `<group>/<ID>.yaml`, 이행 파일은 계약과 같은 그룹의 `<group>/fulfill/<ID>-<RID>.md`(그룹이 없으면 뿌리의 `<ID>.yaml`과 `fulfill/`). 그룹은 경로 조각 하나 이상(`user/`, `server/api/`)이고 `fulfill`이라는 조각은 쓸 수 없다. 계약 ID는 폴더를 넘어 유일하고, 명령은 ID만 받는다. ait가 ait 브랜치에서 그 ID의 파일을 찾는다. 같은 ID가 두 곳에 있으면 형식 오류다(2.2의 거절 3).
- 작업 폴더의 `.ait/`는 ait 브랜치와 같은 모양의 초안 자리다(커밋되지 않는다, Q21): `ait contract new demand|offer|drop [<group>]`이 `.ait/<group>/<새 ID>.yaml`에 틀을 쓰고, 에이전트가 spec까지 그 파일 하나에 채우고, `ait contract add <path>…` → `ait contract commit -m <msg>`가 여러 계약을 커밋(체크인) 하나로 올린다. 위치는 `.ait/` 아래 경로 그대로다. 관문은 도우미 명령과 같은 검사(형식, 전이, 기대는 짝 U41, 섞지 않음 U40)다.
- 도우미 명령(`ait future demand …` 등)은 조건 파일을 인자로 받아 그 내용을 계약 YAML에 담는다. 틀은 `ait contract new spec PATH exec|prompt`가 쓰고(v14 7.4.1a), 그룹은 옵션 `-g <group>`이다.
- spec은 계약 YAML 안에 있다(U45). 그래서 spec을 바꾸는 것은 그 계약의 확인 조건을 바꾸는 것이고 `rev`를 바꾼다(2.5).
- **이행 파일은 `ait fulfill`만 쓴다.** 직접 작성 입구로는 `fulfill/` 아래 파일을 넣거나 `fulfilled:` 목록을 고칠 수 없다(`error: fulfilments are recorded only by 'ait fulfill'`). 이행으로 세는 것은 그 계약의 `fulfilled:`에 있고, 앞머리의 `contract:`가 그 계약이며, `rev`가 맞는 것뿐이다(2.6). 목록에 없이 놓인 이행 파일은 세지 않고, 목록에 있는데 `contract:`가 다르면 형식 오류다.

### 2.4 이행 파일 (U5, U6)

```markdown
---
contract: K1
rev: r7f3a                       # 이행한 계약의 rev
by: agent-b                      # session (U20)
command: make test-api
outcome: pass                    # pass | forced
code:                            # 계약의 provider 범위마다, 이행한 커밋(HEAD)의 코드
  src/api/page.c:10-40 9a1c…: 100644 blob 77b2… 12-42
---
12 passed. 페이지 크기 경계(49/50/51)를 확인함.
```

- `code`의 키는 계약의 provider 범위 문자열 그대로다. 값은 그 범위의 tree 항목 `mode 타입 OID`이고, 행 범위면 그 blob에서 확인한 행 `s-e`를 덧붙인다. "확인한 것은 이 blob의 s–e행"은 이행할 때의 사실이다(규칙 1). 계산으로 대신하지 않는 것은, 계산에 쓰는 계약의 기준 blob이 지워질 수 있기 때문이다: ait 브랜치는 그 blob을 OID 글자로만 가리켜 git이 지켜 주지 않는다(9.21). 모양은 git 패치의 머리(`index` 행의 blob + `@@` 행의 숫자)와 같다. 범위 `/`는 tree 자체(`<tree>^{tree}`, 9.12), 경로가 없으면 그 범위로는 이행할 수 없다(2.8의 0). gitlink는 `160000 commit OID`, symlink는 링크 문자열의 blob으로 똑같이 비교한다(git이 보는 것). mode를 넣는 것은 `chmod +x`나 symlink 전환이 blob OID를 바꾸지 않기 때문이다(9.12).
- git에서 따온 것과 ait가 정한 것(U26): 항목 `(mode, blob OID)`는 git index의 한 행(`git ls-files -s`)이고, 파일 전체가 바뀌었는지는 git도 이 OID로 판정한다(`diff-lib.c:409`, `diff.c:3720`). 파일 일부(행 범위)가 바뀌었는지 계산하는 것은 git의 `git log -L`과 같다: blob 둘을 diff해 행 범위가 닿았는지 숫자로 본다(`line-log.c:1032` `process_diff_filepair`, `:458` `range_set_map_across_diff`). 다만 `log -L`은 범위를 명령이 도는 동안만 들고 있고, "blob + 행 번호"를 적어 두었다가 나중에 다시 판정하는 형식은 git에 없다. 그 형식(`PATH:S-E BLOB`, 이행 파일의 `blob s-e`)은 ait가 정한 것이고 v14 3.3을 이었다. 모양은 패치 머리(`index <old>..<new>`와 `@@` 숫자)를 닮았다. `git apply`는 그 blob과 지금 파일을 OID로 맞춰 보고(`apply.c:3213`), `--3way`는 그 blob을 꺼내 바탕으로 쓰며 없으면 `repository lacks the necessary blob to perform 3-way merge.`로 멈춘다(`apply.c:3664`). 기준 blob이 없으면 판정할 수 없다는 2.6의 한계도 같다.
- 커밋 OID가 아니라 범위의 항목으로 가리키므로 rebase·squash·cherry-pick 뒤에도 유효하다. 디렉터리는 tree OID 하나라 그 아래 새 파일도 바뀐 것으로 잡힌다(9.7).
- 한 번 쓰면 고치지 않는다. ait는 이를 검사하지 않는다. 고쳤는지 알려면 ait 브랜치의 이력을 걸어야 하는데, squash·rebase로 이력이 사라지면 판정이 갈린다. ait는 데이터로 판정하고 git 조작을 쫓지 않는다(C9).

### 2.5 `rev`와 `edited`

- 용어: **확인 조건**은 이행이 확인하는 행 `provider`·`body`·`command`·`undertakes`·`undertakes-partially`다. **계약 행**은 확인 조건에 `consumer`를 더한 것이다(`kind`·`creator`는 바뀌지 않는다). `state`와 `fulfilled`는 둘 다 아니다.
- `rev`는 계약을 만들거나 확인 조건을 바꾸는 요청(`--force` amend는 빼고)이 그 요청 ID로 바꾼다. `consumer`만 바꾸면 `rev`를 둔다(v14 2.3: consumer만 바꾸면 결과가 필요 없다). 이행(첨부 한 줄 더하기), state 변경(cancel, withdraw), `--force` amend는 바꾸지 않는다(C4, C25). state는 이행을 무효로 만들지 않는다: cancelled·withdrawn인 계약은 판정 대상이 아니기 때문이다.
- `edited`는 계약 행을 고치는 모든 요청(`--force` amend 포함)이 그 요청 ID로 바꾼다. 이행과 state 변경은 바꾸지 않는다. `rev`는 이행의 유효성을, `edited`는 merge 충돌을 맡는다(C31).
- 같은 계약의 계약 행을 두 ait 브랜치에서 고치면 git merge가 반드시 충돌해야 한다. 숫자로 올리는 값은 양쪽이 같은 값이 되면 충돌이 사라진다(9.3). 고유한 요청 ID면 반드시 충돌한다. `rev`만으로는 `--force` amend(rev를 두는)와 다른 쪽의 amend가 충돌 없이 합쳐져 누구도 쓰지 않은 조건이 된다(9.18). `edited`가 그 경우를 충돌로 만든다. 이행(첨부 한 줄)은 `edited`를 건드리지 않으므로 계약 행 변경과 깨끗이 합쳐지고, 옛 이행은 `rev`로 걸러진다. state 변경(cancel 등)과 계약 행 변경은 행이 붙어 있지 않으면 합쳐진다("cancelled인데 계약 행은 새것"). 끝난 계약은 판정하지 않으므로 해가 없어 둔다(3차 검수 재현: 계약 행끼리, 이행끼리는 모두 충돌, 계약 행 대 이행은 깨끗).

### 2.6 판정 (계산, 저장 안 함)

판정의 tree X는 읽는 명령(`ait status`)에서는 index의 tree다(v14 7.8.1과 같다: 커밋하기 전의 변경이 이행된 계약을 건드리면 미리 보인다). index에 unmerged 경로가 있으면 그 경로는 HEAD 판으로 읽고 경로마다 `warning: 'P' is unmerged; it is read as HEAD has it`를 쓴다(v14 결정 45). X를 만드는 함수는 하나다. fulfill은 커밋한 뒤의 HEAD를 기록한다(2.8). (unmerged index에서 `git write-tree`는 실패하므로 그 경로를 HEAD 판으로 바꾼 임시 index에서 만든다.)

계약 K(저장된 state가 `future`인 D·O)에 대해. 아래의 current·future는 **판정**이고 저장된 state `future`와 다르다(판정 current인 계약도 저장된 state는 `future`다):
1. **유효한 이행**: 첨부 목록의 이행 파일 중 `rev`가 K의 `rev`와 같은 것. 다른 `rev`의 이행은 옛 조건의 것이라 세지 않는다(U21). 이 비교 하나가 조건 변경도, ait 브랜치끼리의 merge(9.6)도 거른다. ait 명령만 썼다면 `rev`가 같을 때 provider도 같다(2.7).
2. **범위가 같은가**(범위 하나, 이행 파일 하나): `code`에 그 범위 키가 없으면 다르다(손으로 푼 merge가 한쪽의 `rev`와 다른 쪽의 `provider`를 남길 수 있다, U17). 파일·디렉터리·`/`는 X의 항목이 `code`의 항목과 같으면 같다. 행 범위는 `code`의 blob이 이 저장소에 없으면 다르다(v14 3.11. ait 브랜치는 그 blob을 글자로만 가리키므로 지켜 주지 않는다: 올리지 않은 코드 커밋의 blob이면 clone마다 판정이 다를 수 있다, 9.19). 있으면 `code`의 blob 좌표에서 판정한다: `diff0 <code의 blob> <X의 blob>`(v14 3.6의 옵션, 커밋 없이 blob 둘로 된다)의 어떤 hunk의 접촉 구간이 `code`의 s-e와 겹치면 다르다(v14 3.10·3.11). mode가 다르거나 파일이 없으면 다르다. 사상(v14 3.7)은 결과 틀에서 계약의 `S-E BLOB`을 지금 blob의 s-e로 옮길 때와 지금 위치를 보여 줄 때 쓰고, "이행한 뒤 바뀌었는가"는 사상하지 않고 이행한 blob 좌표의 접촉으로 본다(9.13).
3. **결과**(정의는 여기 하나): 유효한 이행 중 K의 provider 범위가 **모두** 같은 이행이 하나라도 있고, K가 offer면 K가 통째로 떠맡은 살아 있는 D가 모두, K가 demand면 K를 부분으로 떠맡은 살아 있는 O가 모두 판정 current이면(2.8a) K는 **current**다. 유효한 이행은 있는데 그런 것이 없으면 **current ?unverified**(이행 뒤 바뀜, v14의 미확인)다. 유효한 이행이 없으면 **future**다. 범위마다 다른 이행을 섞어 current를 만들지 않는다.

- 접촉 구간은 v14 3.10대로 순수 삽입도 `[os, os+1]`로 잡아 범위에 맞닿은 삽입을 바뀐 것으로 본다. git의 `git log -L`은 맞닿은 삽입을 범위의 변경으로 보지 않는다(검수 2차 재현). ait는 git보다 넓게 알린다.
- 이 판정은 ait 브랜치마다 다르다. 같은 코드가 체크아웃한 ait 브랜치에 따라 current이기도 future이기도 하다. 이것이 요구사항을 시험한다는 뜻이다(U9).

### 2.7 amend와 `--force` (U7, U21)

- `ait amend K …`: 조건을 바꾸고 `rev`를 이 요청 ID로 바꾼다. 옛 이행은 첨부 목록과 `fulfill/`에 남지만 `rev`가 달라 세지 않는다.
- `ait amend K … --force -m <why>`: `body`·`command`를 바꾸되 `rev`를 그대로 둔다(`consumer`는 `--force` 없이도 `rev`를 두고 바꾼다, 2.5). "같은 조건이다(사소하다)"는 판단이고, 그래서 옛 이행이 계속 센다. 판단은 그 체크인 커밋의 메시지와 session으로 남는다.
  - **`--force`로는 provider를 바꿀 수 없다**: `error: cannot change the provider of 'K' with --force`(exit 1). 이유는 `hint: --force keeps the old fulfilments, which checked the old provider`. 이행은 provider의 코드를 확인한 것이므로, provider가 바뀌면 옛 이행이 새 provider를 덮는다고 말할 수 없다. 이 규칙 하나로 "유효한 이행이 지금 provider를 다 덮는가"라는 두 번째 판정이 필요 없어진다(C23).
- `ait fulfill K --force -m <why>`: 결과 없이 2.8의 0–3을 그대로 지난다. 덮는 계약 집합은 2.8a로 계산하고(offer면 살아 있는 떠맡은 D들도 `forced` 기록을 받는다), `rev`는 T의 것을 쓴다. `-m <why>`는 코드 커밋과 체크인 커밋의 메시지이고, 그것이 "사소하다"는 판단의 기록이다. v14의 `check forced`와 같은 뜻이다.

### 2.8 fulfill 순서 (U8)

확인은 에이전트가 자기 worktree에서 알아서 하고, ait는 결과가 참인지, 어느 작업 폴더에서 돌았는지 보지 않는다(U27, v14 0.4a). fulfill은 결과 파일을 받아 **관련 파일(stage한 코드)의 커밋과 이행 기록의 체크인을 함께** 한다(U31, U32). 한 커밋이 될 수는 없다: 코드와 이행 기록은 서로 다른 브랜치에 있고 커밋 하나는 tree 하나다(Q15). 기록하는 것은 "이 결과는 이 계약의 이 판을, 이 커밋의 코드로 이행했다"이고, 그 기록이 있어야 나중에 코드가 바뀌었는지(2.6)를 판정할 수 있다.

결과 틀: `ait fulfill K`(결과 없이)는 결과 틀을 낸다. 틀에는 이 이행이 덮는 계약(K와, K가 offer면 살아 있는 떠맡은 D들, 2.8a)마다의 `rev`와 확인할 과제가 적힌다. 과제에는 행 범위가 지금 몇 행인지(기준 blob에서 index로 사상한 s-e)를 보여 준다. 에이전트는 확인하고, 관련 파일을 stage하고, 결과를 채워 `ait fulfill K -r <result> -m <msg>`로 낸다.

**위치 판정(한 함수)**: provider 범위마다 index에서 찾는다. 경로가 없으면 `?missing`, 행 범위의 사상이 `?deleted`면 이행할 수 없다. 계약의 기준 blob이 이 저장소에 없으면 git의 `apply --3way`처럼 `fatal: repository lacks the base blob of 'K' ('<path>')`와 `hint: ait amend K <provider>`로 멈춘다(provider를 지금 판에서 다시 지정하면 새 기준 blob이 생긴다, 9.21). 결과 틀, 0단계, `--force` 이행이 모두 이 함수를 부른다.

0. **먼저 판정한다**(아무것도 바꾸지 않는다). 2.2의 먼저 거절할 상태(쓰고 있는 브랜치 판정인 체크인 3의 (a)는 아직 새 커밋이 없으므로 지금 tip T로 묻는다: `git fetch --dry-run . T:refs/heads/ait/<name>`, 9.28), 결과가 덮는 계약 집합이 2.8a로 지금 계산한 집합과 같고 그 계약마다 T에서 state `future`이며 `rev`가 결과와 같은가, 위치 판정, 결과 형식. 하나라도 틀리면 멈춘다. 체크인이 질 수 있는 판정을 커밋 전에 모두 한다(U8).
1. **관련 파일을 커밋한다.** `git commit -m <msg>`(hook·서명은 git의 것). stage한 것이 없으면(git commit과 같은 판정인 `git diff --cached --quiet`. intent-to-add 항목은 git commit처럼 없는 것으로 본다, `builtin/commit.c:1062`, 9.28) 커밋하지 않고 지금 HEAD를 기록한다(U33). 그때는 `warning: nothing to commit; recording the code at HEAD ('<short OID>') for <덮는 계약 ID들>`을 쓰고 계속한다. `-m <msg>`는 체크인 커밋의 메시지로만 쓴다. **커밋이 되지 않으면 이행할 수 없다(U32)**: git의 오류(hook 거절, 서명 실패, `index.lock`, 이름 미설정 등)를 그대로 보여 준 뒤 `error: commit failed; 'K' is not fulfilled`(exit 1)로 멈춘다. 아무것도 기록되지 않았고, 원인을 고친 뒤 다시 하면 된다.
2. **체크인한다.** 덮는 계약마다 커밋 뒤의 HEAD에서 위치 판정을 다시 하고(hook이 커밋 중에 범위를 지웠을 수 있다, 9.28) `code`를 계산해(provider 범위마다 HEAD의 항목, 행 범위면 사상한 s-e) 이행 파일을 쓰고, 각자의 첨부 목록에 한 줄을 더해 T 위에 체크인한다(2.2). 이 체크인이 읽은 파일은 덮는 계약의 YAML과 그것들을 판정하는 데 읽은 모든 YAML이고, 바꾸는 파일은 그 YAML들과 새 이행 파일이다(2.2의 4). 체크인 커밋의 메시지는 `-m <msg>`다.
3. **2가 실패하면**(HEAD에서의 위치 판정, 체크인 3의 (a) 거절, CAS에서 2.2의 4가 멈춤, T'=T인 실패 모두) 기록은 없다. 1에서 커밋을 만들었으면 `error: committed '<short OID>' but <덮는 계약 ID들> not fulfilled: <이유>`, 만들지 않았으면 `error: <덮는 계약 ID들> not fulfilled: <이유>`를 쓴다(exit 1). 남는 것은 기록 없는 코드 커밋, 즉 판정 future이고 틀린 기록이 아니다. hint는 CAS에서 졌고(T'≠T) 덮는 계약이 모두 그대로일 때만 `hint: ait fulfill K -r <result> -m <msg>`를 쓴다. 다시 하면 그때 stage한 것을 커밋하고 그때의 HEAD를 기록한다. lock·(a)·위치 때문이면 같은 명령이 다시 실패하므로, 계약이 바뀌었으면 다시 확인해야 하므로 hint를 내지 않는다.

- 기록하는 코드는 1의 커밋 뒤 HEAD다. hook이 파일을 고쳐 커밋했으면 고친 것이, hook이 stage를 비워 빈 커밋이 됐으면(git은 hook 전의 index로 커밋할 것이 있는지 정한다, 9.28) 예전 코드가 기록된다. 어느 쪽이든 HEAD의 사실이고, ait는 확인한 코드와 묶지 않는다(U27). 커밋한 뒤에 바뀐 것은 2.6이 "이행 뒤 바뀜"으로 알린다.
- (A)(두 브랜치를 한 ref 트랜잭션으로, 9.27)를 쓰지 않는 것은 `git commit`을 거치지 않으면 사용자의 hook·서명이 돌지 않기 때문이다. git의 커밋을 ait가 다시 만들지 않는다.

git의 선례: 로컬 커밋 뒤 `git push`가 거절되면 커밋은 남기고 이유와 다음 일을 알린다(`builtin/push.c` `reject_reasons`).

### 2.8a undertake (U18, U40)

떠맡기는 두 가지다. 문법은 v14 7.3의 `undertake K K`(D O)에 옵션을 더한다: `undertake [-p|--partial] D O`(U42), `release D O`.

- **통째 떠맡기**(v14 1.6 그대로): "O가 D를 포함한다". O를 이행하면 D도 같은 fulfill에서 함께 이행되고, O가 판정 current이려면 D도 current여야 한다(v14 규칙 5). 한 D를 여러 O가 통째로 떠맡을 수 있다.
- **부분 떠맡기**(U40): "O가 D의 일부를 맡는다". D가 O에 포함된다는 전제가 없다(예: D "이러저러한 화면을 만들어라"를 여러 O가 나눠 맡는다). O를 이행해도 D는 이행되지 않고, O의 판정은 D와 상관없다. D는 D를 이행할 때 닫힌다. D를 이행하려면 D를 부분으로 떠맡은 살아 있는 O가 모두 판정 current여야 한다. 아직 current가 아닌 것은 그 D의 fulfill에서 함께 이행할 수 있다(덮는 계약 집합에 든다, 아래).
- **섞지 않는다**(U40, 대칭): 한 D에 살아 있는 떠맡기는 모두 통째이거나 모두 부분이다. 부분 떠맡기가 있는 D를 통째로 떠맡거나, 통째 떠맡기가 있는 D를 부분으로 떠맡으면 `error: 'D' is already undertaken partially by 'O1'`(또는 `wholly`)로 거절한다(exit 1). 같은 요청에서 상대 쪽 떠맡기를 모두 release하면 허용한다(요청은 한 체크인이므로 판정은 요청이 끝난 뒤의 상태로 한다).
- **YAML**: offer O의 `undertakes:`는 통째로 떠맡은 D의 ID 목록, `undertakes-partially:`는 부분으로 떠맡은 D의 ID 목록이다. 떠맡기·놓기는 O의 이 목록을 바꾸는 요청이고 O의 확인 조건이 바뀐 것이므로 O의 `rev`를 바꾼다(2.5). 섞지 않는다는 판정은 D를 떠맡은 모든 O의 목록을 읽으므로, 체크인이 읽은 파일에 그 O들이 든다(2.2의 4).
- **살아 있는 떠맡기**(정의는 여기 하나): 목록의 D 중 그 브랜치에서 저장된 state가 `future`인 D와, 그 D를 떠맡은 O 중 저장된 state가 `future`인 것. 아닌 항목(merge로 cancel된 D를 가리키게 됐을 수 있다)은 없는 것으로 본다. 저장된 목록을 믿지 않고 판정 때 계산한다(9.17). drop의 target도 같다.
- **판정**(2.6의 3이 정한다): O가 current이려면 통째로 떠맡은 살아 있는 D가 모두 current여야 한다. D가 current이려면 D를 부분으로 떠맡은 살아 있는 O가 모두 current여야 한다.
- **기대는 짝은 함께 고친다**(U41, v14 1.6·5.9 d. 정의는 여기 하나): 기대는 짝은 (통째로 떠맡은 O → D)와 (부분으로 떠맡긴 D → O)다(화살표 쪽에 기댄다). 요청이 계약 X의 `rev`를 바꾸거나(amend, 떠맡기 목록 변경) X에 새 기대를 만들 때(D를 부분으로 떠맡게 하는 undertake), X에 기대는 살아 있는 계약 Y 중 유효한 이행(2.6의 1: `rev`가 맞는 이행 기록)이 있는 것이 있으면 거절한다. 같은 요청에서 Y의 `rev`도 바꾸면(Y를 amend하거나, 바꿀 것이 없으면 빈 amend `amend Y`로 다시 연다) 허용한다. 판정은 이 worktree의 코드가 아니라 상대하는 ait 브랜치의 데이터로 한다(ait 브랜치마다 같은 답).
  - 거절: `error: changing 'X' would reopen 'Y', which depends on it`(exit 1), `hint: ait amend X <…> amend Y`(그 요청의 절에 Y의 빈 amend를 더한 명령. 사람이 정할 인자는 `<…>`).
  - cancel·withdraw는 이 규칙에 걸리지 않는다: 끝난 계약은 기대는 대상에서 빠질 뿐 다른 계약을 current에서 빼지 않는다(살아 있는 떠맡기, 위).
  - 빈 amend `amend K`(인자 없음)는 K의 `rev`를 새 요청 ID로 바꾼다. 그래서 K의 옛 이행이 세지 않게 된다(v14 6.5의 빈 amend, 되돌리기 1.5d).
- **덮는 계약 집합**(fulfill이 함께 이행하는 계약, 정의는 여기 하나): K가 offer면 K와 K가 통째로 떠맡은 살아 있는 D들. K가 demand면 K와 K를 부분으로 떠맡은 살아 있는 O 중 아직 current가 아닌 것들. 결과 틀에는 그 계약마다 `rev`와 과제가 들어가고, 2.8의 2에서 각자의 `rev`와 `code`로 이행 파일을 쓰고 각자의 첨부 목록에 더한다. 체크인이 바꾸는 파일에는 그 계약들의 YAML이 모두 들어가므로, 그새 바뀌었으면 2.2의 4로 멈춘다.

### 2.9 hook

강제가 없어지므로 hook은 선택이다. 없어도 맞게 동작한다.
- 구독 알림: ait 브랜치 ref가 바뀔 때 `git diff-tree -r --name-only OLD NEW`로 바뀐 계약을 안다. 로컬 `reference-transaction`, 서버 `post-receive`.
- 코드 쪽 경고(원하면): post-commit에서 "이행된 K의 provider 경로를 바꿨다".

### 2.10 구독과 알림 (U2, U28)

v14의 `sub`·`unsub`·`listen`(7.2.4–7.2.5), session 파일과 잠금(4.2–4.6), 전달 절차(9.5)를 쓴다. v14 9.5를 ait 브랜치의 ref로 좁힌 것이 v1.1의 알림이다.

- **체크인 커밋의 기록줄**: 모든 체크인 커밋 메시지는 첫 행이 요약(`<명령> <ID들>`, 2.2의 `[ait/<name> <OID>] <요약>`의 요약)이고, 끝에 v14 5.4의 기록줄 `Ait-Request: RID`, `Ait-Agent: NAME`, `Ait-Session: SID`를 붙인다. RID는 v14처럼 만든다. 그래서 알림은 보낸 session을 기록줄로 안다(v14 9.5-3: 자기 자신이 보낸 사건은 건너뛴다). ait가 만들지 않은 커밋(git merge 등)은 기록줄이 없고 보낸 session이 없다.
- **tip**: session 파일의 `tip OID REFNAME` 행들은 `refs/heads/ait/*`와 `refs/remotes/*/ait/*` 전체의 스냅샷이다(v14 4.2의 tip을 ait ref로 좁힘). `session open`과 차례마다 갱신한다.
- **후보**: `git rev-list --reverse --topo-order --ignore-missing --stdin`에 감시하는 ref의 OID들과 tip의 OID마다 `^OID`를 넣는다(v14 9.5-2). 감시하는 ref는 session의 worktree가 상대하는 로컬 ait 브랜치와 그 upstream이다. upstream은 `git rev-parse -q --verify --symbolic-full-name ait/<name>@{upstream}`이 `refs/remotes/*/ait/*`를 줄 때만 쓴다(없거나 사라졌으면 조용히 exit 1, 코드 브랜치를 upstream으로 둔 것은 쓰지 않는다). tip이 모든 ait ref의 스냅샷이므로, 다른 session이 `ait checkout`으로 브랜치를 바꿔도 새 브랜치의 이미 알려진 커밋은 다시 나오지 않는다. 되감기나 force push로 사라진 커밋은 알리지 않는다(v14 규칙 2: 그 브랜치가 옛 상태일 뿐이다).
- **받는 상태**: v14 9.5의 받는 상태 V에 `ait-branch` 파일의 내용을 더한다. 내보내기 전에 V가 바뀌었으면 그 차례를 멈춘다(v14 9.5-3).
- **사건과 키**: 후보 커밋 C가 첫 부모와 비교해 바꾼 계약 파일이다(`git diff-tree -r --root --name-only --diff-merges=first-parent C`, 9.29). 키는 v14 9.5-3처럼 내용으로 잡는다: 바뀐 계약마다 `version ID BLOB`(C에서 그 `<ID>.yaml`의 blob), 이행 파일마다 `fulfil ID BLOB`. 그래서 merge·rebase로 생긴 사본은 같은 키라 한 번만 나간다(4차 검수 재현).
- **받는 쪽**(v14 9.3을 계약 YAML로. 관계는 받는 session이 상대하는 로컬 ait 브랜치의 tip에서, 사건은 C와 그 첫 부모 양쪽의 판에서 본다):
  - 내 약속: 저장된 state가 `future`인 K의 creator가 그 agent → `reason future ROLE K`. K가 그 agent의 future offer가 떠맡은 D이거나, 그 agent의 future D를 떠맡은 O이면 → `reason future ROLE(M) M`. release는 C에서는 관계가 없으므로 첫 부모의 판으로도 본다.
  - 내 요구: K가 그 agent가 만든 demand이고 판정 current다 → `reason demand K`.
  - 내 구독: `sub id K` → `reason sub id K`. `sub scope Q`가 C나 첫 부모의 판에서 K의 consumer·provider와 기대는 겹침(v14 3.9a)이면 → `reason sub scope DISPLAY(Q)`.
  - drop X가 바뀌면 그 target도 바뀐 계약으로 센다(v14 9.2-4).
  - 버려진 내 변경(v14의 `reason overridden`): Q17.
- **seen과 전달**: v14 9.5·9.6 그대로(at-least-once).
- **payload**(v14 9.7을 고침): `ait-event 1`, `commit OID`(사건 커밋), `recipient SID`, `ref REFNAME`, `reason …` 행들, `in-head yes|no`(키가 모두 받는 session이 상대하는 로컬 ait 브랜치의 tip에 있으면 yes), `contract ID ACTION` 행(ACTION은 그 계약의 YAML이 C에서 바뀐 모양: `rev`가 바뀌면 `amend`, `edited`만이면 `edit`, state가 바뀌면 그 state, 새 파일이면 `create`, 첨부가 늘면 `fulfil`), 빈 행, `git show --no-color --no-ext-diff --no-textconv --no-show-signature --diff-merges=first-parent --format=fuller --stat --patch C`. `unverified` 행과 `hint:` 행은 없다(코드 쪽 판정은 `ait status`의 일, C37. 들이기 hint는 git 명령이라 쓰지 않는다).
- `sub scope PATH:S-E`의 기준 blob은 그 session의 worktree의 index에서 고정한다(v14 7.2.4). 기준 blob이 없으면(9.21) 그 구독은 파일 전체로 본다(v14 3.9의 사상하지 못한 range). `sub id`는 상대하는 로컬 ait 브랜치에 그 계약이 있어야 한다.
- `listen --fetch SEC`은 `git fetch --all` 대신 원격마다 `git fetch <remote> 'refs/heads/ait/*:refs/remotes/<remote>/ait/*'`를 한다.
- 코드 쪽의 "이행 뒤 바뀜"(2.6)은 사건으로 보내지 않는다(C37). hook(2.9)은 `listen`을 대신하지 않는다.

### 3.1 명령의 집합 (U38)

ait가 받는 하위 명령은(약어는 없다, U39) `init`, `checkout`, `switch`, `status`, `demand`, `offer`, `undertake`, `release`, `amend`, `cancel`, `drop`, `fulfill`, `sub`, `unsub`, `listen`, `session`뿐이다. 그 밖의 하위 명령은 git에 넘기지 않고 사용법 오류로 멈춘다: `error: '<cmd>' is not an ait command`, 이어서 사용법, exit 129(CLAUDE.md: 사용법 오류는 `error:` 다음 `usage:`로 129). 인자가 없으면 사용법을 쓰고 exit 129.
- git과 같은 이름(`init`, `checkout`, `switch`, `status`)은 git의 그 명령과 같은 쓰임이고(C15), ait가 맡는 꼴이 아닌 인자는 그 git 명령에 넘긴다. 이것은 일반 통과가 아니라 그 명령의 정의다: 어떤 꼴을 ait가 맡고 어떤 꼴을 git에 넘기는지가 명령마다 정해져 있다(2.2, 2.10).
- hint에는 이 집합의 명령과 마치는 git 커밋만 쓴다(CLAUDE.md 출력 규칙).

## 9. git 전제 재현 (git 2.53.0)

### 9.1 작업 폴더를 건드리지 않고 다른 브랜치에 커밋 (C2)
```
echo "dirty" >> a.c
export GIT_INDEX_FILE=$S/idx
B=$(printf 'kind: demand\n…' | git hash-object -w --stdin)
git update-index --add --cacheinfo 100644,$B,K1.yaml
T=$(git write-tree); C=$(git commit-tree $T -m "demand K1")
git update-ref refs/heads/ait/main $C ""     → create ok
git status --short                            →  M a.c   (그대로)
```

### 9.2 CAS (C2)
```
git update-ref refs/heads/ait/main $C3 $C
→ fatal: … cannot lock ref 'refs/heads/ait/main': is at b38e90f… but expected 9af12c1…  (exit 128)
```

### 9.3 `rev` 숫자는 충돌을 숨긴다 (C4)
base `rev: 7, provider: a.c`. ait/master: `rev: 8, provider: a.c,b.c`. ait/try: `rev: 8, provider: a.c, fulfilled: - f/K1-r1.md`.
```
git merge-tree --write-tree --name-only ait/master ait/try   → exit 0
결과: rev: 8 / provider: a.c,b.c / fulfilled: - f/K1-r1.md
```
`rev: rA` / `rev: rB`로 같은 경우:
```
→ 충돌 (내용): K1.yaml에 병합 충돌   exit 1
```

### 9.4 `extensions.worktreeConfig` (없앤 C11의 근거)
```
git config --worktree ait.branch ait/main   → exit 0
git config --local --get ait.branch         → ait/main   (저장소 설정에 씀)
git config extensions.worktreeConfig true
git config --worktree ait.branch ait/x      → .git/config.worktree 에 씀
```

### 9.5 이름과 이력
```
git branch ait          → fatal: cannot lock ref 'refs/heads/ait': 'refs/heads/ait/main' exists
git merge-base main ait/main   → exit 1 (공통 조상 없음)
```
`ait`라는 코드 브랜치가 있으면 ait 브랜치를 만들 수 없다. `ait init`은 그때 git의 오류를 그대로 전한다.

### 9.6 첨부 목록 비우기는 merge에서 뚫린다 (C10)
base `rev: r0, provider: a.c, fulfilled:`(빈 목록). ait/master: amend로 `rev: rA, provider: a.c,b.c`, 목록 비움(바뀐 행 없음). ait/try: 옛 조건으로 이행, `rev: r0` 그대로, `- fulfill/K1-r1.md` 더함.
```
git merge-tree --write-tree ait/master ait/try   → exit 0
rev: rA / provider: a.c,b.c / fulfilled: - fulfill/K1-r1.md
```
옛 조건의 이행이 새 조건 아래 첨부로 남는다. 이행 파일의 `rev: r0` ≠ `rA`로만 걸러진다. (base 목록이 비어 있지 않으면 같은 경우가 충돌한다: exit 1.)

### 9.7 디렉터리 범위의 tree OID (C7)

echo b > src/api/new.c; git add .; git commit -qm 2
git rev-parse HEAD:src/api   → 5343a5e…   (새 파일로 바뀜)
git ls-tree $(git write-tree) src/api   → 040000 tree 5343a5e…   (index의 tree에서도 같은 값)
```

### 9.8 clone 뒤의 ait 브랜치 수 (C29)

### 9.9 체크아웃된 ait 브랜치에 update-ref하면 다음 커밋이 되돌린다 (C16)
```
git worktree add -q $S/w ait/master; echo n > $S/w/note.txt; git -C $S/w add note.txt
ckin.sh ait/master $O K1.yaml 'rev: rB\nprovider: a.c,b.c\n'   → checkin ok

```
`ckin.sh`는 2.2의 1–3단계(`read-tree OLD`, `hash-object -w`, `update-index --cacheinfo`, `write-tree`, `commit-tree -p OLD`, `update-ref NEW OLD`)를 그대로 옮긴 스크립트다.

### 9.10 `rev` 예외는 동시 `--force` amend를 덮는다 (C3)

A=$(ckin.sh ait/master $T K1.yaml 'rev: r0\nbody: Y\n')

### 9.12 mode와 symlink는 blob OID를 바꾸지 않는다 (C5)

### 9.13 행 범위의 diff는 git이 커밋 없이 준다 (U22, C22)
a.c 10행. 커밋 2에서 맨 위에 2행을 넣고 9행을 고쳤다.
```
git diff --unified=0 $A $B | grep '^@@'    (A, B는 두 판의 blob OID. 커밋 없이 된다)
@@ -0,0 +1,2 @@
@@ -9 +11 @@ line 8
```
옛 좌표에서 판정한다: 4–6행은 접촉 구간 [0,1]·[9,9] 어디에도 겹치지 않는다: 같다(표시할 때는 6–8행으로 사상). 8–10행은 [9,9]에 겹친다: 다르다.
```
git log --format=%s -L 4,6:a.c   → 커밋 1만 나온다 (커밋 2는 맨 위 삽입뿐이라 이 범위를 건드리지 않았다고 git이 판정)
```

### 9.14 행 범위에 기준 blob이 없으면 엉뚱한 행을 본다 (C21)
a.c 50행(`L1`…`L50`), 커밋 1에서 계약 `a.c:10-40`. 커밋 2에서 맨 위에 2행을 넣었다. 커밋 3에서 원래 범위 안의 `L40`을 고쳤다.
```
sed -n 10p a.c; sed -n 40p a.c (커밋 2)   → L8 L38      (10-40을 지금 파일에 그대로 대면 다른 행)
git diff -U0 … $B1 $B2 | grep '^@@'       → @@ -42 +42 @@ L39    (10-40에 닿지 않는다: 잘못된 "같음")
git diff -U0 … $B0 $B1 | grep '^@@'       → @@ -0,0 +1,2 @@       (기준 blob B0에서 사상하면 12-42가 되고, 42행 hunk에 닿는다)
```

git diff-files --quiet -- src/api/a.c → exit 0 ;  git ls-files -v -- src/api/a.c → h src/api/a.c

GIT_INDEX_FILE=$TMP git read-tree $RT; GIT_INDEX_FILE=$TMP git commit -q -m fulfil

```

### 9.28 fulfill의 커밋 단계 (4차 검수, Claude가 다시 돌림)
```
git add -N n.c; git diff --cached --quiet → 0 ; git diff-index --cached --quiet HEAD → 1 ; git commit → "no changes added to commit"
pre-commit: git reset -q HEAD -- p.c ; git commit -qm e → exit 0, HEAD^{tree} == HEAD^^{tree}   (빈 커밋)
(ait/x 체크아웃 중) git fetch -q --dry-run … . "${T}:refs/heads/ait/x" → fatal: refusing to fetch … checked out at …  exit 128 ; 해제 후 exit 0
(리뷰어 재현) pre-commit이 계약 범위 10–40행을 지우고 git add → 커밋 성공, HEAD에서 그 범위가 ?deleted
```

### 9.31 빈 `fulfilled:` 키를 생략하면 amend와 첫 이행이 충돌한다 (규격 2.3.2, Claude가 돌림)
`spec/drafts/v1.1-repro/v6merge.sh`(git 2.53.0):
```
A) 바탕에 fulfilled: 없음, 한쪽 amend(rev·edited·body), 다른 쪽 첫 이행 → merge-tree exit 1
B) 바탕에 빈 fulfilled: 있음, 같은 두 변경                         → merge-tree exit 0
C) 한쪽 undertakes: [D], 다른 쪽 undertakes-partially: [D]        → merge-tree exit 0 (섞인 상태가 충돌 없이 생긴다. 규격 4.10)
```

### 9.32 `git status`는 ait의 범위 인자를 모른다 (규격 6.3, Claude가 돌림)
```

git status --short -- "a.c:1-2"  → (출력 없음) exit 0   (a.c를 고쳤는데도)
git status --short -- :/         →  M a.c
git for-each-ref --format='%(push:remotename)' refs/heads/ait/master → up   (remote.pushDefault=up, branch.ait/master.remote=origin. 규격 6.5.5)

```
