# `ait contract pull` 절차 (초안)

규격 v14의 7.12.1을 바꾸려는 초안이다. 이 문서에 없는 것은 규격 v14(`spec/ait-phase1-spec.md`)를 따른다.

## 1. 왜 바꾸나

지금 규격(7.12.1-4)에서는 받을 커밋에 아직 이행되지 않은 코드가 섞이면 `contract pull`이 멈춘다. 그리고 에이전트에게 계약 커밋만 순서대로 `git cherry-pick`하라고 안내한다(`bring in only its contract commits, in this order, keeping empty ones: 'C1' 'C2' …`). 이 방식에는 문제가 둘 있다.

1. **충돌 없는 `git cherry-pick`에는 ait의 검사 hook이 돌지 않는다.** git 2.53에서 재현해 보니 `prepare-commit-msg`와 `post-commit`만 돌았다. ait가 검사하는 `pre-commit`·`commit-msg`는 돌지 않았다. `--edit`를 주고 편집기를 아무것도 하지 않게 해도 마찬가지였다. 그래서 그 커밋이 계약을 망가뜨려도 그 자리에서 알릴 수 없다. 지금 규격은 이것을 막으려고, pull이 cherry-pick 결과를 미리 흉내 내어 "골라도 되는지"를 따진다. 커밋을 하나씩 적용한 중간 상태까지 본다.
2. **에이전트가 원래 커밋의 OID를 따다가 git 명령을 직접 실행해야 한다.** 커밋을 복사하는 일이 에이전트 손에 있어서, ait가 그 과정을 추적할 수 없다.

그래서 계약 커밋만 받는 일을 `contract pull`이 직접 한다. 에이전트는 어떤 경우든 `ait contract pull …` 하나만 실행한다.

## 2. 쓰는 말 (모두 규격 v14에 있는 것)

- **계약 커밋**(7.10.0): 기록줄 `Ait-Request`가 붙은 커밋(ait 명령이 만든 커밋과 충돌 해결 커밋), 그리고 git으로 만들었지만 계약 경로(`.ait/` 아래와 명세 파일)만 바꾼 병합 아닌 커밋이다. 모든 부모와 다른 경로가 있고 그것이 모두 계약 경로인 병합 커밋도 계약 커밋이다.
- **중립 병합**(7.10.0): 모든 부모와 다른 경로가 없는 병합 커밋이다.
- **이행 커밋**(7.10.0): `fulfill`이 만든 커밋이다. 병합이 아닌 ait 커밋 중, 부모에서 future인 D·O가 그 커밋에서 current인 것이다.
- **아직 이행되지 않은 코드**(7.12.1-4): 받을 커밋 중 계약 커밋도 중립 병합도 아니면서, 받을 커밋 안의 어느 이행 커밋보다도 앞서지 않은(그 조상이 아닌) 커밋이다.
- **ID**: ait 명령이 만든 커밋에는 커밋 메시지의 기록줄 `Ait-Request: R…`로 ID가 붙는다(5.4). 메시지는 cherry-pick이나 rebase로 복사될 때 함께 가므로, 사본도 같은 ID를 가진다.
- **HEAD의 ID 집합**(5.4): HEAD의 이력에 있는 `Ait-Request` 값과 `Ait-Resolves` 값을 모은 것이다. ID가 여기 있으면 그 변경은 이미 HEAD에 있다.
- **충돌 해결 커밋**(7.1.5): git이 merge나 cherry-pick 도중 충돌로 멈추면, 에이전트가 풀고 마치는 커밋(`git commit --allow-empty --no-edit --cleanup=strip`)을 한다. 그 커밋에서 ait의 hook이 돌아 결과를 검사한다. 결과 레코드가 어느 쪽 판과도 다르면 hook은 새 ID와 `Ait-Resolves: <들인 커밋의 ID>`를 붙인다.

## 3. 절차

`ait contract pull ID|OID [--force]`. 쓰기 전제조건(5.2)은 지금과 같다.

1. **이미 있는가.** ID가 HEAD의 ID 집합에 있거나 OID가 HEAD의 조상이면 `already ID`를 쓰고 끝낸다(지금과 같다).
2. **해결한 커밋으로 바꾸기.** ref 목록에 그 ID를 `Ait-Resolves`로 가진 커밋이 있으면, 그 커밋의 ID로 바꾸어 다시 본다(지금의 7.12.1-2와 같다. 6.3절의 열린 문제 참고).
3. **받을 커밋.** 대상 커밋을 C로 정한다. 받을 커밋은 `git rev-list C ^HEAD`다. C보다 뒤에 쌓인 커밋은 들어오지 않는다.
4. **나누기.** 받을 커밋을 계약 커밋, 중립 병합, 이행 커밋 앞의 코드 커밋(받는다), 아직 이행되지 않은 코드로 나눈다.
5. **아직 이행되지 않은 코드가 없으면 merge한다.** C의 상태를 검사(validate)하고 `git merge --ff --no-edit C`를 한다. 지금 규격과 같다. 이행 커밋 앞의 구현 커밋도 함께 들어온다(규칙 8). 충돌이 나면 git이 멈추고, 충돌 해결 커밋으로 마친다(7.1.3).
6. **아직 이행되지 않은 코드가 있으면 계약 커밋만 받는다.**
   1. **이행은 먼저 merge한다.** 받을 커밋 안에 이행 커밋이 있으면, 그중 다른 이행 커밋의 조상이 아닌 것들을 차례로 먼저 `git merge`한다. 각각 merge하기 전에 그 상태를 검사(validate)한다. 이행 커밋의 조상에는 아직 이행되지 않은 코드가 없으므로(정의상), 이 merge는 이행과 그 구현만 들인다. 충돌이 나면 5처럼 git이 멈춘다. 마친 뒤 같은 pull을 다시 실행하면 이어서 한다.
   2. **받을 수 있는가.** 남은 받을 커밋을 다시 구한다(`git rev-list C ^HEAD`). 그중 계약 커밋이고, 병합이 아니고, 계약 경로만 바꿨고, ID가 HEAD의 ID 집합에 없는 것이 **받을 계약 커밋**이다. 순서는 `--reverse --topo-order`다. 같은 ID를 가진 것이 여럿이면 5.4의 방법으로 하나만 쓴다. 다음 중 하나라도 맞으면 계약 커밋만으로는 받을 수 없다.
      - 남은 계약 커밋 중 받을 계약 커밋이 될 수 없는 것(병합 커밋, 코드도 바꾼 ait 커밋)이 있다.
      - 아직 이행되지 않은 코드 중 계약 경로를 바꾼 커밋이 있다.

      그때는 지금처럼 멈춘다(`E_MIXED`). hint는 `--force`(코드까지 받는다)와 `to see it without taking its code, read commit 'C'`다.
   3. **하나씩 계산하고 검사한다.** 받을 계약 커밋 X마다 차례로 다음을 한다. 여기까지는 HEAD도 index도 작업 폴더도 건드리지 않는다.
      - `git merge-tree --write-tree --merge-base=X^ <지금까지의 결과> X`로 X를 얹은 tree를 메모리에서 계산한다. 이 명령은 ait의 merge driver(`.gitattributes`의 `merge=ait`)를 쓴다. 재현으로 확인했다.
      - 충돌이 없으면 그 tree의 상태를 검사한다. 상태가 틀리지 않아야 하고(validate), 새 미확인이 생기지 않아야 한다(9.1). 지금 규격의 "골라도 되는지" 판정(7.12.1-4)과 같은 조건이다. 어기면 아무것도 공개하지 않고 멈춘다. hint는 2와 같다.
      - 통과하면 `git commit-tree`로 커밋을 만든다. 메시지와 author는 X의 것이다. 결과 레코드가 X의 판과 같으면 메시지는 그대로이고(같은 ID), 다르면 충돌 해결 커밋과 같은 규칙을 따른다. 곧 새 ID, `Ait-Resolves: <X의 ID>`, `Ait-Agent`·`Ait-Session`은 pull을 실행한 쪽의 것이다(7.1.5).
   4. **공개한다.** 충돌 없이 계산한 커밋들을 5.5의 방법으로 한 번에 공개한다. 브랜치 ref를 CAS로 옮기고, index와 작업 폴더를 맞춘다. 중간에 HEAD가 움직였으면 `E_HEAD_MOVED`이고 아무것도 바뀌지 않는다.
   5. **충돌이 나면 거기서 git에 넘긴다.** 3에서 X가 충돌하면, 그 앞까지 계산한 커밋을 4로 공개한다. 그다음 작업 폴더에서 실제로 `git cherry-pick --allow-empty --keep-redundant-commits X`를 실행한다. merge-tree가 충돌이라고 한 것이므로 git도 충돌로 멈춘다. 그러면 지금 규격의 충돌 처리(7.1.3 통합 상태, 7.13 merge driver의 hint, 마치는 커밋)가 그대로 적용된다. pull은 git의 종료 코드로 끝나고, hint에 같은 pull을 다시 실행하라는 말을 붙인다.
   6. **다시 실행하면 이어서 한다.** 이미 받은 커밋은 ID가 HEAD의 ID 집합에 있으므로 건너뛴다. 충돌 해결 커밋은 `Ait-Resolves: <X의 ID>`를 가지므로 X도 건너뛴다.
7. **출력.** 끝까지 받았으면 `included ID`를 쓰고, 지금처럼 받은 변경에 대한 hint를 새 HEAD로 판정해 쓴다(7.12.1-7). 6에서 계산해 공개한 커밋에는 hook이 돌지 않았다. 그래서 그 경고(들여온 미확인)는 pull이 직접 쓴다. 지금 규격에서 fast-forward나 `--force`일 때 하는 것과 같다.
8. **`--force`**는 지금처럼 C까지 모두 merge한다(`--no-verify`).

에이전트가 보는 것은 `ait contract pull …`과 그 출력뿐이다. git의 cherry-pick이나 원래 커밋의 OID를 다룰 일이 없다. 충돌로 멈췄을 때만 지금처럼 충돌을 풀고 마치는 커밋을 한다.

## 4. 재현으로 확인한 git 동작

scratch 저장소, git 2.53.

| 확인한 것 | 결과 |
| --- | --- |
| 이행 커밋 R6까지 merge(구현 커밋 impl → R6 → wip → R7) | R6, impl, 그 앞의 offer 커밋만 들어온다. wip·R7은 안 들어온다 |
| cherry-pick 사본 | OID는 바뀌고, `Ait-Request: R1` 기록줄은 그대로 따라온다. 원본은 HEAD의 조상이 아니다 |
| 충돌 없는 `git cherry-pick`에서 도는 hook | `prepare-commit-msg`, `post-commit`뿐이다. `--edit`와 아무것도 안 하는 편집기를 줘도 같다 |
| `git cherry-pick --no-commit` | 충돌이 있든 없든 `CHERRY_PICK_HEAD`를 남기지 않는다. 그래서 ait가 통합 상태로 알아보지 못한다. 쓸 수 없다 |
| 원래 빈 커밋을 cherry-pick | `--allow-empty`가 없으면 멈춘다. 있으면 기록줄과 함께 들어온다 |
| 이미 든 내용을 다시 cherry-pick(결과가 빔) | `--allow-empty --keep-redundant-commits`면 빈 커밋으로 들어온다 |
| `git merge-tree --write-tree --merge-base=X^ HEAD X` | 작업 폴더와 HEAD를 건드리지 않고 tree를 계산한다. ait의 merge driver를 쓴다 |
| merge-tree의 버전 | `--write-tree`는 git 2.38, `--merge-base`는 2.40부터다(git RelNotes). 규격의 최소 버전은 2.34다 |

## 5. 여러 에이전트가 동시에 일할 때 살펴본 것

1. **받는 대상은 시작할 때 고정된다.** C는 커밋이므로, 보낸 쪽이 그 뒤에 더 커밋해도 받을 커밋은 바뀌지 않는다.
2. **내 브랜치는 나만 움직인다.** 에이전트 하나가 worktree 하나와 브랜치 하나를 쓴다(10.1). 그래도 같은 worktree에서 다른 ait 명령이 동시에 돌 수 있다. 공개는 CAS(5.5)라서 HEAD가 움직였으면 아무것도 바꾸지 않고 멈춘다. 다시 실행하면 이어서 한다.
3. **알림이 두 번 가지 않는다.** listener는 사본을 보면, 같은 ID에 같은 뜻 지문(FP, 9.5)이면 건너뛴다. 계산한 사본의 레코드가 X와 같으면 FP도 같다. merge되어 레코드가 달라진 사본은 새 ID를 받으므로 새 사건으로 알린다. 내용이 실제로 다르기 때문이다.
4. **두 에이전트가 같은 변경을 각자 받으면** 두 브랜치에 같은 ID의 사본이 생긴다. 나중에 두 브랜치를 합치면 같은 내용이라 충돌 없이 합쳐진다. HEAD의 ID 집합과 이력(7.9.5, 같은 ID에 같은 레코드는 한 번만 쓴다)은 ID로 하나로 본다.
5. **보낸 쪽이 rebase하면** 원본의 OID가 사라진다. 받은 쪽의 사본은 ID가 같으므로 다시 받으라고 하지 않는다.
6. **받은 뒤 원본 브랜치를 merge하면**(예: 보낸 쪽의 이행을 받을 때) 같은 변경이 사본과 원본으로 두 번 들어온다. 같은 내용이면 git이 충돌 없이 합친다. 그 사이 내가 그 레코드를 더 바꿨으면 줄이 겹칠 때 충돌하고, 7.13의 merge driver가 다룬다.

## 6. 열린 문제 (검수에서 봐 주기를 바라는 것)

1. **더 나은 알고리즘이 있는가.** 아래 대안을 생각했다.
   - **(지금 안)** merge-tree로 메모리에서 계산하고, 충돌만 git에 넘긴다. 결과가 정확하고, 공개 전에 검사하므로 어중간한 상태가 남지 않는다. git 최소 버전은 2.34에서 2.40으로 오른다(사용자가 허용함, 2026-10-09).
   - **(2.34 유지)** X가 바꾼 경로마다 HEAD의 판이 X^의 판과 같으면 X의 판을 그대로 쓴다. merge가 필요 없으므로 ait가 직접 tree를 만든다. merge가 필요한 경로가 하나라도 있으면 실제 `git cherry-pick`에 넘긴다. 그런데 git이 충돌 없이 합치면(merge driver가 푼 경우 포함) hook 없이 커밋된다. 그러면 pull이 그 뒤에 검사하고 경고만 할 수 있다.
   - **(계약 상태만 한 커밋으로)** 받을 계약 커밋들이 만드는 레코드 상태를 커밋 하나에 담고, 기록줄에 그 ID들을 `Ait-Resolves`로 단다. 단순하다. 하지만 ID마다의 사본이 남지 않고, 그 커밋은 새 ID를 가지므로 다른 에이전트에게 새 알림이 간다.
   - **(보내는 쪽에서 막기)** 계약 커밋을 언제나 코드 커밋보다 앞(공유된 판 바로 위)에 두게 해서, 받을 때 섞일 일 자체를 없앤다. 그런데 일하다가 요구를 거는 것이 정상 흐름이라(전제 2, 10.1a) 막을 수 없다.
2. **6.1(이행을 먼저 merge)이 맞는가.** 이 단계가 없으면, 이행 뒤에 작업 중 코드가 쌓인 브랜치에서 그보다 뒤의 계약 변경을 받을 때 `--force`밖에 없다. 이행을 코드 없이 받으면 미확인이 되기 때문이다. 단계를 하나 더 두는 것이 맞는지, 더 단순한 길이 있는지 봐 주기를 바란다.
3. **해결한 커밋으로 바꾸기(3의 2).** pull의 2단계는 ID를 `Ait-Resolves`로 가진 커밋이 ref 목록 어디에 있든 그쪽으로 바꾼다. 해결 커밋은 X가 반영된 D의 다음 상태이므로, 누가 만들었든 그것을 받는 것은 문제가 아니다(전제 1: 코드에는 주인이 없다). 해결 커밋이 있는 브랜치의 코드도 6의 골라 받기로 들어오지 않는다. 확인할 것은 다음이다: B가 merge로 충돌을 풀었으면 그 해결 커밋은 병합 커밋이라 골라 받을 수 없다(6.2). 그러면 X를 원래 브랜치에서 바로 받았으면 받았을 pull이, B의 해결 커밋으로 바뀌어 멈출 수 있다. 실제로 그런지, 그렇다면 바꾸기를 어떻게 해야 하는지.
4. **같은 ID인데 내용이 다른 경우.** 보낸 쪽이 `git commit --amend`로 기록줄은 둔 채 레코드를 바꾸면, ID는 같고 내용은 다르다. 그러면 1단계(`already`)는 이미 있다고 한다. 알림은 FP가 달라 변경 사건으로 오고, 그때 hint는 OID로 받게 한다(9.4). 이것으로 충분한가.
5. **merge driver와 merge-tree.** merge-tree가 쓰는 attributes는 어디서 읽는가(작업 폴더의 `.gitattributes`인지, HEAD tree인지). 그 차이로 결과가 달라질 수 있는가.
6. **이 밖에 동시 작업에서 모순이 생기는 경우.** 받을 계약 커밋 중 하나가 내 브랜치에 이미 다른 판으로 있는 경우, 받은 뒤 보낸 쪽이 그 계약을 되돌린 경우, 같은 worktree에 session이 둘 있는 경우 등.

## 7. 판 이력으로 받기와, 실험에서 경우를 줄이는 근거 (2026-10-09)

git의 merge·cherry-pick으로 받는 방식은 경우 216개를 두 순서로 돌린 실험에서 어느 변형도 하한(충돌 90, 멈춤 0)에 이르지 못했다. 레코드의 판 이력(prev, 2.2.4)으로 받는 함수는 216번 모두 하한에 이르렀다. 실험 틀과 결과는 scratchpad의 `r22-matrix/`에 있다.

### 7.1 함수 (레코드마다)

- `a ⊒ b`: b가 a 자신이거나 a의 prev를 따라가서 닿는 판. blob은 내용의 해시이고 내용에 prev의 해시가 들어가므로 순환이 없다. 그래서 ⊒는 유한 부분 순서다(해시 충돌은 없다고 본다).
- 뜻: prev와 고정(pin)을 뺀 내용. 뜻이 같다는 동치 관계다(1.5e, 7.1.3-5).
- 받으려는 변경 K의 판 k. U(k) = k를 포함하는 판들. M = U(k)의 극대 판들.
- (0) 내 판 ⊒ k면 이미 받았다.
- (1) M 중 내 판을 포함하는 것이 있으면 그중 하나로 옮긴다(mine′).
- (2) R = M 중 mine′이 포함하지 않는 판. R이 모두 mine′과 뜻이 같으면 결정 없이 합친다(prev = mine′과 R). 하나라도 뜻이 다르면 결정 한 번(prev = mine′과 R).
- blob이 없어 따라갈 수 없으면 포함하지 않는다고 본다.

### 7.2 정리

1. 받은 뒤의 내 판은 k와 M의 모든 판을 포함한다.
2. 결정은 mine′과 뜻이 다른 판이 R에 있고, 둘을 함께 포함하는 판이 저장소에 없을 때만 생긴다.
3. 받기 한 번에 레코드 하나당 결정은 많아야 한 번이다.

### 7.3 실험에 넣지 않은 것과 그 근거

- 해결한 사람이 셋 이상: 분기는 (이미 받음)·(옮길 판 있음/없음)·(R 없음/모두 같은 뜻/다른 뜻 있음)뿐이고, 판이 둘(F의 선택 포함)일 때 모두 나온다. 정리 1~3은 극대 판 수와 무관하다.
- 해결이 여러 번 이어짐: 사이에 끼는 판은 극대가 아니므로 ⊒와 M이 그대로다. 길이 때문에 달라지는 것은 따라갈 blob 수이고, blob이 없는 경우는 "이력 일부가 없는 clone"으로 덮는다.
- clone이 셋 이상: 함수는 E의 저장소 안에서만 돈다. clone 수는 E에 있는 판의 부분집합으로만 영향을 주고, 그 부분 순서에서도 정리가 성립한다.
- E의 자기 변경 종류: 구조 검사(5.9)는 상태 하나의 내용만 본다. 레코드 여럿을 보는 검사는 b·c·d 앞부분·e가 모두 레코드 둘 사이의 관계이고, d 뒷부분(연결 undertaken ∧ O current ⇒ D가 future 아님)만 셋을 본다. 그 위반 상태의 앞 둘(연결 undertaken, O current)은 한 사람이 떠맡고 이행해 혼자 만들 수 있으므로, 셋이 각자 하나씩 바꿔야만 생기는 위반은 없다. 쌍은 "E가 B의 변경을 가짐" 값에서 (내 판의 종류, 받는 판의 종류) = (B의 종류, X의 종류)로 모두 돈다. 조건: 실험의 "이행" 값은 D를 떠맡은 offer의 이행이어야 한다.
