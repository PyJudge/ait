## 3. 바뀐 동작 (의도한 것)

- **environment 출력 형식**: 실행 요청 파일에 environment를 써 넣을 때 schema 타입을 따라 다시 쓴다. 키는 따옴표 없이 쓰고, 목록은 흐름 형식(`[["make", "setup"]]`)으로, 문자열 값은 따옴표로 감싸서 쓴다. 값 자체는 같다.
- **빈 목록**: 목록 키에 값을 비워 두면 형식 오류다. `fulfilled:`만 예외다(U54, 사용자 결정).
- **기록줄 검사의 시점**: 두 검사를 나눴다. 끊는 줄이 메시지에 있는지는 공통 검사보다 먼저 본다(E_USAGE). 설정이 기록줄을 가리는지는 session 뒤에 커밋할 바이트 그대로 본다(E_CONFIG).

## 4. 사용자에게 묻는 것

명세가 정하지 않았거나, 내가 정하면 CLAUDE.md에 어긋나는 것들이다.

1. **`sigchain_push_common` 재정의** (스냅샷에 있던 것)
   - 상황: ait가 git에서 옮겨 온 `sigchain.c`에서 이 함수를 빼고, `ait.c:177`에 같은 이름으로 다르게(SIG_IGN을 보존하게) 다시 정의했다. git에서 옮겨 온 `tempfile.c`와 `run-command.c`가 이 재정의된 동작에 기댄다.
   - 문제: CLAUDE.md의 "옮겨 온 코드는 고치지 않는다"에 걸린다.
   - 선택지:
     - (a) 그대로 둔다.
     - (b) git의 함수를 되살리고, ait 쪽에는 다른 이름을 붙여 ait의 정리 코드만 그것을 쓴다. 이러면 tempfile과 run-command가 git의 동작으로 돌아가서, t10~t12의 신호 처리 시험을 다시 봐야 한다.
2. **upstream을 두 곳에서 판정함**
   - 상황: pull은 `upstream_of`(`rev-parse <branch>@{upstream}`)를 쓰고, status와 listen은 `names_upstream`(for-each-ref 한 번)을 쓴다. "upstream이 원격 ait ref인가"를 두 함수가 각자 판정한다.
   - 선택지: 명세 6.5.6이 pull에 `%(upstream:remotename)`을 쓰라고 하므로 for-each-ref 쪽 하나로 합칠 수 있다. 합칠지 묻는다.
3. **probe 커밋을 쓰는 곳**
   - 상황: 기록줄 검사가 쓰는 probe 커밋은 임시 object 디렉터리에 쓰고 지운다. 그래서 저장소에는 아무것도 남지 않는다.
   - 선택지: 저장소 object에 쓰면 코드가 짧아지는 대신 gc 대상인 객체가 남는다. 지금 방식으로 둘지 묻는다.
4. **128자를 넘는 키**: libyaml은 키가 128자를 넘으면 YAML complex key(`? …`)로 쓴다. 이렇게 쓴 파일도 ait가 다시 읽을 수는 있지만, 사람이 보기에는 낯선 모양이다. 그대로 둘지, 키 길이에 상한을 둘지 묻는다.

### 4장의 결정 (2026-10-17)

1. (a) 둔다. 옮겨 온 코드를 고친 곳마다 무엇을 왜 바꿨는지 주석으로 적었다(U55). 같은 원인으로 표시 없이 바뀌어 있던 `precompose.c`의 설정 읽기도 표시했다. `strbuf_vaddf`의 `_()`는 git 원문으로 되돌렸다. 쓰이지 않던 `utf8.c`·`utf8.h`는 지웠다.
2. 합쳤다(U56). `names_upstream` 하나가 판정하고, `upstream_of`는 없앴다.
3. 임시 object 디렉터리를 유지한다(U57).
4. 그대로 둔다(U58). 해당하는 키는 환경 정의의 `env.set` 변수 이름뿐이다.
