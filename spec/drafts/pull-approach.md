# `ait contract pull`: 어떻게 여기까지 왔나 (검수자용)

검수 대상은 [pull-criteria.md](pull-criteria.md)(기준, 개정 3)다. 이 문서는 그 기준이 어떤 문제에서 나왔고 어떤 차원으로 경우를 나눴는지를 적는다. 근거가 된 사용자의 결정은 [pull-decisions.md](pull-decisions.md)에 있다.

## 1. 지나온 길

1. **v14** (`../ait-phase1-spec.md` 7.12): `pull RID`는 요청 커밋과 그 조상을 git merge로 들인다. 아직 이행되지 않은 코드가 섞이면 계약 커밋만 골라 cherry-pick하게 하고, 이미 받았는지는 요청 ID로 본다.
   - 드러난 문제:
     - 충돌 없는 cherry-pick에는 ait 검사 hook이 돌지 않는다.
     - 남이 merge로 해결한 커밋은 골라 받을 수 없다.
     - 같은 ID에 내용이 다른 amend를 "이미 받음"으로 본다.
2. **개정 2** (r24 검수본): 계약 단위로 바꿨고, 계약 파일의 판과 그 `prev`로 포함 관계를 본다. 그런데 받는 방법은 판과 고정한 파일의 **내용만 복사**하는 것이었다.
3. **r24 4중 검수 결과** ([pull-review-r24.md](pull-review-r24.md)): 판으로 판정하는 핵심은 버텼다. 그러나 내용만 복사하니 남의 커밋이 내 이력에 들어오지 않았고, 커밋 이력에 기대던 판단이 깨졌다.
   - 확인 기록이 사라져 미확인이 생긴다.
   - merge base가 어긋난다.
   - 구현이 기대는 파일(고정되지 않은 내부 함수 등)이 오지 않는다.
4. **사용자 결정** (2026-10-09): ait는 버전 관리 프로그램이다.
   - pull은 **이력째** 받는다. 받을 판이 처음 들어간 커밋과 그 앞을 merge한다.
   - 들어오는 이력이 바꾸는 **계약은 모두 지정**해야 받고, 코드는 언제나 함께 온다.
   - git 조작은 보지 않고 **판만** 본다.
     - 규칙에 안 맞는 판은 사고이고, 받지 않는다.
     - 옛 판으로 돌아간 브랜치는 그 브랜치만 옛 상태에 있을 뿐이다.

## 2. 경우를 나눈 차원

| 차원 | 값 | 기준의 행 |
| --- | --- | --- |
| A. 최신 판의 모양 | 하나 / 둘 이상(본문 다름) / 둘 이상(본문 같음) / 내 판이 그중에 있음·없음 / 누가 이미 merge로 합친 판이 있음 | A1~A3, U1~U8, G1~G4b |
| B. 판을 만든 일 | 조건 수정, 이행, cancel, 다시 확인(고정만 다름), drop 이행(withdrawn), amend로 다시 씀 | U1, U3, U4, U6, U7, U8 |
| C. 들이는 이력에 든 것 | 코드만 / 다른 계약 변경 / 떠맡기 기록 / 나중에 되돌려진 판 | W1, N1, W2, K1, K6, K7, E1 |
| D. 받는 결과의 검사 | 5.9 d(떠맡기), 5.9 e(공유 명세), 내 current의 코드·명세, 받는 current에 내 변경이 합쳐짐, 확인한 파일의 코드 충돌, 확인과 무관한 코드 충돌 | N5, SF1, S1~S4, C1~C4 |
| E. git 조작과 객체 | revert, amend, cherry-pick 사본, 이력 다시 쓰기, 얕은 clone, 손으로 고친 판 | U8, R1~R3, CP1, M1 |
| F. 들이는 커밋 수 | 하나 / 둘 이상(octopus 성공·실패) | MH1, MH2 |

넣지 않은 것과 그 이유는 다음과 같다.
- **셋 이상이 갈라진 경우:** 선택지가 늘 뿐 규칙이 같다(U2는 둘).
- **계약 파일 이름이 바뀌는 경우:** ID는 바뀌지 않는다(2.1.5).
- **지워진 원격 브랜치의 추적 ref:** ref 끝 하나로 다룬다.
- **partial clone:** 객체가 없는 것은 M1과 같다.

## 3. 무엇을 실제로 돌렸나

- [pull-criteria-runs/scen.py](pull-criteria-runs/scen.py)가 각 행의 이력을 실제 git 저장소(2.53.0)로 만든다.
  - 계약 파일 merge에는 v14 merge driver(7.13.1)의 1·2·3·5단계를 쓴다.
  - 출력하는 것은 두 가지다. 하나는 git의 사실(merge와 merge-tree 결과, 충돌 경로, 들이는 커밋과 그 새 커밋 수)이고, 다른 하나는 기준의 낱말에 따른 데이터(포함, 최신 판, 사고 판)다.
- [flows.py](pull-criteria-runs/flows.py)는 hint를 그대로 따른 결과가 v14의 5.9 b~e를 지나는지, 새 미확인이 없는지를 본다.
- ait의 판정 자체(멈출지, 무엇을 hint로 줄지)는 기준의 규칙으로 손으로 정했다. 스크립트가 판정하지 않으므로, 기대값을 구현과 비교하는 순환은 없다.

## 4. 검수에서 특히 보아 줄 것

1. 기준의 규칙이 결정 1~12와 어긋나는 곳.
2. 같은 입력에서 두 구현이 서로 다른 결과를 낼 수 있는 곳(정의가 모자란 곳).
3. hint를 그대로 따랐는데 같은 거절이 되풀이되거나, 막다른 길로 가는 경우.
4. 표에 빠진 경우 중, 규칙이 답을 정하지 못하는 것.
5. 5절(규격에서 바뀌는 것)에 빠진 조항.

반례와 대안은 반드시 실제 git 저장소에서 돌린 명령과 출력으로 보여 준다.
