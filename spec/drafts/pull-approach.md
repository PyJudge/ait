# `ait contract pull`: 어떻게 여기까지 왔나 (검수자용)

검수 대상은 `pull-criteria.md`(기준)다. 이 문서는 그 기준이 어떤 문제와 차원에서 나왔는지를 적는다.

## 1. 출발점: v14의 pull은 커밋 단위다

규격 v14(`../ait-phase1-spec.md` 7.12)의 `ait contract pull RID`는 다음과 같다.
- 요청 커밋과 그 조상을 `git merge`로 들인다.
- 아직 이행되지 않은 코드가 섞이면 계약 커밋만 골라 cherry-pick하게 한다.
- 이미 받았는지는 요청 ID(`Ait-Request`)로 판단한다.
- 그 ID를 `Ait-Resolves`로 가진 해결 커밋이 있으면 그쪽으로 바꿔 받는다.

## 2. 드러난 문제 (검수와 실험)

- 충돌 없는 cherry-pick에는 ait의 검사 hook이 돌지 않는다(재현함).
- 다른 브랜치의 merge 해결 커밋으로 바꿔 받으면, 그 커밋은 골라 받을 수 없어 멈춘다.
- 이미 더 나중 판에 들어 있는 중간 판을 따로 얹다가 충돌한다.
- 같은 ID인데 내용이 다른 amend를 "이미 받음"으로 본다. 기록줄이 없는 계약 커밋은 추적하지 못한다.

## 3. 실험

경우 216개(아래 차원 A)를 두 받는 순서로, 실제 git으로 돌렸다.
- 커밋 단위의 변형들(항상 바꿔 받기 / 바꾸지 않기 / 조건부 / 막히지 않을 때만 / 병합 커밋도 고르기)은 어느 것도 하한에 이르지 못했다. 하한은 정말 갈라진 것만 결정으로 세는 것이다.
- 레코드의 판 이력(`prev`, 2.2.4)으로 판정하는 방식은 모든 경우에서 하한에 이르렀다.
- 원인: 같은 계약 변경이 사본, merge, 남의 해결로 여러 커밋에 흩어지면, 커밋 그래프는 "어느 판이 어느 판을 포함하는지"를 모른다. 레코드의 `prev`는 그것을 직접 담고 있다.

## 4. 방향 전환

- 받는 단위를 커밋에서 **계약**으로 바꿨다: `ait contract pull K…`.
- 같은지는 **판의 본문**(`prev`를 뺀 레코드 내용)을 바이트로 비교해 정한다. 고정(BLOB)도 내용이다.
- 가장 나중 판의 본문이 하나면 통과, 둘 이상이면 오류로 멈추고 고르게 한다.
- 다른 계약은 자동으로 따라오지 않는다. 필요하면 hint로 알리고 함께 지정하게 한다(ait의 "따로 시키지 않은 일은 하지 않는다" 원칙).

## 5. 생각한 차원

| 묶음 | 값 |
| --- | --- |
| A. 갈라짐의 모양 | A 브랜치 앞에 이행 안 된 코드 있음/없음; B 브랜치 없음/이행 안 된 코드/무관한 이행; E 상태 없음/B의 변경 가짐/자기 변경; B의 해결 B 쪽/X 쪽/합침; 해결한 사람 B만/B와 F(F의 선택 셋); 생긴 순서 X 먼저/B 먼저; E가 받는 때 사건마다/마지막에 한 번 |
| B. 레코드 수 | X가 바꾼 계약 D/D와 Q; B가 바꾼 계약 D/D와 Q |
| C. 상태와 변경 종류 | D가 future일 때: 범위 amend, 조건 amend, 떠맡아 이행(구현 커밋 따로/함께), cancel, 떠맡기. D가 current일 때: 다시 확인, 조건 바꾸며 다시 확인, 되돌리기, 되돌리며 조건 변경, 철회, (B만) 사고 |
| D. 명세 파일 공유 | 없음 / E의 future 계약과 공유 / E의 current 계약과 공유 |
| E. 환경 | 같은 저장소 / 이력 일부가 없는 clone; 같은 worktree 동시 작업 없음/있음 |

넣지 않은 것과 그 근거는 `contract-pull.md` 7.3에 있다. 해결한 사람 셋 이상, 해결이 여러 번 이어짐, clone 셋 이상, E의 자기 변경 종류는 판 이력의 부분 순서 성질과 구조 검사가 쌍으로 나뉜다는 것으로 뺐다.

## 6. 왜 기준부터인가

판정 규칙을 코드로 옮긴 모형으로 수십만 건을 돌렸지만, 판독기가 그 코드와 같아 의미가 없었다. 그래서 무엇이 맞는 결과인지를 데이터와 규칙만으로 먼저 정하고(`pull-criteria.md`), 그 뒤에 로직을 만들어 기준에 맞춘다.
