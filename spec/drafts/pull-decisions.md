# `ait contract pull`: 정한 것 (2026-10-09, r24 검수 뒤)

r24 검수 뒤 사용자와 하나씩 정한 것을 적는다. `pull-criteria.md`의 "내용만 복사해 새 커밋을 만든다"는 방식은 버렸다. 새 기준은 이 결정들로 다시 쓴다.

1. **이력째 받는다.**
   - `pull K`는 K의 받을 판이 처음 들어간 커밋을 받는다. 그 커밋과 그 앞의 커밋이 모두 내 이력에 들어온다. 그 뒤의 커밋은 받지 않는다.
   - 근거: ait는 버전 관리 프로그램이다. 어떤 코드가 필요한지 가려낼 수 없다. 예를 들어 고정된 함수가 고정되지 않은 내부 유틸 함수를 부를 수 있다.
2. **들어오는 계약은 모두 지정한다.** 들어오는 이력이 바꾸는 계약을 모두 지정하지 않으면 거절하고, 아무것도 바꾸지 않는다.
   - 예: B의 이행 앞에 A의 이행이 있으면 `pull B`는 거절된다. hint는 `ait contract pull A B`다.
   - 리스너가 A도 본 다음에 받게 하기 위해서다.
3. **코드 커밋은 언제나 받는다.**
   - 계약 변경이 아닌 커밋은 지정 없이 받는다(1의 유틸 예).
   - v14의 `E_MIXED`, "아직 이행되지 않은 남의 코드는 받지 않는다", 그것을 넘기던 pull의 `--force`를 뺀다.
4. **최신이 둘 이상이면 고른다.**
   - 지정한 계약의 최신 판(`prev`로 다른 판에 포함되지 않는 판)의 내용이 둘 이상이면 거절한다.
   - hint는 판을 커밋 이름으로 고르는 명령이다: `pull B=c2`. 내 판이 최신 중 하나면 `B=HEAD`도 선택지에 든다.
   - 고른 쪽의 이력만 받는다. 받은 계약 파일의 `prev`에는 고르지 않은 판도 적는다. 그래서 다음 pull에서 같은 갈라짐으로 다시 멈추지 않는다.
   - 고르지 않은 쪽에는 알림이 간다.
   - 합치려면 하나를 골라 받은 뒤 그 계약을 고친다(amend).
   - 누군가 이미 합쳐 둔 판이 있으면 최신이 하나이므로 그 커밋을 받는다.
5. **이미 받았는지는 판으로 판단한다.** 내 계약 파일이 최신 판들을 모두 포함하면 `already K`다. 요청 ID로 판단하지 않는다.
6. **내 계약이 확인한 것이 바뀌면 받기 전에 거절한다.**
   - 받으면 내 current 계약이 확인한 코드나 명세 파일이 바뀌는 경우, 받기 전에 거절하고 아무것도 바꾸지 않는다.
   - hint:
     - `reopen it first: 'ait future amend K -m <why>', then rerun this command`
     - K를 내 current offer O가 떠맡고 있으면 `'K' is undertaken by current 'O'; reopen them in the same request: 'ait future amend O future amend K -m <why>', then rerun this command`
     - 또는 `ait contract pull B --force -m <why>`. 사소하다고 판단해 받는 것이고, K의 `forced` 확인 기록으로 남는다. v14에 없는 새 길이다.
     - (10에서 첫 두 hint를 한 요청 꼴로 바꿨다: `ait contract pull B future amend K -m <why>`.)
   - 명세 파일을 공유하는 내 계약이 future면 거절하지 않는다. 새 내용으로 다시 고정한다(6.2).

7. **떠맡기 기록은 D와 O 둘 다의 변경이다.**
   - `.ait/undertake/D-O`가 바뀌는 것은 D와 O의 변경으로 본다(9.2-3과 같다). 그래서 들어오는 이력에 떠맡기나 release가 있으면 2에 따라 D와 O를 모두 지정해야 받는다.
   - 따로 둔 offer→demand 규칙(옛 J8)은 없앤다.
   - 예: 내 current offer O에 남이 떠맡기를 붙인 이력을 `pull D`로 받으려 하면 거절된다. hint는 `ait contract pull D O`다.

8. **git 조작을 보지 않고 계약 파일(판)만 본다.** git과 술래잡기를 하지 않는다. 어떤 git 조작으로 커밋이 생겼는지, 기록줄이 있는지는 판정에 쓰지 않는다.
   - **규칙 1:** 판은 `prev`에서 ait 규칙(상태 전이)으로 갈 수 있어야 한다. 갈 수 없는 판은 사고다.
     - 무엇인지 모르는 판이므로 pull은 받지 않는다.
     - 그 브랜치는 고칠 때까지 막는다(5.10과 같다).
   - **규칙 2:** 브랜치가 옛 판으로 돌아간 것(revert, reset, 파일만 되돌리기)은 사고가 아니다.
     - 그 브랜치가 옛 계약 상태에 있을 뿐이다. 새 판이 없으므로 남에게 전해지지 않는다.
     - 남에게도 거두려면 ait 명령으로 새 판을 남긴다. 계약 변경은 ait 명령으로만 전해진다.
   - 같은 판을 옮긴 것(cherry-pick, rebase, squash)은 기록줄이 사라져도 사고가 아니다. 규칙에 맞게 손으로 고친 판도 사고가 아니다(이력에 `?`). 기록줄 위조는 판정과 상관없다.
   - ait는 `post-commit` hook을 더 쓴다. 충돌 없는 revert에서도 git이 부르므로, 그 자리에서 알린다(막지 않는다). 옛 판으로 돌아갔을 때의 출력:
     - `warning: this commit put 'D' back to an older version; only this branch has it`
     - `hint: to take it back for others too, undo this commit and reopen it with ait: 'ait future amend D -m <why>'`
     - 되돌린 커밋을 무르면 HEAD가 다시 D1이다. 그래서 그 위의 되돌리기는 `prev`가 D1인 새 판이 되어 전해진다.
   - 규칙 1의 사고도 post-commit에서 알리고, 고치는 길은 5.10의 hint다.
   - 9.2의 사건은 새 판에만 생긴다. 옛 판으로 돌아간 커밋은 남에게 사건이 아니다(규칙 2).

9. **pull은 검사하고, 고르고, 그다음 git merge한다.**
   - 받는 일 자체는 git merge다.
   - ait가 더하는 것은 셋이다: 받을 커밋 찾기, 받기 전 검사(2·6·8), 고르지 않은 판을 `prev`에 남기기(4).
   - git merge를 직접 쓰는 길은 규격·SKILL·hint 어디에서도 가르치지 않는다.

10. **받는 계약 자신의 확인한 코드가 내 변경과 합쳐져 달라지면 받기 전에 거절한다.** 받은 D가 곧바로 미확인이 되기 때문이다. hint는 둘이다.
    - 받으면서 같은 요청에서 되돌린다: `ait contract pull D future amend D -m <why>`. pull 뒤에 도우미 명령 절을 잇는 문법을 새로 둔다.
    - 사소하면: `ait contract pull D --force -m <why>`.
    - 6의 hint도 같은 꼴(한 요청)으로 맞춘다: `ait contract pull B future amend K -m <why>`.
11. **스스로 정한 것** (사용자에게 알림):
    - 같은 판이 여러 커밋에 따로 들어갔으면(복사) 멈추지 않는다. 들어올 커밋이 가장 적은 쪽을 받는다.
    - 코드가 실제로 충돌하면 git처럼 그 자리에서 멈추고, 받는 쪽이 해결해 마친다. 계약 검사는 모두 그 전에 끝난다.

12. **알림은 (계약, 판) 단위로 센다.** 같은 판은 몇 커밋에 생기든 받는 쪽에 한 번만 간다. 옛 판으로 돌아간 것은 사건이 아니므로(8) 섞이지 않는다. 사본을 요청 ID로 가리던 v14 9.5를 대신한다.

13. **끝난 쪽이 이긴다.** 두 사람이 한 계약을 다르게 바꿨는데 한쪽이 끝낸 것(cancel, 철회)이면, 고르라고 멈추지 않고 끝낸 쪽을 받는다. 끝난 상태는 되돌릴 수 없기 때문이다(2.3).
    - 결과는 끝낸 쪽의 내용이고, `prev`에는 내 것도 남는다.
    - 경고: `warning: your change to 'D' is overridden: 'D' was withdrawn in 'a2'`.
    - 그 일이 여전히 필요하면 새 계약을 만든다.
    - 둘 다 끝냈는데 서로 다르면(cancel과 철회) 지금처럼 고른다.
    - r27 검수의 U7 막다른 길(Claude A 3, Claude B 2)을 푼다.

14. **받을 브랜치 끝이 여럿이면 pull 한 번이 차례로 다 받는다.**
    - `pull D O`에서 D와 O의 가장 나중 것이 서로 다른 브랜치 끝(a1, b1)에 있으면, pull이 안에서 차례로(커밋 ID 순) merge한다.
    - octopus는 쓰지 않는다. 계약 파일과 고정 명세 파일은 pull이 정한다.
    - 받을 수 있는지(지정, 고르기, 구조 검사, 확인 검사)는 merge를 시작하기 전에 모든 단계에 대해 판정한다.
    - 코드 충돌이 없으면 부모가 HEAD와 그 끝들인 커밋 하나를 만든다.
    - 코드가 충돌하면 git처럼 그 단계에서 멈춘다. 앞 단계까지는 병합 커밋으로 남는다. 해결해 마친 뒤 같은 명령을 다시 실행하면 나머지를 받는다. → 결정 20으로 바꿨다.
    - D-O 떠맡기 교착과 엇갈린 갈라짐(c가 Y·Z를 고치고 a1·b1이 나눠 더 고친 경우)을 푼다. 둘 다 "pull 한 번에 끝 하나" 제한에서 생겼던 것이다. 실행 확인: `r26-criteria/cycle3.py`(부모 셋, 5.9 통과), `cross.py`.
15. **갈라졌는지는 3-way로 판단한다.** git merge와 같은 방식이다.
    - 두 쪽의 계약 파일이 다르면, 두 쪽이 마지막으로 같았던 내용을 찾는다. 그것은 두 쪽 `prev` 사슬의 공통 조상 중 가장 나중 것들이다.
    - 한쪽이 그 뒤로 바뀌지 않았으면(본문이 그것과 같으면), 다른 쪽이 앞으로 나간 것이다. 고르지 않고 받는다. 결과는 앞으로 나간 쪽의 본문에 `prev` = 두 쪽이다.
    - 둘 다 바뀌었거나, 가장 나중 공통 조상이 여럿이고 내용이 서로 다르면 갈라짐이다. 이때 고른다.
    - 상대 것을 고른 뒤 상대가 더 고치면 또 묻던 구멍을 푼다(실행 확인 `cross.py` T1). 내가 내 것을 골라 두었으면 다시 묻는다(T1b). 둘 다 바꿨기 때문이다.

16. **버려진 변경을 만든 에이전트에게도 알린다.** 고르기나 3-way로 누군가의 변경이 버려지면, 그 변경을 만든 커밋의 `Ait-Agent`를 받는 쪽(9.3)에 더한다.
    - 기록줄은 계약이 맞는지 판정하는 데 쓰지 않고(결정 8), 알림을 누구에게 보낼지 찾는 데만 쓴다.
    - 기록줄이 없으면 보내지 않는다.
    - 결정 4의 "고르지 않은 쪽에는 알림이 간다"를 이것으로 지킨다.

17. **확인은 계약 파일 안에 PINS와 함께 적는다.**
    - `-r`로 확인하면 `check reported <PINS>` 행을, `--force`면 `check forced <PINS>` 행을 계약 파일에 적는다. `--force`는 그전과 같다고 보고 책임진다는 뜻이다.
    - PINS는 그 계약이 지금 고정한 코드와 명세 파일 내용의 해시다. 그래서 고정이 바뀌었는데 옛 확인 행이 남아 있으면 PINS가 맞지 않아 드러난다.
    - 까닭: 커밋 메시지에만 남기면, squash나 amend로 메시지를 다시 쓴 것과 ait를 우회해 확인 없이 바꾼 것이 데이터로 똑같아진다(실행 확인: 두 저장소의 tree, 계약 파일, 명세 파일, 이력의 기록줄이 같았다).
    - 그래서 판정이 모두 데이터만으로 된다(결정 8과 맞다).
      - **사고:** 고정이 바뀌었는데 PINS가 맞는 확인 행이 없다. 확인 없이 current가 된 것도 여기에 든다. 명세 파일이 고정과 다른 것(2.4.1)과 규칙 1에 어긋나는 계약 파일도 사고다.
      - **미확인:** 확인 행이 맞는데, provider 코드가 고정과 다르다.
    - r27 검수의 "확인 기록이 아예 없는 current를 그냥 받는다"(Codex A H1, Claude A 5)가 사고로 잡힌다.
    - 남는 한계: PINS를 계산해 확인 행을 손으로 써 넣는 위조는 막지 못한다(지금의 기록줄 위조와 같다, 11.1).
    - 바뀌는 규격: 규칙 1("확인은 기록줄에만"), 1.5a, 2.2의 레코드 형식. `Ait-Check` 기록줄은 판정에 쓰지 않는다(남길지는 규격을 쓸 때 정한다). 다시 확인할 때마다 계약 파일에 새 내용이 생기지만, 다시 고정과 같아서 뜻이 바뀌지 않으므로 알림은 가지 않는다.
    - 4번 질문("명세가 확인 없이 바뀐 current")의 답이다.

18. **결정 12의 범위.**
    - 계약 파일이 바뀐 알림은 (계약, 계약 파일 내용) 단위로 센다.
    - 미확인 알림은 (계약, 계약 파일 내용, 그때의 provider 코드 내용) 단위로 센다.
    - 같은 코드 변경이 사본으로 여러 커밋에 생기면 한 번만 가고, 코드가 다시 다르게 바뀌면 또 간다.
    - 까닭: 코드만 바뀌어 미확인이 되는 커밋은 계약 파일이 그대로라서, (계약, 계약 파일 내용)으로만 세면 미확인 알림이 빠진다(r27: Claude A 4, Claude B 9).

19. **O를 나중에 이행할 때는 이미 current인 D도 다시 확인한다.** v14 규칙 5와 1.6 그대로다.
    - 상황: O가 D를 떠맡았고, D가 먼저 이행되어 current다(1.6이 허용한다). O는 future로 남아 개발을 계속한다.
    - 나중에 `ait fulfill O -r <file>`을 할 때, 결과 파일에는 O의 과제와 D의 과제가 함께 들어 있어야 한다.
    - 까닭(사용자): D와 O는 의존 관계라서, O를 구현하는 과정에서 D를 건드렸을 것이다. 사고는 아니라도 미확인을 전제로 하는 것이므로 `-r`을 요구하는 것이 맞다. 미확인은 D의 provider 범위만 보므로, D가 기대는 범위 밖의 코드가 바뀐 경우도 이 확인이 잡는다.
    - 계약 파일(결정 17):
      - O는 current가 되고 확인 행을 적는다.
      - O의 개발이 D가 확인한 코드를 바꿨으면, D는 같은 커밋에서 다시 고정되고 새 확인 행을 적는다.
      - 바꾸지 않았으면 D의 계약 파일은 그대로다. 같은 내용은 이미 확인되어 있다.
    - 함께 고칠 규격: 6.5의 "빈 amend는 레코드가 같아도 다시 확인한다. 확인의 기록은 기록줄이기 때문이다". 결정 17로 확인이 계약 파일에 있으므로, 같은 내용을 다시 확인하면 계약 파일은 바뀌지 않는다. 확인 행이 바뀔 때(예: `forced`를 `-r`로 다시 확인)만 남는다.
    - 4중 검수에서도 확인한다. → r30: v14 1.5b, 1.6, 7.7.4와 맞는다고 확인됐다(Claude A, Codex B). 남은 것은 확인 행을 쓰는 방법뿐이었고, 결정 22로 정했다.

20. **여러 끝을 받다가 코드가 충돌하면, git이 브랜치 여럿을 한 번에 합칠 때의 규칙을 따른다.** (2026-10-10, r30 3절 1번. 결정 14의 마지막 줄을 바꾼다)
    - 중간 커밋을 만들지 않는다. 충돌을 풀고 커밋하면, 부모가 HEAD와 받은 끝 모두인 커밋 하나가 된다.
    - 충돌은 마지막으로 받는 끝 하나에서만 허용한다. 충돌 없이 합쳐지는 끝을 먼저(커밋 ID 순) 받고, 충돌하는 끝을 마지막에 둔다.
    - 충돌하는 끝이 둘 이상이면 아무것도 바꾸지 않고 멈춘다. hint는 나눠 받을 수 있으면 그 명령이고, 아니면(D-O처럼 함께 받아야 구조가 맞으면) 한쪽이 다른 쪽을 먼저 받아야 한다는 상태다.
    - 그래서 모든 검사를 시작 전에 끝낸다. (abort는 git의 일로 두었다. 기록 81)
    - 근거: git 2.53에서 `git merge a b`의 앞쪽 a가 충돌하면 `Should not be doing an octopus.`로 거절하고 아무것도 바꾸지 않는다. 마지막 끝만 충돌하면 충돌 상태로 멈춘다(`pull-criteria-runs/verify-r30.log` V5).
    - 푸는 것: 중간 커밋이 abort해도 시작 상태로 돌아가지 않던 것, 그 커밋이 구조를 어기던 것, 둘째 충돌 뒤의 셋째 끝을 미리 검사할 수 없던 것(Codex A F2, Claude B B8·B9).

21. **`prev`에 끝난 판이 있으면 그 판도 끝난 판이어야 한다. 아니면 사고다.** (2026-10-10, r30 3절 2번)
    - 정확히는, 본문이 `prev`의 끝난 판 중 하나와 같아야 한다.
    - 리팩터링과는 다르다. 리팩터링은 current를 future로 되돌리는 것이고(1.5d), 계약은 살아 있다. 끝난 상태(cancelled, withdrawn 등)에서는 나가는 길이 없다(2.3). 그래서 ait 명령으로는 이미 관문이 막는다(2.3.1). pull도 결정 13으로 되살리지 않는다.
    - 구멍은 git merge 충돌을 손으로 풀 때였다. v14 7.1.3-4는 "출발 판 중 하나에서" 갈 수 있으면 통과시켰다. 그래서 cancel 판을 `prev`에 담은 채 future로 남는 판이 생겼고, 그 판을 받은 쪽에서 cancel이 경고 없이 되살아났다(Claude B B2, `verify-r30.log` V2).
    - 그래서 ait 명령, pull, git merge가 같은 규칙을 따른다. 그 일이 여전히 필요하면 새 계약을 만든다(결정 13).
    - 함께 고칠 규격: 결정 8 규칙 1(사고 판의 정의), v14 2.3.2와 7.1.3-4. 출발 판에 끝난 판이 있으면 끝난 판에서만 출발할 수 있다.

22. **같은 PINS(같은 코드·명세)면 `reported`가 이긴다.** (2026-10-10, r30 3절 3번)
    - 확인 줄은 이렇게 쓴다. 같은 PINS를 테스트로 통과시킨 판(`reported`)이 있으면 결과는 `reported`다. PINS가 바뀌었을 때만 이번 확인의 종류로 새로 쓴다(`-r`이면 `reported`, `--force`면 `forced`).
    - pull이 새 판을 쓸 때: 이번 pull의 최신 판과 내 판 중 결과와 PINS가 같은 판에 `reported`가 있으면 `reported`, 없으면 `forced`다. 그래서 3-way로 이긴 쪽이 확인 줄만 다른 쪽을 덮어도 `-r` 다시 확인이 사라지지 않는다. 내 쪽도 확인 줄이 바뀌면 새 판을 적는다(`kept D`).
    - ait 명령: v14 8.5와 7.7.4의 "`--force`면 확인 집합의 계약마다 `forced`"를 "PINS가 같고 이미 `reported`면 그대로"로 고친다.
    - 결정 19와 맞춘다. D가 `reported`인데 O를 `--force`로 이행하면 D는 그대로다. D가 `forced`인데 O를 `-r`로 이행하면 D는 `reported`로 바뀐다.
    - 같은 내용을 같은 방법으로 다시 확인하면 계약 파일이 그대로이므로 커밋을 만들지 않는다(`noop`). v14 6.6의 "빈 amend가 있으면 noop이 아니다"를 뺀다. 미확인이던 계약은 다시 고정으로 계약 파일이 바뀌므로 그대로 커밋된다(1.5b, H7).
    - 까닭: `reported`는 "이 코드·명세로 테스트가 통과했다"는 사실이다. 나중에 `--force`가 있었다고 그 사실이 없어지지 않는다.
    - 푸는 것: 새 판의 확인 줄이 정해지지 않아 구현마다 다른 판이 나오던 것, current 결과가 확인 줄 없이 사고 판이 되던 것, 3-way가 `-r` 다시 확인을 알리지 않고 버리던 것, 결정 19와 v14 8.5가 부딪히던 것(Claude A H3·M5, Claude B B4, Codex B 4).

26. **코드 충돌은 파일마다 한 번까지 한 merge 상태에 함께 둔다.** (2026-10-10, r33 3절 1번. 결정 20의 "충돌은 마지막 끝에서만"을 넓힌다)

27. **pull로 남의 이행(current)을 버리면, 고른 쪽이 되돌린 쪽이 된다.** (2026-10-10, r33 3절 2번)

28. **사고 판을 거쳐서라도 끝난 판을 포함하는 판은, 본문이 그 끝난 판 중 하나와 같아야 한다. 아니면 사고다.** (2026-10-10, r39 3절. 기록 88을 결정으로 올렸다)

30. **본문이 같은 판 중 하나를 들일 때(TIE)는, 내 판을 포함하는 판의 커밋을 먼저 고른다.** (2026-10-10, r42 3절)
    - 예(RP6, RP7): 내가 받아 둔 이행 C를 x가 되돌리고 c-B로 바꿨고, y는 처음부터 c-B로 바꿨다. x의 판은 C를 포함하고 y의 판은 포함하지 않는다. pull은 x의 커밋을 들인다. 그래서 x의 되돌림을 실어 오고, 되돌린 쪽은 x다.
    - git과 같다. 내 상태 위에 쌓은 쪽은 git에서 fast-forward로, 판단 없이 받는다. 다른 쪽(y)을 merge하면 충돌을 푼 사람이 되돌린 쪽이 된다. pull에서는 `D=y1 -m <why>`로 직접 고른 사람이 되돌린 쪽이다(결정 27).
    - 다른 규칙과 같은 꼴이다. 뜻(누가 책임지는가)을 데이터로 먼저 가리고, 커밋 수와 해시는 마지막에만 쓴다(기록 92의 차례, 결정 22의 확인 행, 결과 판을 기존 판으로 쓰는 규칙).
    - 대가: 커밋이 더 많은 쪽을 들일 수 있다. 들어오는 남의 코드가 그만큼 늘 수 있다.
    - 고르지 않은 길: (가) 지금대로 새 커밋 수와 해시로 고른다. 되돌린 쪽이 해시로 정해진다. (다) 결과 판의 `prev`로 판정한다. y를 들이면 내 이력에 되돌린 쪽이 없고, 판정이 clone마다 다르다.
    - 기록 9(TIE의 차례)에 첫 기준을 더한다.

31. **출력은 git의 선례와 CLAUDE.md의 git 스타일을 따른다. 상황과 목표 상태는 git의 낱말로 쓴다.** (2026-10-10, C 테스트를 쓰며. 사용자: "깃 용어로 써야지. git의 힌트 예를 따라야지?", "claude.md 참고해")
    - 메시지는 영어 한 행이고, 소문자로 시작하며 마침표를 찍지 않는다. 무엇이 잘못됐는지(까닭)는 `error:` 행에, 할 일은 `hint:` 행에 쓴다.
    - hint는 ait 명령이나 이루어질 상태다. git 명령은 마치는 커밋 하나뿐이다. git 조작을 시키는 말("stash them", "deepen the clone")도 쓰지 않는다. 상태를 말할 때는 git의 낱말(rebased onto, merges cleanly, shallow)을 쓴다.
    - 틀릴 수 있는 hint는 주지 않는다. "여기서 할 수 있는 일이 없다"는 쓰지 않는다. 멈추면 언제나 이루어질 상태가 있다(사용자: "여기서 할 수 있는 일이 없다는 게 말이야 똥이야").
    - MH8(함께만 받을 수 있는 끝들이 같은 파일로 두 번 충돌): 결정 20의 상태(한쪽이 다른 쪽을 담는다)는 rebase로 이룬다. merge로 합친 커밋은 판이 처음 들어간 커밋을 바꾸지 않으므로 이 상태가 아니다(결정 1, scratchpad `r44`에서 확인). 내 쪽에서 이룰 상태도 함께 준다(끝이 둘일 때만. 셋 이상이면 틀릴 수 있어 주지 않는다).
      ```
      error: 'a1' and 'b1' can only be taken together, but both change 'src/x.c', which you changed too
      hint: they can be taken once one of them is rebased onto the other, or once your branch merges cleanly with one of them
      ```
    - 작업 폴더(WT1), 추적하지 않는 파일(NEW2), shallow(SH1), 사고 판 고치기(ID1, ACC1)의 hint도 이 꼴로 고쳤다. 명령을 주는 hint(`pick one`, `name them too`, `take them one at a time` 등)는 v14의 꼴 그대로다.

## Claude가 허락 없이 정한 것 (기록)

아래는 사용자가 직접 정하지 않았는데 Claude가 기준에 넣은 것이다. 괄호는 기준에서 적용된 곳이다.

- 대부분은 사용자의 결정(1~31)이나 v14를 그대로 적용해서 답이 하나로 정해지는 것이다. 이런 것은 따로 묻지 않고 여기에 기록만 한다. 그 끌어냄이 맞는지는 4중 검수가 본다(2026-10-10 사용자: "내 결정을 그대로 넣는 건 왜 물어봐? 문제가 발생해서?").
- 결정과 규격으로 답이 여럿이었던 것, 검수에서 문제가 드러난 것은 사용자에게 물어 결정으로 올렸다(결정 20~31).

### A. 낱말과 판정의 정의 (기준 1절)

1. **본문에서 확인 행을 뺀다.** 결정 17은 확인 행을 계약 파일에 적기로 했을 뿐이다. 내용 비교(갈라짐, 3-way)에서 확인 행을 빼는 것은 Claude가 정했다. 까닭: 같은 고정을 `-r`과 `--force`로 각각 확인한 두 판을 갈라짐으로 보지 않기 위해서다.
2. **포함을 따라가다 객체 저장소에 없는 blob을 만나면 그 가지가 끝난다.** 그래서 얕은 clone이나 다시 쓴 이력에서는 갈라짐으로 멈춘다(M1). 개정 2부터 이어 온 정의다.
3. **사고 판 판정의 세부.**
   - 역할과 creator가 같아야 한다.
   - 2.3의 상태 짝만 본다. target이 current여야 한다, withdrawn에는 fulfilled X가 있어야 한다 같은 다른 레코드와의 제약은 사고 판에서 보지 않고, 받는 결과의 구조 검사로 넘긴다.
   - `prev`의 blob이 없어 판정할 수 없으면 사고 판으로 보지 않는다.
   - 떠맡기 기록은 역할과 creator가 없으므로 state 짝만 본다.

   결정 8은 "prev에서 ait 규칙으로 갈 수 있어야 한다"는 원칙만 정했다.
4. **사고 판은 pull이 거절하지 않고 후보에서 빼며 경고한다.** 결정 8은 "pull은 받지 않는다"였다. 거절할지, 빼고 남은 후보로 계속할지는 Claude가 정했다. 까닭: 남의 브랜치 하나에 사고가 있다고 모든 사람의 pull이 막히지 않게 하기 위해서다.
5. **후보 판에 이번 pull이 들이는 커밋이 가진 판을 더한다(E1).** 그리고 후보가 더 늘지 않을 때까지 1~3단계를 되풀이한다. r27 검수의 지적을 Claude가 이렇게 풀었다.
6. **끝난 판의 범위.** D·O는 cancelled와 withdrawn, X는 fulfilled와 cancelled다.
7. **3-way의 세부.**
   - 가장 나중 공통 조상이 여럿이고 그 본문이 서로 다르면 갈라짐으로 본다.
   - 두 쪽이 모두 공통 조상 그대로이면, 어느 쪽도 앞으로 나간 것이 아니므로 같은 본문으로 본다(G2).
8. **남는 판을 정하는 차례.** 끝난 쪽 규칙(결정 13)을 먼저 적용하고, 3-way(결정 15)를 그다음에 적용한다. → r30에서 뒤집었다(53번).
9. **같은 본문의 서로 다른 판 중 들일 커밋.** (HEAD에 없는 커밋 수, 커밋 OID) 순으로 고른다(TIE). 결정 11은 같은 판의 사본만 다뤘다. 서로 다른 판으로 넓힌 것과 OID로 동률을 푸는 것은 Claude가 정했다. → r42: 결정 30으로 첫 기준(내 판을 포함하는 판)을 더했다.
10. **계약 파일과 고정된 명세 파일은 pull이 정하고, git merge 결과는 코드에만 쓴다.** r27 검수의 공통 원인을 Claude가 이렇게 고쳤다. 이에 딸린 규칙은 다음과 같다. → r42: 명세 파일은 107로 바꿨다(ait는 받지 않을 변경만 정하고 git이 합친다).
    - 지정하지 않은 계약은 내 판을 둔다.
    - 레코드는 지우지 않는다.
    - 끝난 계약은 명세 파일을 놓지 않는다.
    - 6.2의 다시 고정은 받는 결과에서 한다.
11. **들어오는 계약의 정의.** 들이는 커밋이 가진 판 중 내 판에 포함되지 않고 사고 판이 아닌 것이 있는 계약이다. 그래서 옛 판으로 돌아간 계약이나 지운 레코드는 들어오는 계약이 아니다(RV2, DEL1).
12. **도우미 절은 pull이 정한 판 위에 적용하고, 새 판의 `prev`는 그 판이다.** 결정 10은 문법만 정했다. → r30에서 고쳤다(51번).
13. **pull이 쓰는 경로의 정의.** git이 merge로 쓰는 경로와 pull이 정하는 파일을 함께 센다.

### B. 판정의 단계 (기준 2절)

14. **`-m`은 도우미 절이나 `--force`가 있을 때만 필요하다.** → r30: v14 5.3·5.9a와 어긋난다는 지적. 결정 25로 바뀌었다(고르기에도 `-m`).
15. **"멈추면 아무것도 바꾸지 않는다"의 범위.** ref, HEAD, index, 작업 폴더, ait 상태다. 객체 저장소에 객체가 느는 것은 예외로 둔다.
16. **0단계(시작 조건)에 둔 것.**
    - pull이 쓰는 경로에 커밋하지 않은 변경이 있으면 멈춘다. 추적하지 않는 파일도 같다. merge인데 index가 HEAD와 다르면 `E_DIRTY`다.
    - shallow 경계 밖의 이력이 필요하면 멈춘다.
    - partial clone에서는 git이 객체를 받아 오는 대로 읽고, 받아 오지 못하면 멈춘다.
17. **경고와 오류 문구.** 영어 문구 전부를 Claude가 썼다.
    - 갈라짐: `error: 'D' has 2 latest versions…` / `hint: pick one: …`
    - 지정: `error: taking 'a2' also changes contracts you did not name: …` / `hint: name them too: …`
    - 끝난 쪽: `warning: your change to 'D' is overridden: …`, `warning: the change to 'D' in 'b1' is overridden: …`
    - 사고 판: `warning: skipping 'D' at 'a' (a2): it was changed outside ait's rules`
    - 레코드 삭제: `warning: skipping the removal of 'Q' in 'a1': records are never removed`
    - 작업 폴더: `error: your local changes to … would be overwritten by this pull`
    - 받은 것: `included K from 'C'`, `kept K`
18. **끝난 쪽이 이길 때 다른 브랜치의 판이 빠지는 경우의 경고.** 결정 13은 내 판이 빠지는 경우만 다뤘다.
19. **결과 판의 꼴.** 남는 판이 하나인데 내 판을 포함하지 않으면(앞으로 나갔거나 끝난 쪽이 이겼으면), 그 본문에 `prev` = {그 판, 내 판}인 새 판을 만든다.
20. **`K=C`의 규칙.**
    - C의 판은 남는 판이어야 한다.
    - 남는 판이 하나면 새 판을 만들지 않는다.
    - `K=HEAD`인데 내 판이 유일하게 남으면 `already`다.
    - C의 판이 남는 판이 아니면 멈춘다. 그 계약이 갈라져 있으면 고르기 hint를, 아니면 고르기를 뺀 `pull K…`를 준다(KB1~KB3).
21. **갈라진 계약이 여럿이면 모두 같은 커밋을 고르는 hint를 먼저 준다(SF1).**
22. **내 브랜치가 git으로 옛 판에 돌아간 뒤 `pull D`를 하면, 가장 나중 판을 HEAD 위의 커밋으로 적는다(RV3).** 코드는 오지 않는다.
23. **들일 끝이 여럿일 때의 차례는 커밋 OID 순이다.** 결정 14는 "차례로"만 정했다. → 결정 20에서 사용자가 "충돌 없는 끝을 먼저 커밋 ID 순으로, 충돌하는 끝은 마지막"으로 정했다.
24. **`pull D`는 `.ait/D`만 본다.** 떠맡기 기록은 들이는 이력에 있거나, D와 O를 함께 지정했을 때만 본다(K7). 검수자 한 명은 반대로 제안했다. 그렇게 하면 관계없는 브랜치에서 누가 D를 떠맡기만 해도, 그 브랜치를 통째로 받아야 D를 받을 수 있게 된다. 그래서 Claude가 이쪽으로 정했다. → r30: 결정 7과 어긋나고 r27의 고침을 되돌렸다는 지적. 결정 23으로 뒤집혔다.
25. **구조 검사(4단계)는 이 pull이 바꾼 레코드에 얽힌 위반만 본다.** HEAD에 이미 있던 위반은 시작 조건(5.10)에 맡긴다.
26. **hint 하나에 모든 위반의 절을 계약 ID 순으로 한 번씩 담는다.**
27. **확인 검사(5단계)의 세부.**
    - 막는 것은 pull이 **새로** 만드는 미확인뿐이다(9.1의 "새 미확인").
    - 이미 미확인이던 것(내 쪽이든 보낸 쪽이든)은 막지 않고 `warning: 'D' comes in unverified`와 H7을 쓴다(v14 7.12.1-7의 선례).
    - provider를 찾을 수 없게 되면 `--force` 대신 H8의 꼴을 준다.
    - 확인한 파일에서 코드가 충돌하면 `--force`를 주지 않는다.
    - 코드가 충돌할 pull에는 `--force`를 받지 않는다.
28. **되돌리기 hint는 5.9a를 따른다.** current offer가 그 계약을 떠맡았으면 그 offer도 함께 되돌린다(S4, IND1). 결정 6·10의 hint 꼴을 5.9a에 맞춰 넓힌 것이다.
29. **받기(6단계)의 세부.**
    - fast-forward 조건: 받는 결과가 그 커밋의 tree와 같을 때만 한다.
    - pull은 `commit-tree`로 커밋을 직접 만들고 hook을 거치지 않는다(v14 11.2를 바꿈).
    - 새 판을 적는 커밋은 요청 커밋(기록줄)이다.
    - 코드 충돌로 멈출 때 pull의 결정을 ait 로컬 상태에 적는다. 마치는 커밋의 hook은 그것을 다시 정규화하지 않는다. → r33: 로컬 상태를 뺐다(81).
    - 들일 끝이 여럿인데 중간에 충돌하면 앞 단계는 병합 커밋으로 남는다. 다시 실행하면 나머지를 받는다. 결정 14에서 Claude가 제안하고 사용자가 OK했다. 다만 중간 커밋의 계약 파일을 "그때까지 들인 커밋으로 정한 것"으로 둔 것은 Claude가 정했다. → r30: 중간 커밋이 abort해도 시작 상태로 돌아가지 않고 구조 위반일 수 있다는 지적. 결정 20으로 정해졌다(중간 커밋 없음).

### M. C로 옮기며 Claude가 정한 것 (2026-10-10)

사용자 결정(2026-10-10): 글과 Python 재현을 마치고 C로 쓴다. 먼저 3절의 행을 `t/pull/` 테스트로 옮긴다. 테스트는 구현 전까지 `make test`에서 빼고 `make test-pull`로 따로 돌린다. 이력은 레코드를 직접 쓰는 도우미로 만든다. 알림(결정 16, 18)은 당분간 테스트하지 않는다.

114. **pull의 멈춤과 종료 코드는 git을 따른다.** `error:`로 시작하는 멈춤(갈라짐, 지정, 사고 판, 같은 파일 두 번 충돌, 확인 검사, 작업 폴더, 코드 충돌)은 종료 코드 1이다. git 2.53.0에서 merge가 덮어쓸 로컬 변경·추적하지 않는 파일·index 변경으로 거절할 때와 내용 충돌로 멈출 때 모두 `error:`와 종료 코드 1이었다(scratchpad `r43-gitcodes`). 기준이 문구를 정하지 않은 멈춤(KB1의 고르기 거절, C3의 확인한 파일 충돌, NEW2의 추적하지 않는 파일, SH1의 shallow, 코드 충돌 pull의 `--force`)은 v14 5.8을 쓸 때 정한다. 그때까지 테스트는 종료 코드와 `error:`만 본다.
115. **받지 않는 변경은 결과의 고정으로 바꿔 git에 넘긴다.** 결과가 그 경로를 한 내용으로 고정하지 않으면 merge base의 내용이다. 107의 "merge base의 내용으로 되돌린다"를 고친다. 끝이 여럿이면 git은 뒤의 끝을 지금까지 합친 결과와의 merge base(더 새로운 것)로 합치므로, 앞서 merge base 내용으로 되돌린 것이 그 merge base에서는 변경으로 보여 충돌했다(X1, t63 작성 중 발견, `lib.py`로 재현). 결과의 고정으로 바꾸면 어느 merge base에서도 결과와 같은 쪽이 되어 충돌하지 않는다. 다른 행의 결과는 그대로였다. 받지 않는 변경의 뜻(결과가 원하는 내용을 남긴다)에서 끌어냈다.
    - 같은 테스트 작성에서: RP4는 결과의 본문이 내 판의 것이라 들일 커밋이 없다(G4b). 행이 a1을 들이는 것으로 적혀 있었고, 그래서 v14 옛 식에 대한 사실도 틀렸다. 고쳤다. RN1은 107을 그대로 따르면 내 명세 변경(끝난 쪽에 덮인 내 판의 명세)을 받지 않으므로 `src/moved.c`가 a의 내용이다. 행을 고쳤다.
116. **테스트를 쓰며 정한 출력의 세부.** 기존 규칙에서 하나로 나오는 것만 적는다. 문구 전체는 v14 5.8을 쓸 때 정한다.
    - 이름을 더하라는 hint의 이름은 계약 ID 순이다. 구조 검사 hint의 "절은 계약 ID 순"과 같다(K1, E1, K8). K8의 hint는 `pull D D2 O1`이 된다.
    - 고르기 hint의 커밋 이름은 그 판의 들이는 커밋이다(1절, TIE 순서). E1b는 `D=b1`이다. 사용자가 그 판을 가진 다른 커밋(b2)을 주어도 받는다(KB1의 규칙).
    - 고르기가 없는 hint(KB1, KB2의 `pull D`)에는 `-m`이 없다(결정 25).
    - 지정 검사 문장: 들이는 커밋이 여럿이면 `taking 'c1' and 'd1' also changes …`다. 떠맡기 기록 때문에만 필요한 이름에만 `(undertake 'D-O')`를 붙인다(K1의 D는 직접 들어오므로 붙이지 않는다).
    - MERGE_HEAD의 끝은 합친 차례대로 적는다. git이 merge한 차례대로 적는 것과 같다. 충돌 행(`CONFLICT …`, `Automatic merge failed; …`)은 git처럼 stdout에 쓴다.
    - 지정하지 않은 계약의 건너뛰기 경고(MF2)는 2절 1의 두 문구와 같다.
